# osp-api — свой API портала ОСП

Этап 3 переезда (`migration/PLAN.md`): трафик браузера и внешних потребителей переводится с Supabase на
свой сервис. Сейчас здесь маршруты вместо Edge Functions Supabase. Данные пока берутся из Supabase; при
переносе базы меняется только источник, маршруты остаются.

| Маршрут | Вместо | Доступ | Лимиты |
|---|---|---|---|
| `POST /api/fn/s3-presign` | Edge Function `s3-presign` (протокол новый — с ключом операции, ниже) | токен пользователя Supabase; одобренный, не заблокированный; загрузка и удаление — право раздела (`osp_can`); подрядчик — только скачивание файлов своих договоров | 300 в минуту на пользователя |
| `POST /api/fn/ai-assist` | Edge Function `ai-assist` | токен; **только одобренный сотрудник** (функция пускала любого вошедшего) | 6 в минуту и 1 одновременно на пользователя, 4 одновременно всего |
| `GET /api/rates/{kp,supply,larix,health}` | Edge Function `rates-api` (+ `larix` — только здесь) | ключ `X-API-Key` или `?key=`: выпущенный в «Администрировании» (права и срок — в базе) или из `RATES_API_KEYS` (`ключ:kp+larix` — только перечисленные ресурсы, ключ без «:» — kp и supply) | 60 в минуту и 2 одновременно на ключ |
| `GET`, `POST /api/admin/api-keys…` | — | токен или своя сессия; **только администратор**: ключи API — список, выпуск, правка, отзыв, удаление, журнал вызовов (ниже) | выпуск и правка — 30 в минуту на пользователя |
| `POST /api/fn/cover-upload` | бакет обложек `object-photos` Supabase | токен; **сотрудник с правом правки объектов** (`osp_can('objects','edit')`); только изображение до 20 МБ, тип файла подписан, занятое имя — 409 | 300 в минуту на пользователя (общий с файлами) |
| `GET /api/covers/<имя>` | общедоступный адрес обложки в Supabase | без входа, как раньше: `<img>` токен не передаёт; только `UUID.расширение` в каталоге `covers/`, ответ — подписанная ссылка на 10 минут | — |
| `GET /api/covers/<имя>/thumb` | нет: новая | миниатюра той же обложки для карточки, без входа; не вышло — ссылка на оригинал | — |
| `GET /api/health` | — | без доступа; показывает только «задано / не задано» | — |
| `GET /api/ready` | — | только с `127.0.0.1` (через nginx — 404) | — |

Сверх лимитов — `429` с понятным текстом. Тело запроса — до 2 МБ, иначе `413`. Ответы не кешируются
(`Cache-Control: no-store`).

**Отличия от функций** (у `ai-assist` и `/api/rates` всё остальное — запрос, ответ, коды и тексты ошибок —
как у функций, это проверяют `tests/osp-api`):
- `ai-assist` закрыт для неодобренных и подрядчиков.
- `rates-api` без `limit` / `price_min` / `price_max` работает по документации. В функции `Number(null)`
  давал 0: выдача шла по 1 строке и только с ценой 0.
- **Файлы — свой протокол с ключом операции** (заход Б, Р5-ядро; ниже).

### Обложки объектов: cloud.ru вместо бакета Supabase

С данными в базе Яндекса (флаг `ospDb`) обложки лежат в cloud.ru, каталог `covers/` бакета портала, адрес на
сайте — `/api/covers/<имя>` (`src/routes/covers.js`, сайт — `src/api/files.js`). Прежние обложки переносит
`src/covers-copy.js` (`deploy/docker/deploy.sh covers-copy`): каждый файл скачивается по общедоступному
адресу Supabase, кладётся в `covers/` и скачивается обратно для сверки SHA-256; лежащий там другой файл не
перезаписывается. Адреса в базе меняет загрузка копии (`migration/target/load.sh --covers <журнал>`).

**Миниатюры** — `GET /api/covers/<имя>/thumb` (`src/lib/coverThumbs.js`): карточка объекта и окно правки показывают
WebP не больше рамки 800×450 (на обложках прода 11,1 МБ → 0,92 МБ) с постоянного адреса, браузер запоминает ответ на
год (`Cache-Control: immutable`): имя — UUID, файл не перезаписывается. Правило кэша ставит маршрут, nginx его
передаёт только в `location ^~ /api/covers/` (`deploy/docker/web/site.conf`); везде в остальном `/api/` — `no-store`.
Откуда берётся: память процесса (до 16 МБ) → `covers/thumbs/800/<имя>.webp` в хранилище → делается из оригинала один
раз. Разбор — `sharp` в отдельном процессе (`src/lib/coverThumbChild.js`), строго по одному: библиотека — машинный код,
файл присылают люди, поэтому упасть должен этот процесс, а не служба (`oom_score_adj` = 1000); замер в образе при
потолке службы — ~0,9 с на обложку, пик контейнера — 160 МБ из 384. **Не отказывает:** не разобралось (повторно — через
час), хранилище не ответило, ожидающих больше 64, ждали дольше 5 с (миниатюра доделается в фоне) — ответ, как у
оригинала, переадресация без кэша; нет обложки — 404. Барьер записи — показывается, в хранилище не кладётся. Другой
размер рамки — другой каталог (`coverThumbKey`).
Память пуста после каждой выкладки, поэтому служба сама читает обложки из `objects.cover_image_url` в неё сразу после запуска
(`warmCoverThumbs`, по 3 одновременно, `OSP_COVER_WARM=0` — выключить): первому, кто откроет «Объекты», хранилище ждать не приходится.

### Файлы: ключ операции, право записи, удаление

Браузер (`src/api/ospFiles.js`) создаёт ключ операции — UUIDv7 — один раз на выбранный файл и считает
SHA-256. Все шаги идут с этим ключом:

| Действие | Что делает | Повтор |
|---|---|---|
| `upload` | ссылка на PUT; ключ объекта — `<каталог>/<owner_id>/<operation_id>-<имя>` | та же ссылка на тот же объект; документ уже есть — `{ already, document }` |
| `confirm` | объект в бакете есть и того же размера → строка `s3_documents` с `id = operation_id` (под токеном пользователя) | та же строка; параллельный повтор (23505) — тоже |
| `download` | ссылка на скачивание, как у функции | — |
| `delete` | сначала строка (`DELETE … RETURNING`), затем объект | строки уже нет — `{ ok, already }`, хранилище не трогается |
| `rename` | новое `file_name` в строке (право — как у `delete`, расширение прежнее — `src/shared/fileRename.js`); объект и его ключ не меняются | то же имя ещё раз — тот же ответ |
| `describe` | новое `notes` (описание) в строке — только у файлов заявок на ДС, у других там служебные данные (`400`); право — как у `delete`; пустое снимает описание; до 500 знаков | то же значение — та же строка |

- **Права на файл** (11.11.2026): загрузка — `WRITE_RULES`; изменение и удаление (`delete`, `rename`, `describe`) —
  `CHANGE_RULES` по таблице владельца и категории: правка раздела (у ВОР и РД тендера — ещё правка «ВОРов и РД»), у файла
  задачи — загрузивший, автор задачи или администратор. Скачивание — строка видна (правило базы: владелец виден, право
  раздела, охват по объектам), ключ лежит в каталоге своего владельца (иначе — только администратор), владелец виден и
  есть право чтения его раздела (`READ_RULES`). `supply-notes` — строки распознанного счёта при файле расценки снабжения.
- **Загрузка:** предел — `OSP_UPLOAD_MAX_BYTES` (100 МБ), РД, ВОР и тендерный пакет — `OSP_UPLOAD_MAX_BYTES_RD` (300 МБ),
  больше — 413; ссылка подписывает `content-type` и `content-length`. Выданные, но не подтверждённые загрузки —
  `osp_private.s3_upload_intents` ([src/lib/uploadIntents.js](src/lib/uploadIntents.js)): не больше 20 и 2 ГБ на пользователя
  за час (429 `OSP_UPLOADS_PENDING`), объекты без строки старше часа служба удаляет сама.
- **Отпечаток объекта** (12.11.2026, миграция 20270216): `confirm` пишет ETag объекта из хранилища в
  `s3_documents.content_etag` (база без колонки — строка без него, повтором вставки). Ссылка на загрузку живёт ещё до 15
  минут, и по ней объект можно перезаписать другим содержимым того же размера; поэтому `download` файла заявки на проверку
  ДП/ДС (`CHECKED_OWNERS`) сверяет ETag с хранилищем: не совпал — `409 OSP_FILE_CHANGED` и запись в журнале службы, объекта
  нет — 404. Файлы без отпечатка (прежний портал, до миграции) и других разделов — как раньше, без запроса к хранилищу.
- **Файл в обсуждении заявки на проверку** (`doc_category` `doc_check_chat`, `CATEGORY_RULES.doc_check_requests`): загружает
  и удаляет просмотр раздела — как пишет сообщение; отправленный файл не меняется и не удаляется никем, свой черновик автор
  убирает — решает триггер базы `s3_documents_doc_check_guard` (отказ — 403).
- Тот же ключ для другого файла (владелец, имя, тип, размер, SHA-256) — `409 OSP_KEY_REUSE`.
- Объекта нет или размер другой — `409 OSP_NOT_UPLOADED` / `OSP_SIZE_MISMATCH`, строка не создаётся.
- Хранилище не удалило объект после удаления строки — `{ ok, object_deleted: false }` и запись в журнале.
  Остаётся только объект без строки, документа на удалённый файл не бывает.
- **Владелец:** `owner_id` — uuid; сущность существует и видна пользователю (чтение под его токеном, RLS).
  `tender` — тендер или строка `tender_docs` (вкладка «Документы» тендера); `general` — ПСДЦ, заявка
  на ВОР, шаблон раздела или расценка реестра КП, добавленная вручную (`kp_manual_rates`, 20261122);
  `customer` не поддерживается.
- **Право записи** (`WRITE_RULES` в `src/routes/s3Presign.js`) — ровно как в интерфейсе
  (`migration/rights-map.md`):
  - тендер — видеть «Тендеры», «Тендеры на материалы» или «ВОРы и РД»;
  - договор — видеть договоры;
  - объект, контрагент, заявка на ДС, заявка на проверку, документ раздела — правка своего раздела;
  - ПСДЦ — правка договоров; заявка на ВОР — правка тендеров или ВОР;
  - документ ручной расценки реестра КП — правка «Реестра расценок» (`rates_registry`);
  - заявка на ДП — работа с заявками (`dp_requests`) или право их создавать (`dp_requests_create`); свою заявку от чужой
    отличает триггер базы `s3_documents_dp_request_guard` (миграции 20261227, 20261231), строка пишется под токеном пользователя;
  - задача — видеть её;
  - категории со своим правом вместо права раздела владельца (`CATEGORY_RULES`, проверка при ссылке на загрузку,
    подтверждении и удалении): документы «Расчёта ПЗ» объекта (`cost_plan_direct_costs`,
    `cost_plan_kp_before_transfers`) — право `cost_plan_docs` (администратор и экономист ОСП); правка «Объектов» их
    не открывает, а это право не открывает прочие файлы объекта. Кто и когда — журнал `cost_plan_calc_file_log`
    (пишет триггер базы, миграция 20261130).

  Проверка — функция `osp_can` (миграция Р2a). Её нет — `503 OSP_RIGHTS_UNAVAILABLE`: без проверки прав
  не пишем, скачивание работает.
- **Все места загрузки в интерфейсе** перечислены в `tests/osp-api/lib/upload-sites.mjs`. Сканер
  исходников роняет тест, если место появилось или сменило тип владельца, а сервер загружает по каждой
  паре «тип → таблица».

**Безопасность.**
- Строки базы читаются под токеном пользователя, поэтому действует тот же RLS, что в браузере.
- Служебный ключ Supabase используется только в `/api/rates`.
- **Журнал:** пишутся метод, шаблон маршрута, код и время. Адреса с `?key=`, заголовки и тела запросов (в
  них текст договоров) в журнал не попадают. nginx пишет `/api/` без параметров и без ошибок с полной
  строкой запроса (`deploy/nginx/osp.root.sx.conf`). По HTTP `/api/` — 403 без перенаправления: ключ не
  возвращается в `Location`, журнал порта 80 — без параметров.
- Служба работает от отдельного системного пользователя `osp-api`.

**Готовность (`/api/ready`).** Проверяются настроенные зависимости, за 5 с:
- Supabase — `auth/v1/health`;
- S3 — запись и удаление служебного объекта `osp-api/ready-check` (ровно те права, что нужны файлам);
- Anthropic — список моделей, без токенов.

Ответ — `200`, только если **каждая обязательная** зависимость ответила `ok`; иначе `503`. В ответе —
`ok` / `fail` / `not_configured` по каждой и список обязательных. Обязательные — `OSP_API_REQUIRE`, по
умолчанию `supabase,s3,anthropic`: не заданный ключ тоже отказ. Сузить можно только явно — например,
`supabase,s3`, если Anthropic недоступен с сервера; тогда `ospApiAi` не включать. Опечатка или список
без `supabase` — служба не запускается.

По готовности `deploy/api-deploy.sh` решает, засчитать ли выкладку. Не прошла — прежний релиз; для первого
релиза возвращать некуда — служба останавливается.

## Права на маршрутах

Права объявляются на маршруте, а не в теле обработчика (`src/lib/access.js`):

```js
app.route({ method: 'POST', url: '/api/fn/пример', config: {
  access: access.user({ require: 'employee', deny: 'Только сотрудникам' }),
  body: z.object({ title: z.string() }),
}, handler: async (request) => { const { user, roleRow, supabase } = request.auth /* … */ } })
```

- **Закрыто по умолчанию.** Маршрут без `config.access` не регистрируется: сервер не стартует.
- **Открытые маршруты** (без входа пользователя: `access.open`, `access.apiKey`) — только из
  утверждённого списка `src/open-routes.js`, у каждого обоснование.
- **Вошедший пользователь** (`access.user`): токен → лимит, если объявлен → требование к учётке
  (`approved` — одобрен и не заблокирован; `employee` — ещё и не подрядчик) → схема тела. Обработчик
  получает `request.auth`.
- **Тело запроса** — по схеме zod с явным перечнем полей; лишние поля отбрасываются до обработчика. Роль,
  организация и авторство из тела не принимаются: они берутся из `request.auth`.
- **Право на конкретную запись** (чей договор, чей файл) решает обработчик — ему нужны данные записи.

Эталоны лежат в `tests/osp-api/baseline/` и сверяются в `npm run test:api`:
- `routes.json` — маршрут → вид доступа, требование, поля тела. Новый маршрут, новое открытое право или
  новое поле видны строкой в diff.
- `access.json` — замер «кто → маршрут → код ответа» по классам пользователей, включая запрос без входа.

Намеренное изменение прав: `UPDATE_BASELINE=1 npm run test:api` и коммит эталона. Маршрут без замера
прав тест не пропускает.

Проверки перед отправкой в GitHub включаются один раз на машине: `npm run hooks:install`
(`scripts/git-hooks/pre-push`: `lint`, `check:transport`, `test:api`).

## Путь к базе

Маршруты данных ходят в базу только через обёртку транзакции `src/lib/db.js` (маршруты файлов, ИИ и
расценок без шлюза идут через Supabase, со шлюзом — через PostgREST на этом сервере):

```js
const rows = await db.read(who, async (tx) => (await tx.query('select … where id = $1', [id])).rows)
await db.write(who, async (tx) => { await tx.query('update … set … where id = $1', [id]) })
```

- `read` — транзакция только на чтение: читающая операция не может изменить данные.
- `who` — `{ userId, email }` из проверенного сервером входа или `null` для служебной операции. В базу
  уходит собранный здесь контекст, а не исходный токен; он и таймауты действуют до конца транзакции.
- Любая ошибка — откат; подключение с неудавшимся откатом или обрывом в пул не возвращается.
- Запрос — одна параметризованная команда; несколько команд в строке база не примет.
- Одно действие пользователя — одна операция — одна транзакция.
- Пул ограничен (`OSP_DB_POOL_MAX`): у учётки базы общий лимит подключений с другими системами.
- К базе не на этой машине — только с проверкой сертификата и имени сервера: нужен `OSP_DB_CA_FILE`,
  без него служба не запускается. Строка `OSP_DB_URL` проверку не ослабляет: из параметров допустим только
  `sslmode=verify-full`, остальное — отказ при запуске.

В коде сервера нет команд изменения структуры и прав, драйвер базы подключён только в обёртке — это
проверяет `tests/osp-api/no-ddl.test.mjs`. Гарантии обёртки на настоящем PostgreSQL — `tests/osp-api/db.test.mjs`,
проверка сертификата — `tests/osp-api/db-tls.test.mjs`.

## Шлюз данных `/api/db`

Портал читает и пишет базу Яндекса через `/api/db/<таблица>` и `/api/db/rpc/<функция>` — теми же запросами,
что слал в Supabase: `src/api/db.js` отдаёт страницам тот же построитель (`@supabase/postgrest-js`), флаг
`ospDb` выбирает путь. За шлюзом — PostgREST на этом же сервере (`deploy/postgrest`, только `127.0.0.1`).

| Что | Где решается |
|---|---|
| Кто это | шлюз: токен входа Supabase (как у остальных маршрутов); без токена — аноним |
| Какие таблицы, действия, функции и связи в `select` можно вообще | шлюз: `src/data/allow.json` — выдача прав прода как есть (`node scripts/build-db-allow.mjs`) |
| Какие строки видны и изменяемы | база: правила по строкам действуют и на единственную учётку (`migration/target/sql/load-single-owner.sql`) |

- В PostgREST уходит свой токен на 60 секунд: `role` — учётка базы, `osp_role` — кто пользователь
  (`anon` / `authenticated` / `service_role`), `sub`, `email`. Токен браузера дальше шлюза не идёт. PostgREST
  без такого токена запрос не примет, а база откажет запросу без `osp_role` (`osp_private.pre_request`).
- Запрос и ответ передаются как есть: тело — байт в байт, диапазоны, коды и ошибки PostgREST. Отказы самого
  шлюза имеют тот же вид (`{ code, message, details, hint }`): `42501` — не разрешено, `PGRST205` / `PGRST202` —
  такой таблицы или функции для шлюза нет.
- **До чтения тела** шлюз решает всё, для чего тело не нужно: кто это, список, барьер записи (`admit` в
  `src/routes/dbGateway.js`). Запрос, которому нельзя, не занимает память службы, а nginx сайта передаёт тело потоком.
- **Адрес шлюз и PostgREST читают одинаково.** Для PostgREST `;` — тоже разделитель параметров, для `URLSearchParams` —
  нет, поэтому `;` в строке параметров — отказ 400 `PGRST100`; построитель запросов портала кодирует его как `%3B`.
- **Без входа — лимит по адресу** (`dbAnonPerIp`, 300 запросов в минуту, сверх — 429 `OSP_RATE_LIMIT`); вошедшие из одного
  офиса под него не попадают.
- **Барьер записи:** есть файл `OSP_DB_READONLY_FILE` — сервер только читает: запись и вызовы функций через
  шлюз, а также загрузка, подтверждение, удаление, переименование и описание файлов (`/api/fn/s3-presign`) — 503 `OSP_READONLY`;
  чтение и скачивание работают (`src/lib/writeBarrier.js`). Включить: `touch /var/lib/osp-api/db-readonly`,
  выключить: `rm`.
- **Учётки входа** остаются в Supabase Auth. `admin_delete_user` и `admin_confirm_user_email` сначала меняют
  учётку там (служебным ключом, только если база подтвердила, что вызывает администратор), затем строки в
  базе. Учётка не названа (нет `target_user_id`, тело не JSON) — 400 `OSP_AUTH_TARGET`, функция базы не
  вызывается. Список пользователей для администратора читает копию `auth.users` в базе; копия обновляется
  из Supabase Auth перед показом (`src/lib/authUsers.js`).
- **Репетиция переноса.** Сервер сам читает, какая копия лежит в базе (`osp_meta.load_log`, отметку ставит
  `migration/target/load.sh --status rehearsal | final`; `src/lib/loadStatus.js`). У репетиционной копии
  хранилище файлов и вход — те же, что у рабочего портала, поэтому, пока копия не `final`:
  - удаление документа убирает строку, а объект из хранилища — только если документ создан уже в
    репетиции; объект, пришедший с рабочими данными, остаётся (`{ ok, object_deleted: false, rehearsal: true }`);
  - `admin_delete_user` и `admin_confirm_user_email` — 409 `OSP_REHEARSAL`, до обращения ко входу и к базе.

  Отметка не читается (нет подключения, нет таблицы, загрузка не завершена) — считается репетицией.
  `/api/ready` показывает режим: `"data": "rehearsal" | "final" | "unknown"`.
- **Реестр расценок** пересчитывается самой службой (`OSP_REGISTRY_REFRESH=1`, такт 10 минут) — в Supabase
  это делало расписание pg_cron. Только если источники менялись ([src/lib/registryRefresh.js](src/lib/registryRefresh.js)):
  пересчёт на копии рабочей базы — 13 с и 223 МБ временных файлов, 137 раз в сутки. Такт сверяет счётчики записей
  таблиц-источников (список — из зависимостей представлений), без изменений пишет только подпись «Данные на …»;
  не прочиталось или источник не таблица — пересчёт, раз в 6 часов — в любом случае, кнопка «Обновить» — как раньше.
- Маршруты файлов, ИИ и расценок при включённом шлюзе читают данные через тот же PostgREST.
- **Принятые отступления** (`docs/API_RULES.md`): браузер называет таблицы, у шлюза нет схемы тела, права по
  строкам — в базе. Так же устроен портал в Supabase сегодня; перевод разделов на отдельные операции — после.

### Права разделов в шлюзе (11.11.2026)

После списка `allow.json` шлюз решает, какое **право раздела** нужно запросу ([src/lib/dbSections.js](src/lib/dbSections.js),

пользователю сессии ([src/lib/sectionRights.js](src/lib/sectionRights.js): тот же расчёт, что `osp_can()`, кэш 30 с);
не прочитались — 503 `OSP_RIGHTS_UNAVAILABLE`. Отказ — 403 `42501`, до PostgREST запрос не доходит.

- Правило: `"employee"` (любой одобренный сотрудник, строки режет база), `"admin"`, `"none"` (никому через шлюз) или

- Строковые условия — в базе, не в карте: ключи `app_settings` (триггер `app_settings_write_guard`), свой профиль

- **Подрядчик** проходит вместо карты свой явный список [src/data/allow-contractor.json](src/data/allow-contractor.json);
  учётка с регистрации — ещё и `allow-self-contractor.json`.
- **Режимы:** `OSP_DB_SECTIONS_WRITE=enforce` (по умолчанию; `log` — аварийно), `OSP_DB_SECTIONS_READ_REFERENCE=log|enforce`

  кабинета подрядчика — ещё и строка в `allow-contractor.json`.

## Загрузка договорных расценок из Larix.CPM

Не маршрут, а работа службы: вкладка «Договорные расценки (Larix)» реестра расценок читает представление
`larix_rates_registry` над закрытой таблицей `osp_private.larix_rates` (миграции `20261018`, `20261021`), служба раз
в день наполняет её из Larix.CPM (метод «ВОР по договорам», `GET /api/contract/data/project_contract_boq` после
входа `POST /api/login`).

- **Когда.** Такт раз в 5 минут (первый — через минуту после запуска) спрашивает базу `larix_sync_begin`:
  пора ли. База отвечает «да» после 05:00 по Москве, если сегодня ещё не было удачной (или отложенной)
  загрузки, прошлая попытка была больше 30 минут назад и попыток за день меньше 6. Одна загрузка
  одновременно — уникальный индекс в базе (и между копиями службы, и между серверами); зависшая дольше
  30 минут снимается. Барьер записи — такт пропускается.
- **Память.** Ответ — десятки МБ (16.10 — 65 МБ), а загрузка идёт внутри службы с потолком 384 МБ. Поэтому он
  разбирается потоком (`createJsonArrayParser`): каждая позиция сразу становится короткой строкой для базы,
  исходный объект не хранится. Замер (`tests/deploy/larix-memory.test.mjs`): 100 МБ ответа — пик ~215 МБ
  процесса; разбор целиком в тех же потолках убит по памяти. Предел всего ответа `LARIX_MAX_BYTES` (256 МБ)
  защищает от бесконечного ответа, одной позиции — 1 МБ.
- **Как.** Один запрос в Larix вне транзакций базы, проверка каждой позиции (`normalizeBoqRow`: числа
  конечные, id целые, дата ISO, длины строк ограничены; больше 5 % отброшенных — сбой `invalid`), порции по
  1000 (`larix_sync_add_rows`, повтор порции безопасен), замена одной транзакцией (`larix_sync_finish`):
  строка — позиция с ценой материалов и ценой работ, одинаковые строки ВОР (договор, позиция и единица без
  учёта регистра и пробелов, цены) схлопываются в одну (`repeats`), дата договора — по Москве, наш договор — по
  ссылке «Путь к Larix.CPM» (`contracts.document_link`, только однозначное совпадение).
- **Защита данных.** Пустой ответ при непустых данных и падение ниже 30 % прежнего числа позиций — статус
  `held`, прежние расценки остаются, на вкладке предупреждение; принять — `larix sync --force`. Сбой Larix
  или базы — `failed` с причиной из набора (`login | http | timeout | too_large | invalid | db | stale`),
  прежние расценки остаются, повтор — через 30 минут.
- **Секреты.** Логин и пароль Larix — только в окружении службы; токен живёт в памяти одного прогона. Ни
  логин, ни пароль, ни токен не попадают в журнал службы, в журнал загрузок и в тексты ошибок
  (`redact`). Только `https://cpm.su10.larix.ru` (другой адрес — служба не запускается), перенаправления
  не выполняются (тело входа с паролем не уйдёт по чужому адресу), пределы времени и размера ответа.
- **Куда** (`LARIX_SYNC_TARGETS`): `db` — своя база (служебная операция, отметка `osp:internal`);
  `supabase` — база прежнего портала через служебный ключ, только четыре функции `larix_sync_*`. Пока за
  шлюзом репетиция, запись в Supabase — сознательное исключение из правила «не менять общее с рабочим
  порталом»: расценки Larix — не данные людей, их источник — Larix. После переноса — только `db`.
- **Ручной запуск** — `node src/larix-cli.js probe | sync [--force] [--target db|supabase]`, на сервере corp
  — `bash /opt/portals/osp/deploy.sh larix …` (`deploy/docker/README.md`).

Настройки — `LARIX_*` в `osp-api.env.example`; `/api/health` показывает только `larix: true/false`, в
`/api/ready` Larix не входит. Тесты: `tests/osp-api/larix-client.test.mjs` (поддельный Larix),
`tests/osp-api/larix-sync.test.mjs` (настоящий PostgreSQL, обе базы-цели, служба целиком),
`tests/deploy/larix-memory.test.mjs` (память в контейнере с потолками службы, Docker).

## Позиции ВОР для расценки снабжением — заранее (`OSP_SUPPLY_IMPORT=1`)

[src/lib/supplyImport.js](src/lib/supplyImport.js), миграция `20261024_supply_import_state` (обе базы). Такт — раз в 10 минут,
прохода нет, если с прошлого чистого прохода счётчики записей нужных таблиц не менялись (не успели, сбой — проход есть; раз в
6 часов — в любом случае; `runOnce` — всегда). При проходе (первый — через 90 с после запуска) служба проходит по основным тендерам, у которых есть тендер на материалы,
и делает то же, что автозагрузка страницы расценки: файлы ВОР из «ВОРов и РД» (лист «Материалы», иначе лист ВОР по
колонке «КОД»), если ни один не дал позиций — вкладка «ВОР» карточки; пустые устаревшие списки убираются, цены не
трогаются. Итог по тендеру — `tender_supply_import_state` (`ok` | `no_vor` | `issues` | `locked` | `pending`, причины
отказов): по нему реестр тендеров на материалы показывает «Расценка: N из M» / «ВОР не загрузился» / «нет ВОР» без
открытия расценки, а страница не скачивает файл, который служба уже не смогла разобрать.

- **Один код с сайтом.** Разбор и план загрузки — копии `src/utils` в [src/shared](src/shared) (образ собирается только
  из `server/osp-api`). Правка — в оригинале, затем `node scripts/sync-osp-api-shared.mjs`; расхождение роняет
  `tests/osp-api/shared-sync.test.mjs`. Версии файлов и вкладки — в том же виде, что у страницы: служба и браузер не
  перезагружают списки друг за другом.
- **Бережно к серверу** (у службы 384 МБ и 0,45 процессора): файл разбирается в отдельном процессе
  ([supplyParseChild.js](src/lib/supplyParseChild.js): потолок памяти 192 МБ, низкий приоритет, таймаут 2 минуты) —
  не хватило памяти, упадёт он, а не API. За проход — не больше 40 файлов и 6 минут; файл больше 25 МБ не скачивается
  (его разберёт страница). Неразборный, слишком большой или тяжёлый файл не берётся снова до новой версии файла или
  разбора; вкладка «ВОР» читается, только если сменилась её подпись. Повторный проход без изменений ничего не пишет.
- **Запись** — служебная операция (`osp:internal`) с версией строки: одновременная загрузка в браузере не
  перетирается. Завершённый тендер на материалы — списки не меняются (их не пустит и база). При барьере записи такт
  пропускается.
- Тест — `tests/supply/server-import.test.mjs` (слепок прода, настоящие миграции, хранилище-подделка с книгами Excel).

## Кто вошёл

По умолчанию — как раньше: на каждый запрос служба спрашивает Supabase «чей это токен» и читает оттуда
строку ролей. Два ключа окружения переводят оба шага на сервер; включаются по отдельности, в любом порядке:

| Ключ | Что меняется | Проверка в `/api/ready` |
|---|---|---|
| `SUPABASE_JWT_SECRET` | токен проверяется здесь (`src/lib/token.js`): подпись, срок, издатель, назначение, роль | `token`: секрет сверяется с публичным ключом сайта — секрет другого проекта даёт отказ готовности |
| `OSP_DB_URL` (+ `OSP_DB_CA_FILE`) | статус учётки (`user_roles`) читается из базы с кэшем на 30 с (`src/lib/userStatus.js`) | `db`: база отвечает |

- Принимается только токен вошедшего пользователя этого проекта, алгоритм — только HS256. Публичный и
  служебный ключи проекта подписаны тем же секретом, но токеном пользователя не являются — 401.
- Токен живёт до часа и о блокировке не знает. Блокировка, отзыв одобрения и удаление учётки действуют
  через статус из базы — не позже чем через 30 с (предел кэша — минута). Выход пользователя до истечения
  токена сервер не видит.
- База не ответила — 503 «повторите», а не 403: сбой не выдаётся за отсутствие прав.
- Секрет подписи по силе равен служебному ключу (им выпускается токен любого пользователя): только в
  файле окружения службы.
- **Вернуть прежний путь:** убрать ключ из файла окружения и перезапустить службу.

Тесты: `tests/osp-api/token.test.mjs`, `tests/osp-api/identity.test.mjs`.

## Свой вход (tender.su10.ru)

Вход нового портала без Supabase Auth: учётки — в `auth.users` базы Яндекса (те же идентификаторы), пароли —
в закрытой схеме `osp_auth`, сессии — в `osp_session` (миграция `migration/yandex/20261019_own_auth.sql`).
Пароль проверяет эта служба, сессия — непрозрачный id в cookie. Вход osp.root.sx не меняется: он в Supabase.

**Режим** `AUTH_MODE` — переключается одной строкой окружения и перезапуском API, без сборки
(`scripts/deploy-server.sh auth-mode`):

| Режим | Что принимает | Для чего |
|---|---|---|
| `supabase` (по умолчанию) | только токен Supabase | как раньше |
| `both` | токен Supabase и свою сессию — только пилоту (`OSP_AUTH_PILOT_IDS`) | проверка в одном браузере (`?features=ownLogin`) |
| `own` | только свою сессию; токен Supabase — 401 `OSP_AUTH_MODE` (вкладка перезагружается) | после переключения; Supabase службе не нужен |

Фронт узнаёт режим из `GET /api/auth/config`, только если в `config.json` есть `authServer: true` (на
osp.root.sx его нет — сервер не спрашивается). В режимах `both` и `own` служба не стартует без `OSP_AUTH_KEYS`,
`OSP_PUBLIC_ORIGIN`, `OSP_DB_URL` и шлюза данных; `/api/ready` проверяет `auth` (канарейка ключа, все ключи
строк паролей есть в окружении), `db`, `gateway`.

**Маршруты** (`src/routes/auth.js`): `GET /api/auth/config`, `POST /api/auth/login`, `POST /api/auth/logout`
(открытые), `POST /api/auth/password`, `GET /api/auth/me`, `POST /api/auth/admin/users`,
`POST /api/auth/admin/reset-password` (администратор). Самостоятельной регистрации нет: писем портал не
отправляет, учётки и временные пароли выдаёт администратор (временный показывается один раз, при входе его
обязательно сменить).

**Гарантии** (`tests/osp-api/own-auth.test.mjs`, `own-auth-unit.test.mjs`):

- **Пароли.** Прежние — bcrypt из Supabase, люди входят тем же паролем; после входа отпечаток пересчитывается
  в scrypt (`src/lib/auth/passwords.js`: N=2^15, r=8, p=3, соль 16 байт, `maxmem` 64 МиБ, не больше 4 расчётов
  сразу и 32 в очереди). В базе отпечаток зашифрован ключом сервера (AES-256-GCM, привязка к учётке).
- **Новые пароли** (`src/lib/auth/policy.js`, NIST SP 800-63B-4): NFC, 15–128 кодовых точек, без правил
  состава; целиком — не из списка распространённых (`src/data/common-passwords.txt.gz`) и не почта или ФИО.
- **Перебор.** По почте: после 5 неудач пауза от 1 до 15 минут (в базе, и для несуществующей почты); по адресу
  клиента — 60 попыток за 10 минут. Время ответа одинаково для любой учётки, ответ на неудачу один.
- **Гонка входа и смены пароля.** Сессия создаётся в одной транзакции только при той же версии пароля, что
  была проверена; смена, сброс и перенос пароля повышают версию и отзывают сессии той же транзакцией.
- **Сессия.** `__Host-osp_session` (HttpOnly, Secure, SameSite=Lax), в базе — только sha256 id; без
  активности 14 дней, всего 30. Блокировка и снятие одобрения (в том числе правкой строки `user_roles`)
  отзывают сессии триггером — доступ прекращается не позже 5 с.
- **CSRF.** Меняющий запрос со своей сессией — заголовок `X-OSP-CSRF` (= cookie `__Host-osp_csrf`), `Origin`
  портала и `Sec-Fetch-Site: same-origin`; вход — строгие `Origin`, `Sec-Fetch-Site` и только JSON.
- **Кто это** (`src/lib/principal.js`) — одна проверка для функций, шлюза и `/api/auth/*`; пользователь в ней
  не создаётся. Удаление учётки администратором — надгробие и функция базы одной транзакцией.
- **Отметки.** Пароли читаются только с отметкой `osp:auth` (`tx.mark('auth')`, только в `src/lib/auth/`);
  пропуск служебных функций их не открывает, а `osp:auth` не видит таблиц портала.
- **Адрес клиента.** `OSP_TRUST_PROXY=peer` — `X-Forwarded-For` только от непосредственного соседа (osp-web
  перезаписывает его адресом клиента, который берёт у общего nginx по жетону).
- В журнал и ответы не попадают пароли, отпечатки, id сессии и CSRF.

Перенос учёток и паролей из Supabase — `migration/accounts/README.md`.

## Вход через Keycloak su10 (`AUTH_MODE=keycloak`)

Единый вход контура su10 (auth.su10.ru, OIDC, код + PKCE, BFF): браузер видит только cookie сессии портала, токены Keycloak —
только на сервере, шифром ключа сервера (AAD — id сессии). Учётка портала прежняя (`auth.users.id`), связь с учёткой СУ-10 —
`osp_auth.identity_links`; роли, объекты, права разделов, одобрение и блокировка в портале — по-прежнему база портала, из токена не
берутся. Переключение `own ⇄ keycloak` — `scripts/deploy-server.sh auth-mode`, порядок — `migration/CUTOVER.md`.

- **Вход** (`src/routes/oidc.js`, `src/lib/auth/oidc.js`): `GET /api/auth/oidc/login?returnUrl=` — только переходом страницы
  (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`), cookie состояния на каждую вкладку (`__Host-osp_oidc_<k>`, шифр,
  30 мин, не больше трёх); `GET /api/auth/oidc/callback` — state своей cookie, `iss` ответа (RFC 9207), код с PKCE, id_token
  (`iss`, `aud`, `nonce`), access token по JWKS (RS256, `iss`, `aud ∋ osp`, `azp = osp`, срок, `sub` — UUID, строгие типы claims).
  Строку запроса возврата снимает `rewriteUrl` до маршрута — в журнал и тексты ошибок она не попадает. `returnUrl` — только свой
  путь (не `//`, не `/\`, не `/api/`), до 512 байт. Discovery — при запуске (Keycloak недоступен — служба работает; issuer не тот —
  не стартует) и лениво потом.
- **Кто это** (`src/lib/principal.js`): матрица режимов — `own` и `both` принимают только парольные сессии, `keycloak` — только
  сессии СУ-10; чужой вид и Bearer — 401 `OSP_AUTH_MODE` (понимают и старые вкладки). CSRF — у любой cookie-сессии. Cookie на
  отказах не стираются (только при выходе).
- **Продление и перепроверка** (`src/lib/auth/oidcRecheck.js`): сессию СУ-10 продлевает только действие — `X-OSP-Activity` = CSRF
  сессии (48 ч без действий, 30 дней всего); раз в 5 минут работы — refresh grant. Отзывают только `invalid_grant`, нет роли
  `access`, чужой `sub`; сбой Keycloak — работа до часа (`OIDC_MAX_OFFLINE_SEC`), повтор раз в минуту, потом 503
  `OSP_SSO_UNAVAILABLE`. Одна перепроверка на сессию — аренда в строке (владелец, 10 с), параллельные ждут до 5 с. Простой
  вкладки (30 минут без действий) — фоновым запросам 401 `OSP_IDLE` без отзыва.
- **Связь и заявки** (`src/lib/auth/identity.js`): по `sub`; по почте — только в окно (`OIDC_LINK_BY_EMAIL=true`), ровно одна
  одобренная учётка без связи, не администратор; иначе заявка. Решения администратора — `src/routes/identityAdmin.js`
  (`/api/admin/identity-requests*`, `/api/admin/identities`, `DELETE /api/admin/users/:id/identity`). Роль «Администратор» и связи
  администраторов — только суперадминистратор: проверка в маршрутах и триггер базы `user_roles_admin_guard` (транзакции идут от
  имени администратора). Пользователей сами не создаём.
- **Сверка группы** (`src/lib/auth/accessSync.js`, `src/lib/auth/kcAdmin.js`): клиент `osp-access-sync`, только участники
  `osp-access`, только нужные поля; раз в `KC_ACCESS_SYNC_INTERVAL_SEC` и по «Проверить СУ-10». Новые участники — заявки
  `kc_sync`; заявки без входов ушедших — снимаются; сессии связанных не из группы — отзываются. Предохранитель: отзыв или чистка
  больше max(10, 20 %), падение участников на 30 % (от 10), пустая группа после непустой — ни отзыва, ни чистки (`held`), принять —
  `deploy-server.sh identity sync --force`. Одна сверка на все экземпляры — аренда в `osp_auth.meta`.
- **Выход:** `POST /api/auth/logout` → `{ endSessionUrl }` (id_token читается до отзыва; отзыв затирает токены триггером).
- **Режимы:** в `keycloak` парольные маршруты, регистрация и решения по регистрациям — 410 `OSP_SSO_ONLY`; код парольного входа
  и пароли остаются — это путь возврата в `own`. `/api/ready` показывает `oidc` справочно, вне готовности.
- **Ручные команды** — `src/identity-cli.js` (`deploy.sh identity …`): `export-users`, `links-apply [--apply]`, `links-report`,
  `sync [--force]`, `revoke-sessions --kind keycloak|password`, `orgs-sync [--check] [--force]` (организации СУ-10, ниже).
- Тесты: `tests/osp-api/keycloak.test.mjs` (Keycloak в памяти, настоящая база и миграции), `identity-cli.test.mjs`,
  `client-auth.test.mjs`.

### Организация учётки СУ-10 → контрагент (`src/lib/auth/orgs.js`, миграция 20270201)

Задача auth — `temp/osp-org-mapping.md`, план ред. 2 (11.11.2026, после рецензии). Правило — fail-closed: ошибка связи открыла бы
подрядчику чужую историю контрагента.

- **Реестр** — подгруппы `/org` realm su10 (`kcAdmin.orgRegistry()`: только прямые подгруппы, атрибуты `su10_org_id`,
  `su10_org_kind`, `org_name`, `inn` — строго; повтор id — обе с ошибкой). Кэш — `osp_auth.su10_orgs` с состоянием
  `active | missing | invalid` и поколением: сверка только полным чтением, неувиденные — `missing`. Предохранитель: пустой
  реестр после непустого, выбывание больше max(5, 20 %) связанных или активных — ничего не меняется (`org.registry {held}`),
  принять — `identity orgs-sync --force`. Сверка — после сверки группы, при открытии вкладки и при незнакомой организации во
  входе (не чаще раза в 15 с). Сбой Admin API — кэш прежний.
- **Связь** — `osp_auth.org_links` (1:1, внешние ключи на кэш и на контрагента, RESTRICT). Ставит только администратор
  (автоматической связи нет: в выгрузке auth нет ИНН реестра; отчёт с подсказками — `migration/org-links/build.mjs`, вне git).
  Подсказки — `src/lib/orgMatch.js` (уверенная — только ИНН реестра с контрольной суммой и единственный живой контрагент не из ЧС).
- **Решение при входе и каждой перепроверке** — по claim `su10_org_id` access token (строгий: массив UUID ≤ 10), под
  `pg_advisory_xact_lock` по организации, контрагент — `FOR SHARE`, `user_roles` — `FOR UPDATE`:
  - подрядчик (роль `contractor` или `counterparty_id`): действующая связь (организация `active` + `contractor`, контрагент жив и
    не в ЧС) → контрагент из связи (другой — `UPDATE` + отметка `counterparty_source='su10'`, все сессии закрыты, `org.change`;
    при перепроверке — 401 `OSP_ORG_CHANGED`); иначе — отказ (`/login?sso_error=org_unmapped`, 403 `OSP_ORG_UNMAPPED`), все сессии
    закрыты, `counterparty_id` не трогается;
  - сотрудник — только своя действующая организация (решение пользователя 11.11); иначе отказ (`org_denied`, 403 `OSP_ORG_DENIED`)
    и закрытие сессий, кроме исключения суперадминистратора (`osp_auth.org_exceptions`: для той же организации, у двух
    организаций в claim — не действует);
  - `counterparty_id = NULL` автоматически не ставится нигде.
- **Сразу, без перепроверки:** отвязка и связь администратором (та же блокировка организации), выбывание связанной организации
  при сверке, чёрный список и удаление контрагента (триггер `counterparties_revoke_sessions`), любая смена `counterparty_id` и
  переход роли в `contractor` и из неё (триггер `user_roles_counterparty_revoke`). Перевод учётки в другую организацию на `/manage`
  доходит при перепроверке (5 минут работы).
- **Мимо сервера контрагента не поменять:** триггер `user_roles_counterparty_guard` — без пропуска служебных функций нельзя ставить
  отметку `su10` и менять контрагента у строки с ней (42501); «Администрирование» при входе через СУ-10 поле не шлёт.
- **Маршруты** — `src/routes/orgAdmin.js` (`/api/admin/su10-orgs*`, `/api/admin/counterparties/:id/su10-org`,
  `/api/admin/su10-org-exceptions*`; исключения — только суперадминистратор). Работают в режимах `own` и `keycloak` при
  `OIDC_ISSUER`, `KC_ADMIN_*` и таблицах: связи готовят до переключения, в `own` на вход по паролю они не влияют. «Создать
  пользователя» по заявке: подрядчику контрагент — только из связи (409 `org_unmapped`), сотруднику не своей организации — 409
  `org_not_own`, СУ-10 не ответил и организации нет — 503.
- **Готовность режима keycloak** (`/api/ready`, `auth`): таблицы, поколение полной сверки и действующая своя организация.
  `deploy-server.sh auth-mode keycloak` сначала запускает `identity orgs-sync --check` (права: `token`, поиск `/org`,
  `children`, участники группы, `users/{sub}/groups` — нужно `view-users`, при необходимости `query-groups`) и `identity orgs-sync`.
- Тесты: `tests/osp-api/su10-orgs.test.mjs` (настоящая база, Keycloak в памяти — `tests/osp-api/lib/fake-keycloak.mjs`),

## Регистрация подрядчика на сайте

Два режима, `OSP_CONTRACTOR_SIGNUP_MODE` (закрыта, пока не заданы все настройки, `osp-api.env.example`: тогда открытые адреса отвечают 404, а
`/api/auth/config` не сообщает `signup`; иначе там же `signupMode`):

**`manual` — по умолчанию (05.11.2026): заявки решает администратор, почта не нужна.** `POST /api/auth/register` сразу ставит заявку в очередь `review`, без пароля и письма. Те же проверки компании, но их итог — подсказка, что проверить (`reasons`), а не решение: `new_company`, `contact_matches` (почта совпала с контактом в карточке), `contact_differs`, `no_company_mail`, `account_exists`, ЧС и связи с ним, `company_unverified`, `previously_refused`, `email_deleted`. Ответ заявителю всегда один. `POST /api/admin/contractor-signups/:id/decision` с `approve` создаёт учётку `self_registered` с `must_change` и один раз возвращает `temporaryPassword`; необязательный `counterpartyId` — контрагент из реестра, если по ИНН компания не нашлась (в реестре бывает пустой ИНН); при совпавшем ИНН, удалённом и из ЧС — 409. Отказ письма не шлёт. Почта заявителя не подтверждена, поэтому доказательство одно: администратор проверяет человека по контактам из карточки, а не из заявки. Адреса `preview`, `confirm`, `claim`, `password/forgot`, `password/reset` отвечают 404, очередь писем не запускается. Заявку подать дешевле, чем с подтверждением, поэтому пределы ниже: 50 в сутки всего, 5 с адреса (`OSP_SIGNUP_DAILY_CAP` меняет первый).

**`email` — самостоятельно, на будущее, когда появится почта** (дальше всё про этот режим). Подрядчик регистрируется сам: заявка → письмо → подтверждение → проверки → кабинет.

| Адрес | Что делает |
|---|---|
| `GET /api/auth/register/challenge` | задача на вычисление (перед заявкой и письмом о пароле) |
| `POST /api/auth/register` | заявка без пароля: `202 { ok: true }`, есть учётка с этой почтой или нет |
| `POST /api/auth/register/preview` | что подтверждается — по ссылке из письма |
| `POST /api/auth/register/confirm` | хозяин почты подтверждает и задаёт пароль: `{ status: 'active' \| 'review' }` |
| `POST /api/auth/register/claim` | подтверждение или отказ с почты компании из реестра |
| `POST /api/auth/password/forgot`, `/reset` | новый пароль по письму: только учётки с регистрации |
| `GET /api/admin/contractor-signups`, `POST …/:id/decision` | заявки администратору |

**Пароль — только у хозяина почты.** В заявке его нет: иначе чужой человек указал бы почту директора и свой пароль, директор подтвердил бы
письмо СУ-10, и кабинет открылся бы чужому паролем. Страница по ссылке показывает компанию, ИНН и контакт и просит задать пароль.

**Чем заканчивается подтверждение почты.** Новая компания — учётка и контрагент с пометкой `registered_via='self'`. Компания из реестра:
почта совпала с контактом в карточке — учётка сразу; иначе ссылка на почту из карточки (ИНН общедоступен и ничего не доказывает), учётки до
ответа нет; об открытом доступе узнают все адреса компании и отдел. На решение администратору: ИНН, почта, телефон, домен (кроме общих почтовых служб) или название совпали с ЧС,
связь с компанией из ЧС через `counterparty_relations`, в карточке нет почты, ИНН занят компанией с другой регистрации (первый занявший не решает за настоящую компанию), у компании заблокированная
учётка, компания удалена, этой почте или ИНН уже отказывали, компания отказала или не ответила за 7 дней, учётку раньше удалил администратор, превышен предел новых компаний. Для заявителя всё это —
одно «проверяется». Предел: `review` по свежему ИНН значит совпадение контакта или названия с ЧС, подбор ограничен подтверждением почты и лимитами. Компанию в ЧС администратор одобрить не может.
ЧС после регистрации блокирует учётки организации и её дублей по ИНН сразу (триггер, сессии отзываются).

**Что нельзя учётке с регистрации** (`user_roles.self_registered`, ограничение базы: только `contractor`):
- шлюз: только `src/data/allow-self-contractor.json`, остального для неё нет (404). Форма запроса — только простые условия и имена колонок, остальное — отказ; то же без входа. Лимит запросов, одновременных запросов, тело не больше 2 МБ. Расширить список — решение о том, что видит подрядчик, а не правка;
- файлы: `/api/fn/s3-presign` — 403 (требование `approved`), правило `s3_documents` строк не отдаёт. Исключение одно, с 05.11.2026, решение пользователя: **файл ВОР для расценки** — `POST /api/fn/bid-vor-file { file_id }` (`src/routes/bidFiles.js`, требование `contractor`, лимит файлов). Решает функция базы `bid_vor_file` под входом подрядчика: только Excel-файл ВОР идущего тендера и только при доступе организации (участник или заявка не отклонена); иначе 404. Ответ — подписанная ссылка и имя файла, без ключа. Функции нет в списках шлюза. С 11.11.2026 (решение пользователя, миграция 20270113) — ещё **свой ВОР с расценками**: `POST /api/fn/bid-file` (тот же `src/routes/bidFiles.js`, требование `contractor`, барьер записи) — `upload` (ссылка на PUT), `confirm` (объект в хранилище есть и того же размера → строка `tender_bid_files`, прежний файл этой ведомости убирается из хранилища; загрузку, которую база не приняла, служба тоже убирает), `download`, `delete` (сначала строка, затем объект). Решают функции `bid_file_target` / `bid_file_save` / `bid_file_remove` / `bid_file_get` под входом подрядчика: тендер открыт, организация — участник или заявка не отклонена, ведомость — Excel-файл ВОР этого тендера; ключ `bids/<тендер>/<организация из базы>/<ключ операции>-<имя>` задаёт служба, база принимает его только в каталоге своей организации; сводку сумм (её считает страница) служба сокращает до известных полей (`cleanSummary`). Администратору — `POST /api/admin/bid-file { file_id }` (только скачивание). Функций нет в списках шлюза, таблица `tender_bid_files` — только чтение (своя организация, администратор);
- база, второй замок (20261204): `current_counterparty_id()` для неё пуст — на нём держатся `is_my_tender`, `is_my_contract` и правила договоров,
  сметы и КП; `contractor_contracts` и `contractor_set_participation` отказывают;
- `bid_rates_save`: только позиции ВОР этого тендера; наименование, ед. изм. и объём — из разбора, а не из запроса;
- тендеры и позиции — только идущие, даже если её компания участвовала в прошлых;
- реестр расценок: цены компании с регистрации — только если инженер сделал её участником тендера.

**Позиции ВОР** разбирает служба (`src/lib/bidPositions.js`, отдельный процесс, раз в 10 минут, когда регистрация открыта): в `osp_private.bid_vor_files`
только наименование, ед. изм., объём, структура и особые условия; другие колонки и скрытые листы не читаются (скрытые строки видимых листов — читаются: отдел мог скрыть их фильтром). Имя файла подрядчик видит. Читает `bid_positions`.

**Защита:** только с портала (Origin, Sec-Fetch-Site, JSON), тело до 8 КБ; поле-ловушка; задача на вычисление (одноразовая, подписана ключом процесса); отпечаток пароля считается только по настоящей ссылке
из письма; лимиты по адресу и общий в памяти, в базе — за сутки по адресу, почте, домену, новым компаниям и всего; домен почты проверяется по DNS; временные почтовые
службы не принимаются. Смена пароля — с лимитом. Пароль — те же правила, что у своего входа (от 15 знаков, без распространённых). Письма — очередью в зашифрованном виде
(`src/lib/auth/mailOutbox.js`), только текстом; ссылка — токен после `#`, в базе sha256, одноразовая; открытие ссылки ничего не меняет, подтверждает нажатие, вход — отдельно паролем.
В журнал не попадают пароль, ссылки, данные формы. Заявки и письма — `osp_auth` (только отметка `osp:auth`).

**Чего нет:** проверки компании во внешних реестрах (ЕГРЮЛ): выдуманная компания с верным по контрольной сумме ИНН зарегистрируется, но с пометкой «с сайта»,
и её цены не попадут в реестр, пока инженер не сделает её участником.

Тесты: `tests/osp-api/contractor-signup.test.mjs` (настоящая база), `signup-rules.test.mjs`, `tests/tender/contractor-signup-ui.test.mjs` (браузер),
`tests/tender/contractor-self-access-db.test.mjs` (копия прода: полный обход всех таблиц от имени такой учётки).

## Включение на портале

Фронт вызывает функции через `invokeFunction` (`src/api/functions.js`), у каждой свой флаг. **С данными в
базе Яндекса (`ospDb`) файлы идут через osp-api при любом значении `ospApiFilesV2`**, функция файлов
Supabase не вызывается вовсе (`src/api/serverPath.js`): она работает с базой Supabase и удалила бы из
хранилища файл, на который ссылается другая база. ИИ к данным не привязан и идёт по своему флагу.
- `ospApiAi` — для `ai-assist`;
- `ospApiFilesV2` — файлы. Включать только после Р2a/b (`osp_can`) и миграции `20261011` (колонка `sha256`)
  на проде.
- `ospApiFiles` — флаг сборок до захода Б, с прежним протоколом. **Не включать:** новый сервер прежний
  протокол загрузки не принимает. Надёжнее держать в `config.json` явное `false`.

Включить:
- **один браузер (проверка на проде):** `https://osp.root.sx/?features=ospApiAi`, снять — `?features=-ospApiAi`;
- **все пользователи:** `/var/www/osp/shared/config.json` → `{"features": {"ospApiAi": true}}`.

**Откат:** явное `false` в `config.json` выключает флаг и в пилотных браузерах. Открытые вкладки
перечитывают флаги каждые 2 минуты и при возврате на вкладку — перезагрузка не нужна. Путь выбирается в
начале операции: начатая операция заканчивается тем же путём.

**API реестра расценок на tender.su10.ru** (`https://tender.su10.ru/api/rates/…`, инструкция для потребителя —
`docs/RATES_API.md`). `kp` и `supply` при шлюзе читаются через свой PostgREST ролью `service_role` (представления
пускают её через `osp_registry_reader()`), служебный ключ Supabase не нужен. `larix` — служебное чтение своей
базы (`db.read`, READ ONLY, отметка `osp:internal`) из `osp_private.larix_rates`: представление вкладки отдаёт
строки только вошедшему с правом раздела, а у ключа пользователя нет; отбор — параметризованный SQL
(`larixWhere`), колонки — `LARIX_COLS`. Без `OSP_DB_URL` — 503. Ключи — `RATES_API_KEYS`: `ключ:kp+larix` открывает
только перечисленные ресурсы (`kp`, `supply`, `larix`), запись без «:» — kp и supply, как до larix (прежний ключ
договорные расценки сам не получает); запись с неизвестным ресурсом пропускается с ошибкой в журнале (номер
записи, без ключа). Чужой ресурс — 403. Выдача ключа на corp — `deploy/docker/README.md`, «Ключи API реестра
расценок». Тесты — `tests/osp-api/server.test.mjs` («rates-api»), `tests/osp-api/larix-sync.test.mjs` («API
смежным отделам»).

### Ключи API: «Администрирование» → «Доступ к API»

Ключи выпускает администратор портала (`src/routes/apiKeys.js`, хранилище и проверка — `src/lib/apiKeys.js`,
таблицы — `migration/yandex/20261111_api_keys.sql`, только база Яндекса):

| Маршрут | Что делает |
|---|---|
| `GET /api/admin/api-keys` | ключи без отпечатков, перечень ресурсов (`API_RESOURCES`), сегодняшний день по Москве |
| `POST /api/admin/api-keys` | `{ name, scopes, expiresOn?, note? }` → `{ key, secret }`: ключ `osp_` + 43 знака — **только в этом ответе** |
| `POST /api/admin/api-keys/:id` | название, примечание; права и срок — только у выпущенного здесь и не отозванного (иначе 409) |
| `POST /api/admin/api-keys/:id/revoke` | отзыв — сразу и навсегда, `{ reason? }` |
| `POST /api/admin/api-keys/:id/delete` | убрать из списка: ключ отзывается, строка с отпечатком и журнал остаются |
| `GET /api/admin/api-keys/calls` | журнал: `?key=<id>&errors=1&before=<id>&limit=100` |

- **В базе — только sha256 ключа** и первые знаки (`osp_` + 8) для узнавания; таблицы — в `osp_private`, правило
  по строкам пускает только служебные операции (отметка `osp:internal`), права проверяет маршрут (`require: 'admin'`).
- **Проверка ключа** на `/api/rates/*`: отпечаток есть в базе — решает строка (отозван, удалён, срок истёк по Москве —
  401 с `code`); нет — ключ из `RATES_API_KEYS`, как раньше. База не ответила — ключи из настроек сервера работают,
  выпущенным здесь — 503.
- **Ключи из `RATES_API_KEYS`** служба заносит в список при запуске (`source = 'env'`, имя «Ключ из настроек сервера
  № N», видны 4 первых знака): их можно переименовать и отозвать, права — по-прежнему строкой; убранный из строки —
  «Убран с сервера» и не действует. Таблиц ещё нет (миграция не применена) — повтор раз в 10 минут, без перезапуска.
- **Журнал вызовов** (`osp_private.api_key_calls`): ресурс, код, строк, время ответа, адрес, причина отказа — после
  ответа, его не задерживая; при барьере записи не пишется; старше 90 дней удаляется тем же тактом.
- Тесты — `tests/osp-api/api-keys.test.mjs` (настоящий PostgreSQL), права маршрутов — `tests/osp-api/access.test.mjs`.
