# osp-api — свой API портала ОСП

Этап 3 переезда (`migration/PLAN.md`): трафик браузера и внешних потребителей переводится с Supabase на
свой сервис. Сейчас здесь маршруты вместо Edge Functions Supabase. Данные пока берутся из Supabase; при
переносе базы меняется только источник, маршруты остаются.

| Маршрут | Вместо | Доступ | Лимиты |
|---|---|---|---|
| `POST /api/fn/s3-presign` | Edge Function `s3-presign` (протокол новый — с ключом операции, ниже) | токен пользователя Supabase; одобренный, не заблокированный; загрузка и удаление — право раздела (`osp_can`); подрядчик — только скачивание файлов своих договоров | 300 в минуту на пользователя |
| `POST /api/fn/ai-assist` | Edge Function `ai-assist` | токен; **только одобренный сотрудник** (функция пускала любого вошедшего) | 6 в минуту и 1 одновременно на пользователя, 4 одновременно всего |
| `GET /api/rates/{kp,supply,health}` | Edge Function `rates-api` | ключ `X-API-Key` или `?key=` (`RATES_API_KEYS`) | 60 в минуту и 2 одновременно на ключ |
| `POST /api/fn/cover-upload` | бакет обложек `object-photos` Supabase | токен; **сотрудник с правом правки объектов** (`osp_can('objects','edit')`); только изображение до 20 МБ, тип файла подписан, занятое имя — 409 | 300 в минуту на пользователя (общий с файлами) |
| `GET /api/covers/<имя>` | общедоступный адрес обложки в Supabase | без входа, как раньше: `<img>` токен не передаёт; только `UUID.расширение` в каталоге `covers/`, ответ — подписанная ссылка на 10 минут | — |
| `GET /api/health` | — | без доступа; показывает только «задано / не задано» | — |
| `GET /api/ready` | — | только с `127.0.0.1` (через nginx — 404) | — |

Сверх лимитов — `429` с понятным текстом. Тело запроса — до 2 МБ, иначе `413`. Ответы не кешируются
(`Cache-Control: no-store`).

**Отличия от функций** (у `ai-assist` и `/api/rates` всё остальное — запрос, ответ, коды и тексты ошибок —
как у функций, это проверяют `tests/osp-api`):
- `ai-assist` закрыт для неодобренных и подрядчиков.
- `rates-api` без `limit` / `price_min` / `price_max` работает по документации. В функции `Number(null)`
  давал 0: выдача шла по 1 строке и только с ценой 0.
- **Файлы — свой протокол с ключом операции** (заход Б, Р5-ядро; ниже).

### Обложки объектов: cloud.ru вместо бакета Supabase

С данными в базе Яндекса (флаг `ospDb`) обложки лежат в cloud.ru, каталог `covers/` бакета портала, адрес на
сайте — `/api/covers/<имя>` (`src/routes/covers.js`, сайт — `src/api/files.js`). Прежние обложки переносит
`src/covers-copy.js` (`deploy/docker/deploy.sh covers-copy`): каждый файл скачивается по общедоступному
адресу Supabase, кладётся в `covers/` и скачивается обратно для сверки SHA-256; лежащий там другой файл не
перезаписывается. Адреса в базе меняет загрузка копии (`migration/target/load.sh --covers <журнал>`).

### Файлы: ключ операции, право записи, удаление

Браузер (`src/api/ospFiles.js`) создаёт ключ операции — UUIDv7 — один раз на выбранный файл и считает
SHA-256. Все шаги идут с этим ключом:

| Действие | Что делает | Повтор |
|---|---|---|
| `upload` | ссылка на PUT; ключ объекта — `<каталог>/<owner_id>/<operation_id>-<имя>` | та же ссылка на тот же объект; документ уже есть — `{ already, document }` |
| `confirm` | объект в бакете есть и того же размера → строка `s3_documents` с `id = operation_id` (под токеном пользователя) | та же строка; параллельный повтор (23505) — тоже |
| `download` | ссылка на скачивание, как у функции | — |
| `delete` | сначала строка (`DELETE … RETURNING`), затем объект | строки уже нет — `{ ok, already }`, хранилище не трогается |

- Тот же ключ для другого файла (владелец, имя, тип, размер, SHA-256) — `409 OSP_KEY_REUSE`.
- Объекта нет или размер другой — `409 OSP_NOT_UPLOADED` / `OSP_SIZE_MISMATCH`, строка не создаётся.
- Хранилище не удалило объект после удаления строки — `{ ok, object_deleted: false }` и запись в журнале.
  Остаётся только объект без строки, документа на удалённый файл не бывает.
- **Владелец:** `owner_id` — uuid; сущность существует и видна пользователю (чтение под его токеном, RLS).
  `tender` — тендер или строка `tender_docs` (вкладка «Документы» тендера); `general` — ПСДЦ или заявка
  на ВОР; `customer` не поддерживается.
- **Право записи** (`WRITE_RULES` в `src/routes/s3Presign.js`) — ровно как в интерфейсе
  (`migration/rights-map.md`):
  - тендер — видеть «Тендеры», «Тендеры на материалы» или «ВОРы и РД»;
  - договор — видеть договоры;
  - объект, контрагент, заявка на ДС, заявка на проверку, документ раздела — правка своего раздела;
  - ПСДЦ — правка договоров; заявка на ВОР — правка тендеров или ВОР;
  - задача — видеть её.

  Проверка — функция `osp_can` (миграция Р2a). Её нет — `503 OSP_RIGHTS_UNAVAILABLE`: без проверки прав
  не пишем, скачивание работает.
- **Все места загрузки в интерфейсе** перечислены в `tests/osp-api/lib/upload-sites.mjs`. Сканер
  исходников роняет тест, если место появилось или сменило тип владельца, а сервер загружает по каждой
  паре «тип → таблица».

**Безопасность.**
- Строки базы читаются под токеном пользователя, поэтому действует тот же RLS, что в браузере.
- Служебный ключ Supabase используется только в `/api/rates`.
- **Журнал:** пишутся метод, шаблон маршрута, код и время. Адреса с `?key=`, заголовки и тела запросов (в
  них текст договоров) в журнал не попадают. nginx пишет `/api/` без параметров и без ошибок с полной
  строкой запроса (`deploy/nginx/osp.root.sx.conf`). По HTTP `/api/` — 403 без перенаправления: ключ не
  возвращается в `Location`, журнал порта 80 — без параметров.
- Служба работает от отдельного системного пользователя `osp-api`.

**Готовность (`/api/ready`).** Проверяются настроенные зависимости, за 5 с:
- Supabase — `auth/v1/health`;
- S3 — запись и удаление служебного объекта `osp-api/ready-check` (ровно те права, что нужны файлам);
- Anthropic — список моделей, без токенов.

Ответ — `200`, только если **каждая обязательная** зависимость ответила `ok`; иначе `503`. В ответе —
`ok` / `fail` / `not_configured` по каждой и список обязательных. Обязательные — `OSP_API_REQUIRE`, по
умолчанию `supabase,s3,anthropic`: не заданный ключ тоже отказ. Сузить можно только явно — например,
`supabase,s3`, если Anthropic недоступен с сервера; тогда `ospApiAi` не включать. Опечатка или список
без `supabase` — служба не запускается.

По готовности `deploy/api-deploy.sh` решает, засчитать ли выкладку. Не прошла — прежний релиз; для первого
релиза возвращать некуда — служба останавливается.

## Права на маршрутах

Права объявляются на маршруте, а не в теле обработчика (`src/lib/access.js`):

```js
app.route({ method: 'POST', url: '/api/fn/пример', config: {
  access: access.user({ require: 'employee', deny: 'Только сотрудникам' }),
  body: z.object({ title: z.string() }),
}, handler: async (request) => { const { user, roleRow, supabase } = request.auth /* … */ } })
```

- **Закрыто по умолчанию.** Маршрут без `config.access` не регистрируется: сервер не стартует.
- **Открытые маршруты** (без входа пользователя: `access.open`, `access.apiKey`) — только из
  утверждённого списка `src/open-routes.js`, у каждого обоснование.
- **Вошедший пользователь** (`access.user`): токен → лимит, если объявлен → требование к учётке
  (`approved` — одобрен и не заблокирован; `employee` — ещё и не подрядчик) → схема тела. Обработчик
  получает `request.auth`.
- **Тело запроса** — по схеме zod с явным перечнем полей; лишние поля отбрасываются до обработчика. Роль,
  организация и авторство из тела не принимаются: они берутся из `request.auth`.
- **Право на конкретную запись** (чей договор, чей файл) решает обработчик — ему нужны данные записи.

Эталоны лежат в `tests/osp-api/baseline/` и сверяются в `npm run test:api`:
- `routes.json` — маршрут → вид доступа, требование, поля тела. Новый маршрут, новое открытое право или
  новое поле видны строкой в diff.
- `access.json` — замер «кто → маршрут → код ответа» по классам пользователей, включая запрос без входа.

Намеренное изменение прав: `UPDATE_BASELINE=1 npm run test:api` и коммит эталона. Маршрут без замера
прав тест не пропускает.

Проверки перед отправкой в GitHub включаются один раз на машине: `npm run hooks:install`
(`scripts/git-hooks/pre-push`: `lint`, `check:transport`, `test:api`).

## Путь к базе

Маршруты данных ходят в базу только через обёртку транзакции `src/lib/db.js` (маршруты файлов, ИИ и
расценок без шлюза идут через Supabase, со шлюзом — через PostgREST на этом сервере):

```js
const rows = await db.read(who, async (tx) => (await tx.query('select … where id = $1', [id])).rows)
await db.write(who, async (tx) => { await tx.query('update … set … where id = $1', [id]) })
```

- `read` — транзакция только на чтение: читающая операция не может изменить данные.
- `who` — `{ userId, email }` из проверенного сервером входа или `null` для служебной операции. В базу
  уходит собранный здесь контекст, а не исходный токен; он и таймауты действуют до конца транзакции.
- Любая ошибка — откат; подключение с неудавшимся откатом или обрывом в пул не возвращается.
- Запрос — одна параметризованная команда; несколько команд в строке база не примет.
- Одно действие пользователя — одна операция — одна транзакция.
- Пул ограничен (`OSP_DB_POOL_MAX`): у учётки базы общий лимит подключений с другими системами.
- К базе не на этой машине — только с проверкой сертификата и имени сервера: нужен `OSP_DB_CA_FILE`,
  без него служба не запускается. Строка `OSP_DB_URL` проверку не ослабляет: из параметров допустим только
  `sslmode=verify-full`, остальное — отказ при запуске.

В коде сервера нет команд изменения структуры и прав, драйвер базы подключён только в обёртке — это
проверяет `tests/osp-api/no-ddl.test.mjs`. Гарантии обёртки на настоящем PostgreSQL — `tests/osp-api/db.test.mjs`,
проверка сертификата — `tests/osp-api/db-tls.test.mjs`.

## Шлюз данных `/api/db`

Портал читает и пишет базу Яндекса через `/api/db/<таблица>` и `/api/db/rpc/<функция>` — теми же запросами,
что слал в Supabase: `src/api/db.js` отдаёт страницам тот же построитель (`@supabase/postgrest-js`), флаг
`ospDb` выбирает путь. За шлюзом — PostgREST на этом же сервере (`deploy/postgrest`, только `127.0.0.1`).

| Что | Где решается |
|---|---|
| Кто это | шлюз: токен входа Supabase (как у остальных маршрутов); без токена — аноним |
| Какие таблицы, действия, функции и связи в `select` можно вообще | шлюз: `src/data/allow.json` — выдача прав прода как есть (`node scripts/build-db-allow.mjs`) |
| Какие строки видны и изменяемы | база: правила по строкам действуют и на единственную учётку (`migration/target/sql/load-single-owner.sql`) |

- В PostgREST уходит свой токен на 60 секунд: `role` — учётка базы, `osp_role` — кто пользователь
  (`anon` / `authenticated` / `service_role`), `sub`, `email`. Токен браузера дальше шлюза не идёт. PostgREST
  без такого токена запрос не примет, а база откажет запросу без `osp_role` (`osp_private.pre_request`).
- Запрос и ответ передаются как есть: тело — байт в байт, диапазоны, коды и ошибки PostgREST. Отказы самого
  шлюза имеют тот же вид (`{ code, message, details, hint }`): `42501` — не разрешено, `PGRST205` / `PGRST202` —
  такой таблицы или функции для шлюза нет.
- **Барьер записи:** есть файл `OSP_DB_READONLY_FILE` — сервер только читает: запись и вызовы функций через
  шлюз, а также загрузка, подтверждение и удаление файлов (`/api/fn/s3-presign`) — 503 `OSP_READONLY`;
  чтение и скачивание работают (`src/lib/writeBarrier.js`). Включить: `touch /var/lib/osp-api/db-readonly`,
  выключить: `rm`.
- **Учётки входа** остаются в Supabase Auth. `admin_delete_user` и `admin_confirm_user_email` сначала меняют
  учётку там (служебным ключом, только если база подтвердила, что вызывает администратор), затем строки в
  базе. Учётка не названа (нет `target_user_id`, тело не JSON) — 400 `OSP_AUTH_TARGET`, функция базы не
  вызывается. Список пользователей для администратора читает копию `auth.users` в базе; копия обновляется
  из Supabase Auth перед показом (`src/lib/authUsers.js`).
- **Репетиция переноса.** Сервер сам читает, какая копия лежит в базе (`osp_meta.load_log`, отметку ставит
  `migration/target/load.sh --status rehearsal | final`; `src/lib/loadStatus.js`). У репетиционной копии
  хранилище файлов и вход — те же, что у рабочего портала, поэтому, пока копия не `final`:
  - удаление документа убирает строку, а объект из хранилища — только если документ создан уже в
    репетиции; объект, пришедший с рабочими данными, остаётся (`{ ok, object_deleted: false, rehearsal: true }`);
  - `admin_delete_user` и `admin_confirm_user_email` — 409 `OSP_REHEARSAL`, до обращения ко входу и к базе.

  Отметка не читается (нет подключения, нет таблицы, загрузка не завершена) — считается репетицией.
  `/api/ready` показывает режим: `"data": "rehearsal" | "final" | "unknown"`.
- **Реестр расценок** пересчитывается раз в 10 минут самой службой (`OSP_REGISTRY_REFRESH=1`) — в Supabase
  это делало расписание pg_cron.
- Маршруты файлов, ИИ и расценок при включённом шлюзе читают данные через тот же PostgREST.
- **Принятые отступления** (`docs/API_RULES.md`): браузер называет таблицы, у шлюза нет схемы тела, права по
  строкам — в базе. Так же устроен портал в Supabase сегодня; перевод разделов на отдельные операции — после.

Тесты: `tests/osp-api/db-gateway.test.mjs`, `tests/osp-api/load-status.test.mjs`,
`tests/osp-api/client-db.test.mjs`; вся цепочка с настоящим PostgREST на копии прода —
`tests/db/single-owner.test.mjs`. Порядок переноса — `migration/CUTOVER.md`.

## Загрузка договорных расценок из Larix.CPM

Не маршрут, а работа службы: вкладка «Договорные расценки (Larix)» реестра расценок читает представление
`larix_rates_registry` над закрытой таблицей `osp_private.larix_rates` (миграции `20261018`, `20261021`), служба раз
в день наполняет её из Larix.CPM (метод «ВОР по договорам», `GET /api/contract/data/project_contract_boq` после
входа `POST /api/login`).

- **Когда.** Такт раз в 5 минут (первый — через минуту после запуска) спрашивает базу `larix_sync_begin`:
  пора ли. База отвечает «да» после 05:00 по Москве, если сегодня ещё не было удачной (или отложенной)
  загрузки, прошлая попытка была больше 30 минут назад и попыток за день меньше 6. Одна загрузка
  одновременно — уникальный индекс в базе (и между копиями службы, и между серверами); зависшая дольше
  30 минут снимается. Барьер записи — такт пропускается.
- **Память.** Ответ — десятки МБ (16.10 — 65 МБ), а загрузка идёт внутри службы с потолком 384 МБ. Поэтому он
  разбирается потоком (`createJsonArrayParser`): каждая позиция сразу становится короткой строкой для базы,
  исходный объект не хранится. Замер (`tests/deploy/larix-memory.test.mjs`): 100 МБ ответа — пик ~215 МБ
  процесса; разбор целиком в тех же потолках убит по памяти. Предел всего ответа `LARIX_MAX_BYTES` (256 МБ)
  защищает от бесконечного ответа, одной позиции — 1 МБ.
- **Как.** Один запрос в Larix вне транзакций базы, проверка каждой позиции (`normalizeBoqRow`: числа
  конечные, id целые, дата ISO, длины строк ограничены; больше 5 % отброшенных — сбой `invalid`), порции по
  1000 (`larix_sync_add_rows`, повтор порции безопасен), замена одной транзакцией (`larix_sync_finish`):
  строка — позиция с ценой материалов и ценой работ, одинаковые строки ВОР (договор, позиция и единица без
  учёта регистра и пробелов, цены) схлопываются в одну (`repeats`), дата договора — по Москве, наш договор — по
  ссылке «Путь к Larix.CPM» (`contracts.document_link`, только однозначное совпадение).
- **Защита данных.** Пустой ответ при непустых данных и падение ниже 30 % прежнего числа позиций — статус
  `held`, прежние расценки остаются, на вкладке предупреждение; принять — `larix sync --force`. Сбой Larix
  или базы — `failed` с причиной из набора (`login | http | timeout | too_large | invalid | db | stale`),
  прежние расценки остаются, повтор — через 30 минут.
- **Секреты.** Логин и пароль Larix — только в окружении службы; токен живёт в памяти одного прогона. Ни
  логин, ни пароль, ни токен не попадают в журнал службы, в журнал загрузок и в тексты ошибок
  (`redact`). Только `https://cpm.su10.larix.ru` (другой адрес — служба не запускается), перенаправления
  не выполняются (тело входа с паролем не уйдёт по чужому адресу), пределы времени и размера ответа.
- **Куда** (`LARIX_SYNC_TARGETS`): `db` — своя база (служебная операция, отметка `osp:internal`);
  `supabase` — база прежнего портала через служебный ключ, только четыре функции `larix_sync_*`. Пока за
  шлюзом репетиция, запись в Supabase — сознательное исключение из правила «не менять общее с рабочим
  порталом»: расценки Larix — не данные людей, их источник — Larix. После переноса — только `db`.
- **Ручной запуск** — `node src/larix-cli.js probe | sync [--force] [--target db|supabase]`, на сервере corp
  — `bash /opt/portals/osp/deploy.sh larix …` (`deploy/docker/README.md`).

Настройки — `LARIX_*` в `osp-api.env.example`; `/api/health` показывает только `larix: true/false`, в
`/api/ready` Larix не входит. Тесты: `tests/osp-api/larix-client.test.mjs` (поддельный Larix),
`tests/osp-api/larix-sync.test.mjs` (настоящий PostgreSQL, обе базы-цели, служба целиком),
`tests/deploy/larix-memory.test.mjs` (память в контейнере с потолками службы, Docker).

## Кто вошёл

По умолчанию — как раньше: на каждый запрос служба спрашивает Supabase «чей это токен» и читает оттуда
строку ролей. Два ключа окружения переводят оба шага на сервер; включаются по отдельности, в любом порядке:

| Ключ | Что меняется | Проверка в `/api/ready` |
|---|---|---|
| `SUPABASE_JWT_SECRET` | токен проверяется здесь (`src/lib/token.js`): подпись, срок, издатель, назначение, роль | `token`: секрет сверяется с публичным ключом сайта — секрет другого проекта даёт отказ готовности |
| `OSP_DB_URL` (+ `OSP_DB_CA_FILE`) | статус учётки (`user_roles`) читается из базы с кэшем на 30 с (`src/lib/userStatus.js`) | `db`: база отвечает |

- Принимается только токен вошедшего пользователя этого проекта, алгоритм — только HS256. Публичный и
  служебный ключи проекта подписаны тем же секретом, но токеном пользователя не являются — 401.
- Токен живёт до часа и о блокировке не знает. Блокировка, отзыв одобрения и удаление учётки действуют
  через статус из базы — не позже чем через 30 с (предел кэша — минута). Выход пользователя до истечения
  токена сервер не видит.
- База не ответила — 503 «повторите», а не 403: сбой не выдаётся за отсутствие прав.
- Секрет подписи по силе равен служебному ключу (им выпускается токен любого пользователя): только в
  файле окружения службы.
- **Вернуть прежний путь:** убрать ключ из файла окружения и перезапустить службу.

Тесты: `tests/osp-api/token.test.mjs`, `tests/osp-api/identity.test.mjs`.

## Свой вход (tender.su10.ru)

Вход нового портала без Supabase Auth: учётки — в `auth.users` базы Яндекса (те же идентификаторы), пароли —
в закрытой схеме `osp_auth`, сессии — в `osp_session` (миграция `migration/yandex/20261019_own_auth.sql`).
Пароль проверяет эта служба, сессия — непрозрачный id в cookie. Вход osp.root.sx не меняется: он в Supabase.

**Режим** `AUTH_MODE` — переключается одной строкой окружения и перезапуском API, без сборки
(`scripts/deploy-server.sh auth-mode`):

| Режим | Что принимает | Для чего |
|---|---|---|
| `supabase` (по умолчанию) | только токен Supabase | как раньше |
| `both` | токен Supabase и свою сессию — только пилоту (`OSP_AUTH_PILOT_IDS`) | проверка в одном браузере (`?features=ownLogin`) |
| `own` | только свою сессию; токен Supabase — 401 `OSP_AUTH_MODE` (вкладка перезагружается) | после переключения; Supabase службе не нужен |

Фронт узнаёт режим из `GET /api/auth/config`, только если в `config.json` есть `authServer: true` (на
osp.root.sx его нет — сервер не спрашивается). В режимах `both` и `own` служба не стартует без `OSP_AUTH_KEYS`,
`OSP_PUBLIC_ORIGIN`, `OSP_DB_URL` и шлюза данных; `/api/ready` проверяет `auth` (канарейка ключа, все ключи
строк паролей есть в окружении), `db`, `gateway`.

**Маршруты** (`src/routes/auth.js`): `GET /api/auth/config`, `POST /api/auth/login`, `POST /api/auth/logout`
(открытые), `POST /api/auth/password`, `GET /api/auth/me`, `POST /api/auth/admin/users`,
`POST /api/auth/admin/reset-password` (администратор). Самостоятельной регистрации нет: писем портал не
отправляет, учётки и временные пароли выдаёт администратор (временный показывается один раз, при входе его
обязательно сменить).

**Гарантии** (`tests/osp-api/own-auth.test.mjs`, `own-auth-unit.test.mjs`):

- **Пароли.** Прежние — bcrypt из Supabase, люди входят тем же паролем; после входа отпечаток пересчитывается
  в scrypt (`src/lib/auth/passwords.js`: N=2^15, r=8, p=3, соль 16 байт, `maxmem` 64 МиБ, не больше 4 расчётов
  сразу и 32 в очереди). В базе отпечаток зашифрован ключом сервера (AES-256-GCM, привязка к учётке).
- **Новые пароли** (`src/lib/auth/policy.js`, NIST SP 800-63B-4): NFC, 15–128 кодовых точек, без правил
  состава; целиком — не из списка распространённых (`src/data/common-passwords.txt.gz`) и не почта или ФИО.
- **Перебор.** По почте: после 5 неудач пауза от 1 до 15 минут (в базе, и для несуществующей почты); по адресу
  клиента — 60 попыток за 10 минут. Время ответа одинаково для любой учётки, ответ на неудачу один.
- **Гонка входа и смены пароля.** Сессия создаётся в одной транзакции только при той же версии пароля, что
  была проверена; смена, сброс и перенос пароля повышают версию и отзывают сессии той же транзакцией.
- **Сессия.** `__Host-osp_session` (HttpOnly, Secure, SameSite=Lax), в базе — только sha256 id; без
  активности 14 дней, всего 30. Блокировка и снятие одобрения (в том числе правкой строки `user_roles`)
  отзывают сессии триггером — доступ прекращается не позже 5 с.
- **CSRF.** Меняющий запрос со своей сессией — заголовок `X-OSP-CSRF` (= cookie `__Host-osp_csrf`), `Origin`
  портала и `Sec-Fetch-Site: same-origin`; вход — строгие `Origin`, `Sec-Fetch-Site` и только JSON.
- **Кто это** (`src/lib/principal.js`) — одна проверка для функций, шлюза и `/api/auth/*`; пользователь в ней
  не создаётся. Удаление учётки администратором — надгробие и функция базы одной транзакцией.
- **Отметки.** Пароли читаются только с отметкой `osp:auth` (`tx.mark('auth')`, только в `src/lib/auth/`);
  пропуск служебных функций их не открывает, а `osp:auth` не видит таблиц портала.
- **Адрес клиента.** `OSP_TRUST_PROXY=peer` — `X-Forwarded-For` только от непосредственного соседа (osp-web
  перезаписывает его адресом клиента, который берёт у общего nginx по жетону).
- В журнал и ответы не попадают пароли, отпечатки, id сессии и CSRF.

Перенос учёток и паролей из Supabase — `migration/accounts/README.md`.

## Включение на портале

Фронт вызывает функции через `invokeFunction` (`src/api/functions.js`), у каждой свой флаг. **С данными в
базе Яндекса (`ospDb`) файлы идут через osp-api при любом значении `ospApiFilesV2`**, функция файлов
Supabase не вызывается вовсе (`src/api/serverPath.js`): она работает с базой Supabase и удалила бы из
хранилища файл, на который ссылается другая база. ИИ к данным не привязан и идёт по своему флагу.
- `ospApiAi` — для `ai-assist`;
- `ospApiFilesV2` — файлы. Включать только после Р2a/b (`osp_can`) и миграции `20261011` (колонка `sha256`)
  на проде.
- `ospApiFiles` — флаг сборок до захода Б, с прежним протоколом. **Не включать:** новый сервер прежний
  протокол загрузки не принимает. Надёжнее держать в `config.json` явное `false`.

Включить:
- **один браузер (проверка на проде):** `https://osp.root.sx/?features=ospApiAi`, снять — `?features=-ospApiAi`;
- **все пользователи:** `/var/www/osp/shared/config.json` → `{"features": {"ospApiAi": true}}`.

**Откат:** явное `false` в `config.json` выключает флаг и в пилотных браузерах. Открытые вкладки
перечитывают флаги каждые 2 минуты и при возврате на вкладку — перезагрузка не нужна. Путь выбирается в
начале операции: начатая операция заканчивается тем же путём.

`/api/rates` в работе нет: потребители остаются на функции Supabase до переноса базы. Затем — роль только
на чтение вместо служебного ключа, тонкий прокси и проверка у смежного отдела.
