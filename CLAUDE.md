# CLAUDE.md — ОСП (отдел сопровождения подрядчиков)

## Назначение

React 18.3 + Vite, русскоязычный портал строительных объектов, контрагентов, тендеров, договоров, заявок, смет и расценок. Клиент: `src/`; свой API: `server/osp-api/` (Fastify); данные: Supabase и новый портал с базой Яндекса. Не считать режимы авторизации, права и доступность миграций одинаковыми для двух порталов.

Это **короткая инструкция для каждой сессии**, а не журнал изменений. Подробные решения сохранены в [`docs/claude-reference/00-index.md`](docs/claude-reference/00-index.md): открывай **только нужную тему** после определения задачи. Не импортируй справочники через `@`: это загрузит их в контекст целиком. Прежде чем применять описанное там решение, проверяй актуальный код, миграции и тесты; справочник сохраняет также историю и прежние варианты.

## Коммит, пуш, выкатка — только с согласия всех сессий проекта

**Перед КАЖДЫМ `git commit`, `git push` и выкаткой на сервер**:

1. Главная сессия запускает из папки проекта `~/.claude/bin/project-peers`. Учитывает **только** сессии из его вывода (включая worktree того же проекта). Пустой вывод → опрос не нужен.
2. Находит их одноимённые записи и `[ref]` через `ListAgents`, отправляет `SendMessage` **каждой**: операция, ветка, состав файлов/версия. Не пишет другим сессиям, включая `claude-*`.
3. Дожидается явного согласия **всех**. Отказ или молчание → не выполнять; сообщить пользователю кто и почему. Обойти это можно **только по прямому указанию пользователя**.
4. Согласие только на указанную операцию и указанный состав. Состав изменился → опрос повторить. Субагенты опрос не проводят: его делает главная сессия до вызова исполнителя.

На чужой `SendMessage` с запросом согласования **отвечай сразу**: «да» или «нет: причина» (незавершённая конфликтующая работа, миграция, выкатка). Если запрос не о твоём проекте — «да, не мой проект». Не откладывай ответ до конца задачи.

## Перед изменениями

- Определи затронутые файлы и прочитай их; найди существующий аналог и профильные тесты. Не переноси старые архитектурные/безопасностные примеры из справочника, если они расходятся с действующим кодом.
- Для UI перед правкой вёрстки прочитай `docs/UI_GUIDELINES.md`; у разных страниц есть собственные плотные варианты и стили. Сохраняй русские подписи, доступность на телефоне и права на действия.
- Для схемы БД проверь **фактически применённые миграции** и оба пути: `supabase/migrations/` и `migration/yandex/`; название файла с будущей датой само по себе не значит, что миграция применена. Схемы `supabase/schemas/` — справка, не замена миграциям.
- Для API, файлов, авторизации, прав и деплоя сверяй профильные README, маршруты и тесты. Не расширяй права, список публикации данных или публичные поля «на всякий случай».

## Обязательные ограничения архитектуры

- **Доступ фронтенда к серверу — только через `src/api/`** (`db`, `auth`, файлы, функции, realtime). В страницах и сервисах не создавай Supabase-клиент и не импортируй `@supabase/*`. Проверка: `npm run check:transport`.
- **Предел PostgREST — 1000 строк на запрос**, даже с `.limit(5000)`. Для потенциально больших выборок используй `fetchAllRows` / `fetchAllRowsParallel` из `src/utils/fetchAllRows.js`, устойчивый порядок (в конце `id`), для длинных `.in()` — `chunkList`.
- **Права — на сервере и в БД**, не только по скрытым кнопкам, `RoleContext` или `localStorage`. Роли и охват объектов определяй по актуальным правилам шлюза и схемы. Новый маршрут osp-api: `config.access`, проверка входных данных через zod; открытые маршруты — только `src/open-routes.js` сервера.
- Новая таблица/RPC в шлюзе требует проверки `server/osp-api/src/data/allow.json` и `db-sections.json`; доступ подрядчика отдельно ограничен `allow-contractor.json` / `allow-self-contractor.json`. Расширение списков — **решение о доступе**, не механическое действие.
- Файлы: используй действующий путь `src/api/` и `src/services/s3.js`; не раскрывай ключи хранилища, не подменяй проверку прав. Для скачивания — `downloadS3File` из `src/components/FileDownload.jsx`, **не** `window.open` / новую вкладку.
- Не записывай секреты, реальные пароли, приватные выгрузки, ФИО/телефоны из базы в git и примеры. `.env*`, слепки БД и документы реальных подрядчиков — вне репозитория.
- Миграции для Яндекса: по `migration/yandex/README.md`; проверка/откат — `migration/backup/checks/` и `migration/rollback/`. Публикация после миграций обычно `migrate` → `both` (см. `migration/CUTOVER.md` и `deploy/docker/README.md`). **Не запускать выкатку без запроса и согласования сессий.**

## Команды

```bash
npm install                 # установка
npm run dev                 # локально :5173
npm run build               # сборка dist/
npm run lint                # ESLint, --max-warnings 0
npm run check:transport     # граница доступа к серверу
npm run test:tender         # UI / тендеры (Chromium; часть тестов — БД/Docker)
npm run test:supply         # расценки / SQL / PostgreSQL
npm run test:contracts      # договоры, без обязательной БД
npm run test:psdc           # ПСДЦ, PostgreSQL + Chromium
npm run test:api            # osp-api; npm ci --prefix server/osp-api
npm run test:db             # схема, права и шлюз на копии прода
npm run test:release        # проверка релизной сборки
npm run test:deploy         # стенд выкладки, Docker
npm run test:backup         # восстановление и миграции
npm run hooks:install       # локальные pre-push проверки (однократно)
```

Тесты основаны на `node --test`: сначала запускай **затронутые точечные тесты** (`node --test tests/<раздел>/<имя>.test.mjs`), затем подходящие наборы, `lint`, `check:transport`, при UI — сборку. Для БД нужен PostgreSQL 17+ (`PG_BIN` либо Docker, `PG_TEST_MODE`), для UI — Chromium/Playwright (`PSDC_BROWSER`). Без этих зависимостей некоторые тесты **skip**, а не успешная проверка соответствующего поведения. Не называй пропуск успешным прохождением.
