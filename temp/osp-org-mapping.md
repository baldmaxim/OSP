# Задача: контрагент подрядчика — по организации его учётки СУ-10

## Зачем

Сотрудник подрядчика на tender.su10.ru должен видеть всю историю своей организации: тендеры, заявки, договоры. В ОСП
это уже так, если у его `user_roles` верный `counterparty_id` — `current_counterparty_id()`, `is_my_tender`,
`is_my_contract`, `bid_contractor_tenders()` строятся от него. Не хватает однозначного ответа: какой контрагент ОСП у
вошедшей учётки СУ-10.

Ответ даёт auth. Каждая учётка состоит в одной организации реестра контура, у организации постоянный id
`su10_org_id`, и он приходит в токене. ОСП держит у себя связь «`su10_org_id` → `counterparties.id`» (1:1) и по ней
ставит `counterparty_id` сам. Выбирать контрагента руками при разборе заявки больше не нужно.

## Что даёт auth

### Реестр организаций

Подгруппы `/org/орг: <название>` в realm `su10`. Сейчас их 123: 2 свои (СУ-10, СМ) и 121 подрядчик. У каждого
подрядчика пока одна учётка — его представитель из ФОТ.

| Атрибут группы | Смысл |
|---|---|
| `su10_org_id` | постоянный id организации, ключ связи. Не меняется. **Не равен id группы** у организаций, добавленных на `/manage`: брать только атрибут |
| `su10_org_kind` | `own` — своя организация (сотрудники СУ-10), `contractor` — подрядчик |
| `org_name` | точное название (если задано; иначе — имя группы без «орг: », «∕» → «/») |
| `inn` | ИНН, если его ввели на `/manage`. У организаций из ФОТ его нет |
| `fot_org_ids` | служебное (узлы ФОТ), ОСП не нужно |

Новые организации (подрядчики не из ФОТ) заводит администратор доступа на `auth.su10.ru/manage` → «Организации»,
вместе с учётками их сотрудников. Организацию учётки меняют там же («Организация…»).

### Claim `su10_org_id`

В access token и id_token клиента `osp` — **массив**. Норма — ровно одно значение. Пусто — у учётки нет организации;
два и больше — ошибка данных в auth. Значение — `su10_org_id` её организации.

### Список организаций — Admin API, клиент `osp-access-sync`

Тот же служебный клиент и токен, что для сверки `osp-access` (`osp-oidc.md`, раздел 3.3), прав `view-users` хватает:
1. `GET /admin/realms/su10/groups?search=org&exact=true&briefRepresentation=true` — взять элемент с `name === 'org'`
   и `path === '/org'`. Нет такого — ошибка «реестр не найден».
2. `GET /admin/realms/su10/groups/{id}/children?briefRepresentation=false&first=<N>&max=100` — страницы, пока ответ
   не короче `max`.
3. Из каждой подгруппы с атрибутом `su10_org_id` взять `su10_org_id`, `su10_org_kind`, название, `inn`. Подгруппы без
   `su10_org_id` (служебная «(организация не определена)») пропустить.

Организация конкретного человека без входа (для заявки, заведённой сверкой) —
`GET /admin/realms/su10/users/{sub}/groups?briefRepresentation=false`: подгруппа `/org/…` с атрибутами.

Базу Keycloak не читать: интеграция — только через Admin API.

### Файл для разового сопоставления

`su10-orgs-<дата>.csv`: UTF-8 с BOM, разделитель — запятая. Передаётся владельцем вручную, **не через git**: в
названиях есть ИП — это персональные данные.

| Колонка | Что |
|---|---|
| `su10_org_id`, `kind`, `name`, `inn` | как в реестре |
| `fot_org_ids` | служебное |
| `users` | сколько включённых учёток в организации |
| `email_domains` | `домен:число` через `\|` — почтовые домены сотрудников, без публичных (gmail, mail.ru…) |
| `inn_hint`, `inn_hint_names`, `inn_hint_source` | ИНН и название контрагента BillHub, к которому привязан сотрудник этой организации в BillHub (`billhub`). Есть у 29 организаций; у одной ИНН расходятся |

`su10_org_id` в файле — итоговые: связи, построенные по нему, остаются верными и после выкатки auth. Значение,
которое начинается с `=`, `+`, `-`, `@` или табуляции, выгрузка предваряет апострофом (защита от формул в Excel):
при сопоставлении его отбросить.

## Что сделать

### 1. Схема

Новая миграция в `migration/yandex/` по правилам `migration/yandex/README.md`, вместе с `.check.sql`. Таблицы — в
`osp_auth`, как связи учёток.

- **`osp_auth.org_links`:**
  - колонки: `issuer text`, `su10_org_id uuid`, `counterparty_id uuid → counterparties(id) ON DELETE RESTRICT`,
    `source` (`bulk|admin`), `match` (`inn|name|domain|admin`), `linked_by`, `linked_at`;
  - UNIQUE `(issuer, su10_org_id)` и `(issuer, counterparty_id)` — строго 1:1.
- **`osp_auth.su10_orgs`** — кэш реестра:
  - колонки: `su10_org_id uuid PK`, `kind`, `name`, `inn`, `seen_at`;
  - из реестра не удалять: организация, пропавшая из ответа, — только старый `seen_at`.
- **События `osp_auth.events`:** `org.link`, `org.unlink`, `org.change` (у пользователя сменился контрагент),
  `org.denied` (подрядчик без определимой организации).

### 2. Разовое сопоставление — миграцией по файлу

1. Берутся только строки `kind=contractor`. Кандидаты — `counterparties` с `deleted_at IS NULL`.
2. **Признаки по убыванию силы:**
   - **ИНН:** `inn` или `inn_hint` равен ИНН контрагента. ИНН в реестре ОСП записан грязно, поэтому сравнивать
     после нормализации, как в `server/osp-api/src/lib/auth/signup.js`: только цифры, ИНН вместе с КПП через «/»,
     два ИНН в ячейке, потерянный ведущий ноль;
   - **название:** совпадает после нормализации — нижний регистр, ё→е, без ОПФ (ООО, АО, ПАО, ЗАО, ОАО, ИП, НКО), без
     кавычек «»"' и знаков, пробелы схлопнуты. «2Ф ООО» = «ООО «2Ф»»;
   - **почтовый домен:** домен из `email_domains` есть у `counterparty_contacts.email` контрагента. Только подтверждает
     ИНН или название; один не решает.
3. **Дубли контрагентов** по признаку — выбрать основную запись: не из чёрного списка, затем с договорами или
   участием в тендерах, затем по `counterparty_relations`. Не выбирается однозначно — пара в миграцию не идёт.
4. **1:1:** контрагент, на которого претендуют две организации, не связывается ни с одной — в отчёт.
5. **В миграцию идут только пары id:** `VALUES (su10_org_id, counterparty_id, match)`,
   `issuer = 'https://auth.su10.ru/realms/su10'`, `source = 'bulk'`, `ON CONFLICT DO NOTHING`. Названий, ИНН и почт
   в миграции нет.
6. **`.check.sql`:** все `counterparty_id` существуют, пары уникальны.
7. **Отчёт** — несопоставленные и спорные организации с кандидатами. Он вне git, для администратора ОСП; их связывают
   вручную (раздел 5).

Нечёткие совпадения названий — только в отчёт, не в миграцию.

### 3. Кэш реестра

В цикле сверки `osp-access` (`osp-oidc.md`, раздел 3.3) после чтения участников:
- прочитать реестр (раздел «Список организаций») и обновить `osp_auth.su10_orgs`;
- **дополнительно** — при открытии вкладки «Организации СУ-10» и когда во входе пришёл `su10_org_id`, которого нет в
  кэше. Не чаще раза в 15 с.

Ошибка Admin API — сверка организаций пропускается, прежний кэш остаётся.

### 4. Организация пользователя — где и как применяется

**Итог по учётке** (функция `resolveOrg(claim)`):

| claim `su10_org_id` | реестр | связь | итог |
|---|---|---|---|
| пусто | — | — | `none` |
| два и больше | — | — | `ambiguous` |
| одно значение | `own` | — | `own` |
| одно значение | `contractor` | есть | `counterparty(X)` |
| одно значение | `contractor` | нет | `unmapped` |
| одно значение | нет в реестре и после перечитывания | — | `unmapped` |

**Где применяется:**
- в callback — после привязки учётки (`osp-oidc.md`, 3.2);
- при перепроверке — по новому access token (2.4);
- в «Создать пользователя» по заявке (3.4) — для заявки от сверки организацию берут через `users/{sub}/groups`.

**Подрядчик в ОСП** — роль `contractor` или `counterparty_id IS NOT NULL`:

| Итог | Что делает ОСП |
|---|---|
| `counterparty(X)`, у пользователя X | ничего |
| `counterparty(X)`, у пользователя другой | `UPDATE user_roles SET counterparty_id = X`, отозвать прочие сессии, событие `org.change {from, to}`. В callback новая сессия выпускается уже с X |
| `none`, `ambiguous`, `unmapped`, `own` | 403 `OSP_ORG_UNMAPPED` «Организация не сопоставлена с контрагентом ОСП — обратитесь к администратору ОСП», сессию не создавать или отозвать, событие `org.denied`. `counterparty_id` не трогать |

**Сотрудник СУ-10 в ОСП** — `counterparty_id IS NULL` и роль не `contractor`. Организация на его доступ не влияет.
Итог `counterparty(X)` у сотрудника — только событие `org.denied` и пометка в «Организации СУ-10»: превращать
сотрудника в подрядчика решает администратор ОСП.

**Никогда автоматически не ставить `counterparty_id = NULL`**: в ОСП NULL означает «сотрудник СУ-10», он открыл бы
данные отдела.

**«Создать пользователя» по заявке:**
- роль `contractor` → `counterparty_id` из `counterparty(X)` и не правится. Иной итог → 409 `org_unmapped` «Сначала
  сопоставьте организацию «…» с контрагентом» с кнопкой «Сопоставить…»;
- другая роль → `counterparty_id = NULL`; если итог — организация-подрядчик, показать предупреждение.

### 5. Администрирование (`src/pages/AdminPage.jsx`)

Все действия — admin-эндпоинты (`access.user({ require: 'admin' })`, CSRF, zod, событие), не шлюз данных.

- **Вкладка «Организации СУ-10»:**
  - строки — кэш реестра. Фильтр «Без связи» по умолчанию показывает организации-подрядчики, у которых есть
    участники `osp-access` или заявки;
  - колонки: название, ИНН (СУ-10), вид, учёток с доступом к ОСП, связанный контрагент (номер `counterparty_number`
    и название);
  - «Сопоставить…» — поиск контрагента с подсказками по ИНН, названию и домену;
  - «Создать контрагента» — название и ИНН из реестра, одной транзакцией вместе со связью;
  - «Отвязать» — с предупреждением: подрядчики этой организации получат `OSP_ORG_UNMAPPED`, их число показать;
  - ошибку Admin API показать ненавязчиво: вкладка работает по кэшу.
- **Карточка контрагента** — блок «Организация СУ-10»: связанная организация или «Связать…» с выбором из кэша
  реестра. Это путь для нового контрагента, заведённого в ОСП: его организацию находят по названию и ИНН из списка
  auth.
- **Заявка на доступ** — показать организацию СУ-10 человека и её связь.

### 6. Тесты

Keycloak мокать, как в `osp-oidc.md`, раздел 6.

| Область | Сценарии |
|---|---|
| Сопоставление | ИНН с КПП через «/» и без ведущего нуля; название с ОПФ и кавычками; дубль ИНН → основная запись; контрагент на две организации → не связан; в миграции только id |
| Итог | пусто, два значения, `own`, связь есть, связи нет, нет в кэше → перечитывание |
| Подрядчик | свой контрагент → без изменений; другой → `UPDATE`, сессии отозваны, `org.change`; `unmapped`/`own`/`none` → 403, `counterparty_id` не изменился и не NULL |
| Сотрудник | организация-подрядчик в claim → доступ не меняется, событие |
| «Создать пользователя» | подрядчик со связью → контрагент из связи; без связи → 409; сотрудник → NULL |
| Админка | сопоставить, создать контрагента, отвязать — события; не-admin → 403 |
| Кэш | страницы по 100; ошибка Admin API — кэш прежний; троттлинг 15 с |

### 7. Выкатка

1. **Код и схема** вместе с задачей `osp-oidc.md`. Пока `AUTH_MODE=own`, организация не применяется.
2. **Разовое сопоставление** — миграция по файлу; отчёт — администратору ОСП.
3. **auth** выполняет `deploy-auth --migrate`: claim и атрибуты реестра появляются в проде. Порядок с пунктами 1–2
   не важен.
4. **Переключение** на keycloak (`osp-oidc.md`, раздел 10). В окне переключения разобрать отчёт: связать оставшиеся
   организации.

**Смоук:**
1. Сотрудник подрядчика A входит — видит тендеры и договоры A.
2. На `/manage` его переводят в организацию B (связанную) — при следующей перепроверке (до 5 минут работы) сессия
   отозвана; после входа видна история B, в журнале `org.change`.
3. Организация без связи — вход даёт `OSP_ORG_UNMAPPED`, она появилась в «Организации СУ-10» → «Сопоставить…» → вход
   работает.
4. Новый контрагент в ОСП → «Связать…» с организацией из списка СУ-10 → её сотрудники входят с этим контрагентом.

Сообщить команде auth: число связанных организаций после миграции и список тех, что остались без пары.

### 8. Чего не делать

- Не связывать по ИНН или названию на лету при входе: связь ставит только миграция или администратор.
- Не ставить `counterparty_id = NULL` автоматически.
- Не менять реестр в Keycloak и не просить прав на запись: организации заводят на `auth.su10.ru/manage`.
- Не читать базу Keycloak.
- Не класть файл выгрузки и отчёт в git.
