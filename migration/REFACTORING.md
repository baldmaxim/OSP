## Контекст

**Почему сначала рефакторинг.** Общий план переезда (ред. 7, утверждён 2026-10-06) ведёт портал с

переезжать на новый домен. Сейчас портал к переезду не готов:
- **Прямые обращения к Supabase.** 488 обращений к таблицам из 52 файлов, 26 RPC; вход, данные,

- **Около 110 цепочек запросов без транзакции**, 8 из них при сбое теряют данные (смета ВОР, КП,
  смета объекта, стороны договора…). Повтор создания плодит дубли.

  - Подрядчики видят цены всех подрядчиков.
- **Файлы рассогласуются с базой:** старый файл удаляется до сохранения, при удалении сущностей
  остаются сироты.
- **Нет страховки релизов:** нет принудительного обновления, восстановления после ошибки чанка,
  отката одной командой и телеметрии версий.

## Гарантии: данные не теряются, пользователи работают

Рефакторинг идёт на живом портале, без окон обслуживания.

### Данные
1. **Миграции рефакторинга ничего не удаляют.**
   - Нет `DROP TABLE`/`DROP COLUMN`, нет `DELETE`/`UPDATE` бизнес-данных.
   - Данные меняются только так: заполнение новых таблиц и колонок (`superadmins`, `updated_at`,
     `user_settings`) и переписывание адресов обложек.
   - Адреса обложек переписываются только после проверенной копии файлов; прежнее значение
     сохраняется в журнале для возврата.
   - `test:db` проверяет миграции рефакторинга на запрещённые операторы.
2. **Перед каждой миграцией — своя резервная копия, проверенная восстановлением.**
   - Проект на бесплатном тарифе: Supabase резервных копий **не делает** (на панели «Last backup: No
     backups»). Поэтому копию снимаем сами.
   - Копия: `pg_dump` схемы `public` (схема и данные) с удалённой машины в `migration/dumps/`.
     Права `600`, каталог в `.gitignore`, копии удаляются через 30 дней.
   - Скрипт проверки поднимает её во временном PostgreSQL в Docker и сверяет число строк каждой
     таблицы с продом. Копия, которую не проверили восстановлением, копией не считается.
   - Если организация перейдёт на тариф Pro, добавятся ежедневные копии Supabase. Своя копия перед
     миграцией всё равно остаётся.
3. **Новые операции надёжнее старых.** Атомарные RPC заменяют «удалить, потом вставить» — именно там
   сейчас теряются данные. Каждую RPC тест проверяет так:
   - ошибка посередине — данные прежние;
   - повтор — без дубля;
   - число строк до и после сверяется.
4. **Новый код физически не удаляет файлы**, только ставит отметку `deleted_at`. Физическое удаление
   — после переезда, задачей с журналом, через 30 дней.
5. **Настройки и введённые тексты** (шаблон письма и т. п.) копируются из `localStorage` в базу.
   Локальная копия не стирается.
6. **Переключатель в `config.json`** две недели после релиза возвращает старый путь операции без
   пересборки — если новая ведёт себя неверно.

### Работа пользователей
1. **Без перерывов.** Деплой атомарный (каталоги-релизы), старые вкладки догружают свои файлы. При
   ошибке загрузки чанка — одна автоматическая перезагрузка.
2. **Миграции онлайн.** Без долгих блокировок: индексы `CONCURRENTLY`, колонки без перезаписи
   таблицы, политики и функции меняются мгновенно. Применяются в часы низкой нагрузки.
3. **Старое убирается, только когда им никто не пользуется.**
   - Поднимаем `compat` → у старых вкладок окно «обновите».
   - Старую политику или путь удаляем, **только когда** телеметрия и лог nginx показывают ноль
     старых вкладок. До этого момента ввод в старой вкладке продолжает сохраняться.
4. **Сервер разрешает ровно то, что разрешает интерфейс.** Карта «таблица → разделы» берётся из
   кода, матрица прав — по всем ролям. Ручная проверка — под настоящими учётками.
5. **Поломку видно сразу.**
   - Телеметрия ошибок: фронт отправляет коды отказов (`42501`, `401/403`, `PGRST…`) с разделом и
     версией сборки в таблицу `client_errors` (Р1). Без персональных данных и без тел запросов.
   - После каждой выкладки первые часы смотрим её и логи API Supabase. Всплеск отказов — откат или
     исправление в тот же день.
6. **Откат:**
   - фронт — `rollback.sh` за минуту;
   - права — SQL возврата по группе таблиц (аварийно, с вашего разрешения);
   - новые операции — переключатель в конфиге.

### Дальше: перенос на Яндекс и новый домен (этапы 3–5 общего плана, ред. 8.1)

**Что рефакторинг даёт им:**
- **Адаптеры.** Переход на свой API — без правки страниц; путь данных можно вернуть на Supabase
  (откат R-A).
- **Закрытые права.** Дыры не переезжают в новый контур.
- **Атомарные RPC и id с клиента.** Очередь правок окна A применяется без дублей.
- **Настройки в базе.** После смены домена ничего не пропадает.

**Как сами окна сохраняют данные** (механизмы плана, ред. 8.1):
- **Окно A, перенос базы.**
  - Запись в Supabase останавливается барьером.
  - Правки пользователей в это время принимаются в очередь: «Принято» значит «сохранится».
  - Дамп снимается после слива всех транзакций.
  - **Полная сверка всех таблиц — до открытия записи** в новой базе.
  - До этого момента возможен откат R-A.
  - Supabase 30 дней хранится без изменений.
- **После окна A.** Журнал изменений и ночные дампы позволяют восстановиться без потерь.
- **Окно B, вход через Keycloak и новый домен.**
  - Учётки сопоставляет команда auth. Кого ещё не сопоставили, тот видит «ожидает сопоставления», а
    не пустую учётку — доступ к прежним данным не теряется.
  - Правки в окне идут в очередь.
  - Старый домен перенаправляет на новый (закладки, ссылки в письмах).
  - Откат входа возможен 7 дней.
- Окна A и B утверждаются отдельно — после стенда и репетиций.

### Данные — прежде всего

**Правила на всё, что касается прода:**
1. **Пока нет проверенной копии, в прод ничего не пишется.** До этого — только чтение.
2. **Каждая миграция сначала идёт на копии прода.** Копию поднимает `verify.sh` во временной базе.
   Проверяем:
   - миграция проходит;
   - повторный запуск безопасен;
   - **число строк во всех таблицах не изменилось**;
   - результат тот, что нужен.

   Только после этого — на проде.
3. **После миграции на проде** снова считаем строки (`counts.sql`) и сравниваем с подсчётом до.
   Любое необъяснённое расхождение — остановка и разбор, исправление по копии.
4. **Пароль базы не сбрасываем**, пока не известно, что им больше никто не пользуется. Сначала
   пробуем узнать действующий.
5. **Копия содержит данные пользователей:**
   - лежит только на удалённой машине: права `600`, вне git;
   - в чат не выводится ничего, кроме счётчиков;
   - удаляется через 30 дней.

**Что из ближайших шагов касается данных:**

| Шаг | Что делает с базой прода | Риск для данных |
|---|---|---|
| `backup.sh` (копия) | читает: `pg_dump` работает в одной транзакции только на чтение | нет |
| `verify.sh` (проверка копии) | прод не трогает — работает с копией в Docker | нет |
| Слепок схемы | читает только описание объектов, без данных | нет |

## Принципы

1. **Для пользователей ничего не меняется**, кроме перечисленных исправлений. Бизнес-логика и
   дизайн не трогаются. Если сервер начинает запрещать то, что интерфейс разрешал, — это ошибка
   плана, а не «ужесточение».
2. **Маленькие релизы**, каждый выкладывается и откатывается отдельно. Механические правки (импорты)
   не смешиваются со смысловыми.
3. **«Расширить → переключить → сузить».**
   - Сначала добавляем новое (функцию, колонку, хелпер под новым именем).
   - Выкладываем фронт, который его использует, и поднимаем **уровень совместимости**: старые вкладки
     обязаны обновиться.
   - Только после этого убираем старое: политику, грант, клиентскую запись журнала.
   - Миграция не ломает сборку фронта, которая ещё открыта у пользователей.
4. **У каждого релиза есть:**
   - автоматические проверки до выкладки;
   - порядок выкладки (миграция ↔ фронт);
   - чек-лист после;
   - откат и **граница отката** — после какой миграции откат фронта уже небезопасен.
5. **Права ужесточаются только с тестом по ролям.** Тест сначала фиксирует текущее поведение, затем
   релиз меняет ожидания только для дыр.
6. Код, миграции и тесты готовлю я. Коммиты, применение миграций и деплой — вы. В инструкциях указан
   пользователь (`danila`, `root`).

## Как проверяем (без локального Supabase)

- **SQL и права — `npm run test:db` (новый).**
  - Временный PostgreSQL в Docker на удалённой машине, той же версии, что прод (из q1). Тест сам
    поднимает и удаляет контейнер.
  - **Слепок схемы прода** (Р0): схемы `public` и `auth`, только DDL, с владельцами и грантами.
  - **Заглушки:**
    - все роли, названные в слепке: `supabase_admin` — суперпользователь; `postgres` —
      `NOSUPERUSER BYPASSRLS`, как на проде; `service_role` — `BYPASSRLS`; `anon`, `authenticated`,
      `authenticator`, `dashboard_user` и т. д.;
    - расширения в тех схемах, которые показал q1;
    - схема `storage` и публикация `supabase_realtime`.
  - `auth.uid()`, `auth.role()`, `auth.jwt()` берутся из слепка как есть и читают
    `request.jwt.claims`/`request.jwt.claim.sub`. Тест ставит оба.
  - Запросы идут под `SET ROLE authenticated` с пользователем в claims и явным
    `statement_timeout = 30s`, как у роли на проде.
  - **Матрица прав:** роль × таблица × операция.
    - Роли: админ; суперадмин; сотрудник с правом и без права на раздел; пользователь только с

### Р4. Атомарные RPC и создание без дублей
RPC — SECURITY INVOKER, поэтому RLS из Р2 действует. В начале каждой — явная проверка права
(`42501`, понятный текст). Число затронутых строк сверяется через `GET DIAGNOSTICS`: иначе запрет RLS
тихо превратил бы «заменить» в «добавить».

1. **Потеря данных — первыми.**

   | Функция | Заменяет |
   |---|---|
   | `replace_tender_estimate(tender_id, estimate_name, rows)` | ВОР, [TenderDetailPage.jsx:1037](../src/pages/TenderDetailPage.jsx#L1037) |
   | `replace_counterparty_proposals(tender_id, counterparty_id, rows, status)` | КП сотрудника и кабинета; для подрядчика — одна проверка `is_my_tender` в начале, а не на каждой строке (замер на 25 000 строк) |
   | `replace_object_estimate(object_id, rows)` | импорт сметы объекта |
   | `save_warranty_retention(retention, payments)` | удержания и платежи |
   | `save_contract(contract, counterparties, seed_appendices)` | договор и стороны |
   | `set_task_participants(task_id, kind, user_ids)` | соисполнители и наблюдатели |
   | `confirm_tender_winner(tender_id, winner_ids)` | завершение тендера с победителем |
   | `delete_role(key)` | удаление роли |

2. **Большие объёмы.** Если тело запроса не проходит шлюз Supabase (проверяем заранее на самом
   большом реальном объёме), части грузятся в промежуточную таблицу по id операции. Затем одна
   `commit_*` RPC меняет данные одной транзакцией. Частичного состояния нет.
3. **Создание без дублей.**
   - Id создаваемой записи генерирует браузер (`crypto.randomUUID`, полифил есть). Повтор возвращает
     уже созданное.
   - Номера (`display_id`, `public_tender_number`, `request_number`) выдаются в RPC создания: повтор
     даёт тот же номер.
   - **Номер договора остаётся вводом пользователя**, как сейчас. Сервер только предупреждает о
     дубле.
4. **Проверка версии.**
   - Ключевые RPC принимают `expected_updated_at` — **строку как пришла из базы** (микросекунды), не
     пересобранную через `Date`. При расхождении — `version_conflict`, в интерфейсе: «запись изменил
     другой пользователь — обновите».
   - Триггеры `updated_at` для `dc_requests`, `contract_appendices`, `general_documents`; колонка у
     `tender_counterparties`.
5. **Журналы изменений.** Пишутся внутри новых RPC в прежнем формате. Клиентская запись журнала для
   этих действий убирается в том же релизе фронта, иначе строки задвоятся. Остальные журналы — как
   есть до osp-api.
6. **Перестановки** (`sort_order`) — одна RPC на перестановку.
- **Проверки:** `test:db` — атомарность, повтор без дубля, объёмы в пределах `statement_timeout`;

  1. Миграция (новые функции; старые таблицы и права не трогаются).
  2. Фронт с флагом новой операции.
  3. Две недели наблюдения: при сбое флаг выключается.
  4. Подъём `compat`.
  5. Удаление старого пути из кода.

### Р5. Файлы
- **Загрузка.**
  - Действие `upload` в `s3-presign` само создаёт строку `s3_documents` со статусом `pending` от имени
    вызывающего (с проверкой права из Р2f). Браузер грузит в бакет и подтверждает `ready`.
  - Откат загрузки работает: удаление `pending` разрешено автору. Сейчас всегда 404.
  - `pending` видит только автор (RLS). `DEFAULT 'ready'` — старые вкладки работают.
- **Замена файла** (документ объекта, акт гарантии, карточка контрагента, шаблон договора): старый
  файл помечается `deleted_at` через RPC и **после** сохранения формы. Физически не удаляется.
- **Удаление сущности** — тендер, договор, объект, контрагент, ПСДЦ и их дочерние типы владельцев
  (весь список `FOLDER_BY_OWNER`). Триггер помечает файлы `deleted_at`. Физическое удаление через 30
  дней — задача osp-api (этап 3).
- **Обложки → cloud.ru.**
  - Скрипт копирования с SHA-256 и журналом.
  - Показ: обложка рисуется `<img src>`. Выбор — публичный на чтение префикс бакета или пакетная
    выдача ссылок (они живут 60 мин). Решаем при Р5.
  - Подъём `compat` до переписывания URL. Бакет Supabase 30 дней только на чтение.
- **Проверки:** `test:db` для статусов и триггеров; ручная загрузка, замена и удаление по разделам;
  сверка «строки без файла / файлы без строки» скриптом только на чтение.

### Р6. Настройки пользователя в базе
**Зачем.** `localStorage` живёт отдельно на каждом домене, поэтому при переезде на новый домен
настройки пропадут. Среди них есть и пользовательский текст: шаблон письма `letterTemplate:v2`.

- **Полный список ключей** — grep, включая ключи в константах и шаблонных строках:
  - `theme`, `letterTemplate:v2`;
  - `tasksView`, `tasksBoardGroup`;
  - `contracts-hide-tail-columns`, `docCheckView`;
  - `tender-proposal-cols-a/b`, `tender-vor-column-map`, `supply-rates-cols`;
  - `analysis-kp-column-map`;
  - `vors:scope`, фильтры тендеров, `tenders-compact-view:*`;
  - `notifications_read_v2`;
  - и всё, что найдёт grep.
- **Что делаем.**
  - Таблица `user_settings(user_id, key, value)`, RLS — только своя строка.
  - Хук `useUserSetting(key)`: база основная, `localStorage` — кэш.
    - `theme` читается сначала из `localStorage`: тема рисуется до входа.
    - Локальное значение поднимается в базу, только если там пусто: у пользователя может быть
      несколько браузеров.
    - Запись с задержкой.
    - `notifications_read_v2` хранит отметки прочтения: запись в базу с задержкой, старые отметки
      чистим.
  - ESLint запрещает прямой `localStorage` вне хука.
- `userRole`, `contractorInfo`, `rolePreview` выводятся при входе — их не переносим.
- **Условие для смены домена** (этап 5): по телеметрии ≥ N % активных пользователей уже
  синхронизированы. Поэтому Р6 выкладывается заранее, с запасом недель до окна B.
- В колонки-владельцы (inventory, раздел 3) добавить `user_settings.user_id`,
  `client_versions.user_id`, `superadmins.user_id`.

### Р7. SQL и служебная схема — после результата 1 стенда (этап −1 общего плана)
- **Функции, обращающиеся к `auth.users`** (`get_auth_users`, `admin_confirm_user_email`,
  `admin_delete_user`, `is_admin`, `vor_requests_can_access`) переводятся на обёртки. Цель: ни
  одной функции `public`, кроме прослойки `auth.uid()`, не ссылается на `auth.*`. Условие — до
  окна A.
- Tie-breaker в представлениях реестра.
- Схема `ops`: `node_role`, `request_log`, `saga`, `change_outbox` и их триггеры; триггеры
  результата.
- Каталог `db/`: раннер миграций, фильтр схемы, белый список EXECUTE (продолжение Р2g).
- `test:db` с PostgREST под ролью `osp_runtime`.
- Зависит от стендовой базы в контуре (заявка владельцу кластера). До неё не начинаем.

## Готовность к этапу 3 (условие перехода)
- `check:transport` и ESLint: ни одного обращения к Supabase вне `src/api/`.
- Телеметрия и лог nginx: нет старых сборок.
- Матрица прав зелёная:
  - неодобренный, заблокированный, подрядчик (к чужому), аноним — отказ;
  - сотрудник работает в пределах прав разделов, как в интерфейсе;
  - через `anon` вызываются только функции из белого списка.
- 8 опасных цепочек — атомарные RPC с тестами; создание без дублей.
- Файлы: нигде нет «удалить до сохранения»; удаление сущности помечает файлы.
- Настройки пользователей в базе; синхронизация идёт.
- `lint`, `build`, `test:psdc`, `test:tender`, `test:db` зелёные на удалённой машине.
- В миграциях рефакторинга нет разрушительных операций (проверка `test:db`).
- В `client_errors` за последние две недели нет необъяснённых отказов; все флаги новых операций
  включены, старые пути удалены.
- Р7 (обёртки над `auth.users`, служебная схема) — условие окна A, а не этапа 3.
