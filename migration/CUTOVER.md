# Перенос данных портала с базы Supabase на базу Яндекса — порядок действий

Что меняется: страницы портала читают и пишут базу Яндекса через свой сервер (`/api/db` → PostgREST →
база). Что не меняется: адрес сайта, страница входа, вход (Supabase Auth), обложки объектов (хранилище
Supabase). Страницы не переписываются: путь выбирает флаг `ospDb`.

Как это устроено — `server/osp-api/README.md` («Шлюз данных») и `migration/target/sql/load-single-owner.sql`.

**Где работает портал.** Решение владельца от 2026-10-13: портал целиком — сайт, `osp-api` и PostgREST —
переезжает на общий сервер `corp`, у которого есть доступ к базе Яндекса, в образах Docker
(`deploy/docker/README.md`). Адрес `osp.root.sx` прежний. Нынешний сервер под базу не готовится.

**Кто что делает.** Команды на сервере — Cursor, пользователь `corpsu`. Запросы в Supabase SQL Editor —
владелец портала. Загрузку в базу Яндекса и сверку — Claude с удалённой машины, по слову владельца.
Значения секретов в чат и в git не попадают.

**Правило.** Любой шаг дал отказ или расхождение — остановка. Переключение пользователей — только когда
выполнены все четыре доказательства из раздела «Готово».

## Соседи по кластеру не должны пострадать — требование владельца портала

В кластере Яндекса рядом с базой портала — базы других систем (сейчас 20), учётка у нас общая с ними.
Ни одна чужая таблица и ни одна чужая строка не должны измениться. Чем это обеспечено:

| Что могло бы задеть соседей | Почему не заденет | Чем проверяется |
|---|---|---|
| Запись не в ту базу | каждый шаг записи (`load.sh`, `rights.sh`, `reset.sh`) сверяет отпечаток базы (кластер, номер базы, имя, владелец) и при несовпадении отказывает до первой команды; переменные окружения с адресом не используются | `tests/backup/target-load.test.mjs` |
| Затирание существующего | загрузка идёт только в пустую базу, одной транзакцией | там же |
| Удаление лишнего | очистка убирает только объекты из собственного перечня загрузки и только репетицию; нашла что-то сверх перечня — отказ; после настоящего переноса — отказ всегда | там же |
| Команды уровня кластера | их нет: учётка не создаёт и не меняет роли и базы; настройки (`ALTER DATABASE`, права по умолчанию) задаются только базе портала | `tests/osp-api/no-ddl.test.mjs`, тексты `sql/*.sql` |
| Нехватка подключений у других систем | у общей учётки лимит 30, другими системами занято 6. Портал берёт не больше 10: PostgREST — 6 (`PGRST_DB_POOL`), `osp-api` — 4 (`OSP_DB_POOL_MAX=4`) | `neighbors.sh --compare`: предупреждение, если занято больше 70 % лимита |

**Проверка по факту — до и после каждого шага записи** (только чтение, в чужие базы не подключается):
```bash
bash migration/target/neighbors.sh ~/.osp-secrets/target.env --save      # снимок: один раз, до работ
bash migration/target/neighbors.sh ~/.osp-secrets/target.env --compare   # после каждого шага
```
Сравнение показывает: ни одна соседняя база не пропала, не сменила владельца и не уменьшилась заметно,
состав учёток прежний, подключений хватает. `FAIL` — остановка и разбор до любых дальнейших действий.

Чего это не закрывает: пароль общей учётки будет лежать на сервере `corp`, где работают другие проекты
(решение «одна учётка»). Доступ к нему есть у каждого, у кого на сервере права администратора или права
на Docker; права 600 на файлы настроек — единственная защита соседних баз от его утечки.

## А. Портал на сервере corp — в любое время, пользователи не затронуты

Установка, выкладка и правило «соседние проекты на сервере не должны пострадать» —
`deploy/docker/README.md`; вся связка проверяется тестом `tests/deploy/docker.test.mjs`. Порядок:

1. **Выпуск** — на машине сборки (на сервере ничего не собирается): `bash deploy/docker/build.sh`.
   Нужен файл `~/.osp-secrets/web-build.env` с адресом и публичным ключом Supabase для сайта.
2. **Перенос на corp** (Cursor): каталог выпуска и файлы настроек из `~/.osp-secrets/server`
   (`bash migration/target/server-env.sh`): `postgrest.env`, `osp-api.add.env`. В них пароль базы и
   внутренний секрет шлюза — только по `scp`, на экран не выводить, в чат не вставлять.
3. **Сеть до базы Яндекса** — с corp, адрес и порт из файла `db-host`. Нужен `open`:
   ```bash
   # corpsu@corp$
   read -r DBHOST DBPORT < ~/db-host && docker run --rm --entrypoint sh nginx:alpine -c "nc -z -w 5 $DBHOST $DBPORT && echo open || echo closed"; rm -f ~/db-host
   ```
4. **Первая установка** — `deploy/docker/README.md`, «Первая установка на сервере»: снимок соседей, файлы
   настроек (права 600), сертификат базы, установка, сравнение с соседями. В готовности — `"db":"ok"`,
   `"gateway":"ok"`, `"data":"rehearsal"`. С этого шага служба сама пишет в проверочную копию ОСП (копия
   учёток, пересчёт реестра раз в 10 минут) — только в базу ОСП; запуск — по отдельному «да» владельца.
   В `secrets/osp-api.env` также: `SUPABASE_JWT_SECRET` (Supabase → настройки проекта → JWT Keys → Legacy
   JWT Secret; кнопку «Migrate» не нажимать), ключи S3 и Anthropic, служебный ключ Supabase, ключи выдачи
   расценок. Если Anthropic с сервера недоступен — `OSP_API_REQUIRE=supabase,s3`, флаг `ospApiAi` не включать.
5. **Запись в общем nginx** — один файл `osp.conf`, разово (там же, шаг 6).
6. **Проверка без перевода адреса** — на компьютере владельца имя `osp.root.sx` временно указывает на corp:
   сайт с выключенными флагами (данные Supabase), затем раздел Б.
7. **Перевод адреса** — в нерабочее время, по слову владельца: нынешний nginx пересылает запросы на corp →
   проверка → запись DNS. Откат — вернуть прежний файл nginx на нынешнем сервере.

Пока адрес не переведён, пользователи работают с нынешним сервером; сборку с исправлением лишних запросов
реестра тендеров на нём выкладывают как обычно (`deploy/deploy.sh`, пользователь danila).

## Б. Репетиция в базе Яндекса — в любое время

Claude, по отдельному «да» владельца портала на каждую запись в базу Яндекса (утверждение плана таким
«да» не считается):
```bash
bash migration/target/neighbors.sh ~/.osp-secrets/target.env --save                 # снимок кластера до работ
bash migration/target/reset.sh  ~/.osp-secrets/target.env --yes-drop-rehearsal      # убрать прежнюю репетицию
bash migration/target/load.sh   ~/.osp-secrets/target.env <копия.dump> --status rehearsal --single-owner
bash migration/target/verify.sh ~/.osp-secrets/target.env <копия.dump>               # данные и структура
bash migration/target/rights.sh ~/.osp-secrets/target.env <копия.dump>               # права под одну учётку
bash migration/target/neighbors.sh ~/.osp-secrets/target.env --compare              # соседи не пострадали
```
Затем — что видит каждый вид пользователя (только чтение). Права под одну учётку сверены с продом на
локальной копии (`npm run test:db`, `tests/db/single-owner.test.mjs`); этот замер переносит вывод на
настоящую базу — стенд и база Яндекса, загруженные из одной копии, обязаны совпасть:
```bash
bash migration/target/stand.sh up <копия.dump>                                       # локальный стенд из той же копии
bash migration/target/visibility.sh migration/target/reports/stand/stand.env        # замер на стенде → файл
bash migration/target/visibility.sh ~/.osp-secrets/target.env --compare <файл замера стенда>
bash migration/target/stand.sh down
```
После загрузки новой копии PostgREST перечитывает описание структуры базы (corpsu@corp):
`docker compose -p osp kill -s SIGUSR1 postgrest`; проверка — `bash /opt/portals/osp/deploy.sh status`.

**Состояние на 2026-10-13, 13:10 UTC.** Репетиция выполнена: копия `prod-20261013-094329` загружена за 99 с,
сверка — одно ожидаемое расхождение (`kp_rates_registry_mv`, исправляется шагом В.2), права применены за
7 с, проверки — 10 из 10; что видит каждый вид пользователя — совпало со стендом, где права сверены с
продом (680 замеров из 680: 8 видов пользователей × 85 таблиц и представлений); соседние базы без изменений.

**Проверка в одном браузере** (владелец портала): открыть `https://osp.root.sx/?features=ospDb` — этот
браузер работает с репетиционной копией в базе Яндекса, остальные — с Supabase. Пройти под сотрудником,
администратором и подрядчиком: вход, реестры тендеров и договоров, карточка тендера (ВОР, сравнение КП),
реестр расценок, задачи, администрирование; создать, изменить и удалить по одной записи; загрузить,
открыть, скачать и удалить файл. Выключить: `?features=-ospDb`.

**Что у репетиции общее с рабочим порталом.** Строки репетиции потом стираются, и на проде этих правок
не будет. Но хранилище файлов (cloud.ru), вход (Supabase Auth) и обложки объектов (Supabase Storage) у
репетиции те же, что у рабочего портала, — действия в них настоящие. Поэтому:

| Действие в проверочном браузере | Что происходит | Чем обеспечено |
|---|---|---|
| Файлы | идут только через наш сервер; функция файлов Supabase не вызывается ни при каких флагах | `src/api/serverPath.js`, `tests/osp-api/client.test.mjs` |
| Удаление документа, который был до загрузки копии (и записи с такими вложениями) | строка репетиции удаляется, файл в хранилище остаётся — рабочий портал его не теряет | сервер сам читает отметку загрузки (`load.sh --status`); `tests/osp-api/db-gateway.test.mjs` |
| Удаление файла, загруженного в самой проверке | удаляется целиком — и строка, и файл | там же |
| Удаление пользователя, подтверждение почты («Администрирование») | отказ «Проверочная копия данных…»: учётки входа не меняются | там же, `tests/db/single-owner.test.mjs` |

Отметка не читается — сервер считает копию репетицией. В готовности сервера (corpsu@corp:
`bash /opt/portals/osp/deploy.sh status`) видно, с какой копией он работает: `"data":"rehearsal"`.

Чего защита не отменяет: файл, загруженный в проверке и не удалённый там же, останется в хранилище без
строки — удалите его в той же проверке; обложка объекта, загруженная в проверке, и регистрация новой
учётки — настоящие. Прежняя функция файлов Supabase отключается на шаге В.1.

## В. Переключение — в нерабочее время, каждый шаг по слову владельца портала

1. **Барьер записи в Supabase** — старые вкладки больше ничего не запишут и не удалят:
   - SQL Editor: `migration/cutover/01-supabase-readonly.sql`. Проверка — последний запрос файла.
   - **Файлы.** Барьер в базе функцию файлов не останавливает: она удаляет объект из хранилища по строке,
     которую по-прежнему может прочитать. После переключения это был бы файл, на который ссылается база
     Яндекса. Supabase → Edge Functions → Secrets: удалить `S3_SECRET_ACCESS_KEY` (значение есть в `.env`
     на ноутбуке). Без ключа прежняя функция не может ни загрузить, ни выдать, ни удалить файл; файлы
     работают только через наш сервер (с шага 6). Изменение доходит до уже запущенной функции не сразу
     (минуты) — к шагу 3 не переходить, пока проверка не пройдёт: в портале (флаги ещё выключены) документ
     не открывается, повторить через минуту ещё раз.
2. **Исправления в Supabase** (SQL Editor), каждое со своей проверкой:
   - `supabase/migrations/20261011_s3_documents_sha256.sql` → `migration/backup/checks/20261011.sql`;
   - `supabase/migrations/20261015_rates_registry_deterministic.sql` → `migration/backup/checks/20261015.sql`.
3. **Финальная копия** (Cursor): `backup.sh`; Claude — `verify.sh` копии.
4. **Загрузка** (Claude): `neighbors.sh --save` → `reset.sh` репетиции → `load.sh … --status final --single-owner`
   → `verify.sh` (расхождений быть не должно) → `rights.sh` → `neighbors.sh --compare` (без `FAIL`).
5. **Сервер портала** (corpsu@corp): барьер записи шлюза и перезапуск:
   ```bash
   touch /opt/portals/osp/state/db-readonly
   docker compose -p osp kill -s SIGUSR1 postgrest && docker compose -p osp restart api
   bash /opt/portals/osp/deploy.sh status
   ```
   В ответе должно быть `"data":"final"`: сервер видит рабочую копию. `rehearsal` или `unknown` —
   остановка: загрузка шага 4 не завершена или сервер смотрит не в ту базу.
   Барьер закрывает запись через шлюз и загрузку, подтверждение и удаление файлов; чтение и скачивание работают.
6. **Флаги** (corpsu@corp) — в `/opt/portals/osp/shared/config.json`: `"ospDb": true, "ospApiFilesV2": true, "ospApiAi": true`.
   `ospApiAi` — только если в готовности `"anthropic":"ok"`; если Anthropic с сервера недоступен, ИИ остаётся
   на функции Supabase (она данные не читает) — этот флаг не включать.
   Открытые вкладки перейдут в течение двух минут. Портал читает базу Яндекса, запись закрыта барьером.
7. **Проверка чтения** (владелец портала): вход и основные разделы под тремя ролями.
8. **Снять барьер шлюза** (corpsu@corp): `rm /opt/portals/osp/state/db-readonly`. С этого момента записи идут в базу Яндекса.
9. **Проверка записи** под тремя ролями: создать, изменить, удалить запись; загрузить и скачать файл.
10. **Смежному отделу** — новый адрес выдачи расценок: `https://osp.root.sx/api/rates/…` с прежним ключом.

**Откат до шага 8** (ни одной записи пользователей в базе Яндекса и ни одного изменения в хранилище ещё
нет): флаги в `config.json` → `false`, `migration/cutover/02-supabase-readonly-rollback.sql` в SQL Editor,
вернуть секрет `S3_SECRET_ACCESS_KEY` функциям Supabase. Портал снова работает с Supabase.

**После шага 8** возврата на Supabase нет: в нём не будет новых записей. Исправление — только вперёд.
Supabase остаётся замороженным (только чтение) 30 дней.

**Копия базы Яндекса** — сразу после шага 9 и затем каждую ночь (только чтение, чужие базы не трогает):
```bash
bash migration/target/export.sh ~/.osp-secrets/target.env            # снимок всех таблиц одной транзакцией
bash migration/target/export-verify.sh migration/dumps/yandex-<время>  # проверка восстановлением
```
Обычный `pg_dump` данных здесь не подходит: правила по строкам действуют и на владельца.

## Готово, когда есть четыре доказательства
1. Браузер не обращается к базе Supabase: в Usage и в журнале портала нет запросов к таблицам.
2. Все виды пользователей видят ровно разрешённое: замер прав под одной учёткой на финальной копии
   совпадает с эталоном прода (`npm run test:db`, `tests/db/single-owner.test.mjs`), `rights.sh --check` —
   без замечаний, `visibility.sh --compare` стенда и базы Яндекса — совпало.
3. Контрольные суммы финальной копии совпадают: `verify.sh` — без расхождений.
4. Портал читает и пишет в базу Яндекса; откат до шага 8 проверен на репетиции.

## Известные отличия по скорости
Замер 2026-10-13 на одной машине: копия прода с правами прода против той же копии под одной учёткой
(`tests/db/single-owner.test.mjs` поднимает такую же). Полный подсчёт строк таблицы:

| Кто и что | Права прода | Одна учётка |
|---|---|---|
| Сотрудник: позиции смет (64 тыс. строк) | 2,0 с | 0,007 с |
| Сотрудник: предложения подрядчиков (91 тыс.) | 3,0 с | 0,007 с |
| Сотрудник: документы (4,5 тыс.) | 0,15 с | 0,005 с |
| Сотрудник: строки ПСДЦ (102 строки) | 0,10 с | 0,25 с |
| Сотрудник: журнал задач (122 строки) | 0,02 с | 0,08 с |
| Учётка без доступа: позиции смет | 6,0 с | 19 с |

- **Быстрее в сотни раз** — правила, где проверка одна на запрос («сотрудник ли это»): под одной учёткой
  она вычисляется один раз, а не на каждую строку. Это основные реестры и карточки.
- **Медленнее в 2,5–3 раза на строку** — правила, где функция вызывается на каждую строку: `psdc_visible`,
  `psdc_can_view_document`, `can_see_task`, `is_task_participant`, `is_my_tender`, `is_my_contract`. Внутри
  такой функции каждое чтение таблицы теперь тоже проходит правила по строкам.
- **Сегодня это незаметно:** таблицы с построчной проверкой малы (строк ПСДЦ — 102, задач — 49),
  подрядчиков с доступом в данных нет.
- **Станет заметно** на ведомости ПСДЦ в тысячи строк (оценка по замеру: страница в 1000 строк — около 1 с
  с правами прода и около 2,5 с под одной учёткой) и в кабинете подрядчика. До больших ведомостей и до
  открытия регистрации подрядчиков — отдельная задача: проверять доступ один раз на ведомость, тендер или
  договор, а не на строку. Она ускорит и нынешний прод.
- Учётка без доступа ни одной строки не видит в обоих случаях; её полный подсчёт большой таблицы может не
  уложиться в таймаут базы (30 с) и вернуть отказ вместо нуля. Страницы портала таких запросов не делают.

## Что остаётся в Supabase после переключения
Вход (Auth) и обложки объектов (Storage). База заморожена; функция файлов без ключа хранилища не
работает (шаг В.1). Когда смежный отдел перейдёт на новый адрес выдачи расценок — удалить там же секрет
`RATES_API_KEYS`: прежняя функция расценок читает замороженную базу. `ANTHROPIC_API_KEY` — удалить, если
ИИ переведён на наш сервер (`ospApiAi`).
Следующие шаги — отдельные задачи: перенос обложек, свой вход, выключение Supabase.
