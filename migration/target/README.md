# Целевая база: разведка, загрузка, сверка

Инструменты переноса данных портала в выданную базу PostgreSQL (Яндекс). В кластере рядом лежат базы
других порталов, поэтому каждый скрипт работает только с базой из файла подключения.

| Скрипт | Что делает | Пишет в базу |
|---|---|---|
| `probe.sh` | разведка: чья база, права роли, расширения, пуста ли, кто ещё может подключиться | нет |
| `pin.sh` | закрепить базу: отпечаток рядом с файлом подключения | нет |
| `load.sh` | загрузка проверенной копии прода одной транзакцией | да — только в пустую закреплённую базу |
| `verify.sh` | сверка загруженного с копией | нет |
| `reset.sh` | возврат к пустой базе после репетиции | да — удаляет только репетицию |
| `rights.sh` | права под одну учётку после загрузки `--single-owner` и сверки; `--check` — только проверка | да — только в закреплённой базе |
| `neighbors.sh` | соседи по кластеру не пострадали: снимок (`--save`) и сравнение (`--compare`) | нет |
| `export.sh` / `export-verify.sh` | копия базы после переноса под одну учётку и её проверка восстановлением | нет |
| `vault.sh status` | учётки с отпечатками паролей: сколько, у скольких отпечаток устарел или его нет | нет |
| `server-env.sh` | файлы настроек для сервера портала из файла подключения (значения не выводит) | нет |

Второй базы под стенд нет (решение 2026-10-12): репетиции идут локально в Docker, генеральная — в
самой выданной базе, пока портал ею не пользуется. Каждая запись в неё — по отдельному «да».

## Разведка

Первый шаг с любой выданной базой — узнать, что это за база и какие у роли права. **Только чтение.**

На удалённой машине, из корня репозитория:

```bash
bash migration/target/probe.sh ~/.osp-secrets/target.env
```

Файл — строки `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGSSLMODE` (необязательно
`PGSSLROOTCERT`). Он разбирается, а не исполняется. Если `PGPASSWORD` в файле нет, пароль спрашивается
скрыто.

Файл хранится вне репозитория, доступ — только владельцу:

```bash
install -d -m 700 ~/.osp-secrets
# скопировать файл в ~/.osp-secrets/target.env, затем:
chmod 600 ~/.osp-secrets/target.env
```

В git и в чат файл не попадает. После разведки его можно стереть: `shred -u ~/.osp-secrets/target.env`.

## Что гарантировано

Проверяет `tests/backup/target-probe.test.mjs` (`npm run test:backup`):
- **Ничего не меняется.** Запросы идут к системным каталогам в транзакции `READ ONLY` с `ROLLBACK`.
  «Отпечаток» кластера до и после совпадает, даже под суперпользователем.
- **Секретов в выводе нет.** Пароль, адрес и имя пользователя не печатаются. Имена базы и роли — только
  если они из нашей заявки (`migration/requests/cluster-owner.md`). Чужие базы, роли и таблицы — только
  счётчиком.
- **Подключение только к базе из файла.** Переменные `PG*` из окружения не используются.
- **Без зависаний.** Нет связи — понятная строка и код выхода 2.

## Отчёт

Строки `OK` / `ВНИМАНИЕ` / `FAIL` / `ИНФО` — на экран и в `migration/target/reports/probe-<время>.txt`
(вне git, права `600`):
- чья база (Яндекс, Supabase, другая), порт, TLS;
- версия, кодировка, сортировка, часовой пояс — против заявки;
- база и роль, права роли, владелец ли она базы;
- расширения `pg_trgm`, `pgcrypto`, `uuid-ossp`;
- пуста ли база, сколько ещё баз видно;
- режим пулера. Ветка «режим транзакций» на настоящем пулере не проверялась — образа пулера для теста
  нет; окончательный ответ — настройка роли у владельца кластера.

Для `verify-full` нужен корневой сертификат Яндекса. Он кладётся **рядом с файлом подключения** — скрипт
найдёт его сам (порядок: `PGSSLROOTCERT` из файла → `root.crt` рядом → место libpq по умолчанию):

```bash
curl -fsS https://storage.yandexcloud.net/cloud-certs/CA.pem -o ~/.osp-secrets/root.crt && chmod 600 ~/.osp-secrets/root.crt
```

В `~/.postgresql/root.crt`, как советует документация Яндекса, на этой машине класть **нельзя**: при этом
файле libpq проверяет сертификат и у подключений с `sslmode=require`. Сломаются копии Supabase
(`migration/backup/backup.sh`, `counts.sh`) и подключения других проектов под тем же пользователем.

Если имя базы или роли не из заявки, отчёт его не покажет, но скажет, есть ли в нём «osp» и похоже ли
оно на стенд (`stage`, `test`, `dev`) или на боевую (`prod`).

## Закрепление базы: `pin.sh`

Учётка из файла подключения открывает несколько баз кластера. Чтобы опечатка в файле не привела загрузку
или очистку в чужую базу, база закрепляется один раз после разведки:

```bash
bash migration/target/pin.sh ~/.osp-secrets/target.env             # показать, что будет закреплено
bash migration/target/pin.sh ~/.osp-secrets/target.env --confirm   # записать target.env.pin
```

Отпечаток — `sha256` от идентификатора кластера, номера базы, её имени и владельца; сами имена в файл и в
вывод не попадают. `load.sh` и `reset.sh` сверяют его до первой записи: другой адрес, другая база или
другой владелец — отказ. Только чтение.

## Загрузка: `load.sh`

```bash
bash migration/target/load.sh ~/.osp-secrets/target.env migration/dumps/prod-<время>.dump --status rehearsal
bash migration/target/load.sh ~/.osp-secrets/target.env migration/dumps/prod-<время>.dump --status rehearsal --without-rights
```

- **Всё или ничего.** Загрузка — одна транзакция: при любой ошибке в базе не меняется ничего.
- **Только проверенная копия** — с отметкой `.verified` от `migration/backup/verify.sh`.
- **Только в пустую закреплённую базу**, от имени её владельца. Подключение к базе у «всех» (PUBLIC)
  должно быть снято — в Яндексе так и есть; скрипт права на саму базу не меняет, только проверяет.
- **С правами** (по умолчанию): роль приложения (`osp_runtime`) должна существовать и ничем не владеть;
  её и расширения `pg_trgm`, `pgcrypto` создают в консоли Яндекса, скрипт их не создаёт.
- **Без прав** (`--without-rights`, решение 2026-10-12 — второй учётки нет, права проверяет backend):
  роль приложения не нужна; политики и выдача прав не загружаются; у своих функций и типов снимается
  право «всем», и для будущих функций и типов этой учётки в этой базе оно не выдаётся
  (`sql/load-lockdown.sql`). Итог: обычные учётки кластера данные портала не читают и не меняют и его
  функции не вызывают. Не защищает от суперпользователей Яндекса; имена таблиц и тексты функций видны
  любому, кто может подключиться к базе (каталог PostgreSQL). Только для репетиции: `final` без прав —
  отказ, до отдельного решения.
- **Данные, таблицы, функции, индексы — как в копии, без правок.** Правятся только записи о правах
  (`lib/rewrite.mjs`), по строгим правилам; незнакомая роль или форма записи — отказ:
  - роль Supabase `authenticated` → `osp_runtime` — в политиках и выдаче прав;
  - `anon` и `service_role` не переносятся: это публичная витрина тендеров и функции Supabase, их
    заменяет отдельный шаг. Что именно не перенесено — в отчёте;
  - права по умолчанию Supabase («новая таблица открыта всем ролям») не переносятся.
- **Схема `auth`** (`compat/auth.sql`): `auth.uid()`, `role()`, `jwt()`, `email()` с теми же телами, что в
  Supabase, — политики и функции портала работают без правок. Копию `auth.users` без паролей создаёт
  `rights.sh` (`sql/load-single-owner.sql`).
- **Учётные записи** (`--auth`, `sql/load-auth.sql`): выгрузки этой же копии (`.auth-users.csv`,
  `.auth-identities.csv`, целы по `.extras.sha256`) — в закрытую схему `osp_vault`. Правило по строкам
  действует и на владельца, единственная политика — отметка `osp:vault` внутри транзакции, которую не
  ставит ни одна функция портала; PostgREST эту схему не отдаёт. Число строк сверяется с описью копии в
  той же транзакции. Копия `auth.users` без паролей (для функций администратора) наполняется из неё на
  шаге `rights.sh`.
- **Обложки** (`--covers <журнал>`, `sql/load-covers.sql`): журнал `deploy.sh covers-copy`, снятый по
  списку этой же копии. Адрес обложки меняется на `/api/covers/<имя>` только у сверенных файлов и только при
  точном совпадении прежнего адреса; триггеры `objects` на время замены выключены (дата изменения не
  меняется), число заменённых строк обязано совпасть с ожидаемым — иначе отмена всей загрузки. Это
  единственная правка данных при загрузке; сверка (`verify.sh --covers`) делает ту же замену на эталоне.
- **`--status final` — только с `--auth` и `--covers`**, и только если сверены все обложки списка.
- **Часовой пояс базы — UTC**, как в Supabase (у кластера он общий — Москва).
- **Отметка** в схеме `osp_meta`: что загружено (sha256 копии), когда, статус и перечень созданного.
- `--status final` — настоящий перенос: после него `reset.sh` отказывает всегда.

## Сверка: `verify.sh`

```bash
bash migration/target/verify.sh ~/.osp-secrets/target.env migration/dumps/prod-<время>.dump
```

Эталон — та же копия, восстановленная во временный PostgreSQL в Docker со всеми ролями Supabase и с
правилами сортировки прода (ICU `en-US`). Один и тот же набор запросов (`sql/verify-facts.sql`)
выполняется на эталоне и на загруженной базе, ответы обязаны совпасть:
- число строк и контрольная сумма каждой таблицы и материализованного представления;
- счётчики номеров, колонки, ограничения, индексы, триггеры, функции, представления, типы;
- политики (команда, условия, роли) и выданные права: `osp_runtime` в базе против `authenticated` в
  эталоне. После загрузки без прав вместо этого проверяется, что база закрыта (`sql/verify-closed.sql`):
  политик нет; выдач не владельцу на таблицы, колонки, счётчики, функции, типы и служебные схемы нет;
  запрет «всем» для будущих функций и типов стоит. Справочно — сколько ещё обычных учёток может
  подключиться к базе и есть ли их сеансы.

Плюс число строк против подсчёта на проде до и после снятия копии:
- репетиция — в пределах «до» и «после» (во время копии люди работают);
- настоящий перенос — «до» = «после» = в базе; иначе отказ: запись не была остановлена.

И часовой пояс с порядком сортировки кириллицы. Выход 0 — «РАСХОЖДЕНИЙ НЕТ».

## Очистка после репетиции: `reset.sh`

```bash
bash migration/target/reset.sh ~/.osp-secrets/target.env --yes-drop-rehearsal
```

Удаляет ровно то, что создал `load.sh`, одной транзакцией, и возвращает права по умолчанию, если загрузка
была без прав. Отказывает и ничего не меняет, если база не та, что закреплена, если в ней нет нашей
отметки, если последняя загрузка — `final`, или если есть объекты сверх загруженных. Расширения и схему
`public` не трогает.

## Что проверено

`npm run test:backup` (`tests/backup/target-load.test.mjs`, Docker; база — владелец без прав
суперпользователя и без права создавать роли, часовой пояс сервера — Москва):
- ошибка в самом конце загрузки — в базе не остаётся ничего;
- сверка ловит подменённую строку, пропавшую строку, сдвиг счётчика, снятую политику, отозванное право,
  лишнюю колонку;
- права действуют на роль приложения: строки видит только вошедший, структуру менять она не может;
- повторная загрузка в непустую базу, очистка после `final`, чужая таблица в базе — отказ;
- без отпечатка и в другую базу той же учётки загрузка и очистка не идут, в соседней базе ничего не
  создаётся;
- после загрузки без прав соседняя учётка кластера (подключение ей открыто) не читает таблицы,
  представления и счётчики, не вызывает функции — в том числе созданную позже, — не пишет и не создаёт
  объекты; сверка ловит и подмену данных, и выданное постороннему право.

Локально на проверенной копии прода (2026-10-12): загрузка 7 с, сверка 11–12 с, расхождений нет — 76
контрольных сумм, 903 колонки, 310 индексов; с правами — 102 политики и 180 выдач прав, без прав — база
закрыта, соседней учётке отказ на таблицах, представлениях и функциях.

**Не проверено и не сделано:**
- загрузка в саму базу Яндекса — после закрепления базы и отдельного «да»;
- в Яндексе к базе портала могут подключиться ещё две обычные учётки и два суперпользователя (разведка
  2026-10-12): кто они и нужен ли им доступ — вопрос администратору кластера;
- поведение прав по классам пользователей (`test:db`) на загруженной базе — нужен шаг «вход»: проверка
  опирается на таблицу пользователей. Сейчас доказано равенство самих политик и выданных прав;
- пять функций, читающих `auth.users`, и публичная витрина (политики `anon`) — шаг «вход».
