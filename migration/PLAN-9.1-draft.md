## Уточнение владельца портала 2026-10-13: адрес и страница входа прежние
Цель сейчас — полностью и безопасно уйти с Supabase. Переезд на новый адрес и вход через Keycloak —
отдельными шагами позже; ниже всё, что говорит о них (раздел 0a, правило 11; шаг 4 раздела 6), читать с
этой поправкой.

**Вход — через свой API, страница входа прежняя** (правило 11 `docs/API_RULES.md`; §13 стандарта —
самостоятельный вход для портала, не подключённого к Keycloak):
- учётки переносятся из Supabase Auth как есть: идентификатор, почта, зашифрованный пароль (bcrypt),
  признаки подтверждения и блокировки. Идентификаторы не меняются — все ссылки на пользователей в данных
  остаются верными, файл сопоставления не нужен; люди входят той же почтой и тем же паролем;
- osp-api проверяет пароль, выдаёт сессию в httpOnly cookie (обновление с ротацией, отзыв при
  блокировке), защищает вход от перебора; токена в `localStorage` нет;
- переключение — после переноса базы: к этому моменту браузер уже не обращается к Supabase за данными,
  и смена входа ничего больше не затрагивает. Пользователи заметят один повторный вход;
- до переключения решить: письма о подтверждении почты и сбросе пароля (сейчас их шлёт Supabase) — свой
  почтовый сервер либо сброс пароля через администратора;
- выгрузка учёток с паролями — секрет того же уровня, что копия базы: вне git, права `600`, не в чат.

**Порядок без домена и Keycloak:** функции на своём API → основа слоя данных, стенд приёмки, пилоты →
разделы по очереди (и обложки, опрос, расписание) → перенос базы (объявленная пауза записи) → вход через
свой API → Supabase заморожен на 30 дней и выключен.

**Сделано к этому шагу:** обёртка транзакции osp-api (`server/osp-api/src/lib/db.js`) — только чтение для
читающих операций, контекст и таймауты на одну транзакцию, откат при любой ошибке, испорченное
подключение не возвращается в пул, одна параметризованная команда на запрос, второй замок на время
жизни в Supabase; тесты на настоящем PostgreSQL и проверка «в коде сервера нет команд изменения структуры».
Вход без обращения к Supabase на каждый запрос: токен проверяется на сервере (только HS256, издатель,
назначение, роль; ключи самого проекта токеном пользователя не считаются), статус учётки — из базы с кэшем
30 с (блокировка и отзыв одобрения действуют при живом токене), сбой базы — 503, а не «прав нет».
Подключение к базе не на этой машине — только с проверкой сертификата и имени сервера; строка подключения
проверку не ослабляет. Включается ключами окружения, по умолчанию выключено.

## 3. Шаг 0 — репетиция загрузки в базу Яндекса (не зависит от ворот 0)
Зачем: узнать, примет ли кластер загрузку, и **измерить длительность паузы записи** для раздела 6.

**Привязка к базе.** Рядом с файлом подключения — файл с отпечатком цели: `sha256(идентификатор кластера
‖ номер базы ‖ имя ‖ владелец)`. Создаётся отдельной командой после разведки и «да» пользователя.
`load.sh` и `reset.sh` сверяют отпечаток до первой записи; не совпал — отказ. Проверка «`osp` в имени»
убирается.

**Закрытие v2** (`sql/load-lockdown.sql`, та же транзакция, только при загрузке без прав):
- у всех своих функций снять вызов «всем»; у своих типов — пользование «всем»;
- права по умолчанию для будущих объектов нашей учётки в этой базе: функции и типы — без «всем»
  (`ALTER DEFAULT PRIVILEGES … REVOKE … FROM PUBLIC`, действует только в этой базе);
- `reset.sh` возвращает права по умолчанию.

**Проверки без изменения** (`load-preflight.sql`, `verify.sh`):
- право подключения у «всех» снято; создавать в `public` «все» не могут;
- чужих сеансов в базе нет — до загрузки и после;
- на своих объектах (таблицы, колонки, счётчики, представления, функции, типы, схемы `auth` и
  `osp_meta`) нет ни одной выдачи кому-либо, кроме владельца; политик нет.

**Гарантия — сужена:** обычные учётки кластера не читают и не меняют данные портала и не вызывают его
функции. Не гарантируется: суперпользователи Яндекса; имена таблиц, тексты функций и представлений
видны любому, кто может подключиться (каталог PostgreSQL), — таких обычных учёток две.

**Тест под соседней учёткой** — в Docker (есть) и, если администратор согласится, в самом кластере.

**Порядок в Яндексе:** `probe.sh` → отпечаток цели → `load.sh --status rehearsal --without-rights` →
`verify.sh` → отчёт с длительностью → `reset.sh`. Запись — только по явному «да».

**Просим администратора** (тем же обращением, что в разделе 7): кто эти две учётки и нужен ли им
доступ; снять `TEMPORARY` у «всех»; допустимо ли снять у «всех» пользование схемой `public`.

## 4. Шаг 1 — каркас слоя данных в osp-api и пилоты
**Кто вошёл — без обращения к Supabase на каждый запрос.** Подпись токена проверяется локально (`jose`,
алгоритм — из белого списка, по ключу проекта); статус пользователя (одобрен, не заблокирован, роль,
организация) читается из базы с кэшем не дольше 60 с — отзыв прав действует в пределах минуты. Тест:
заблокированный пользователь с ещё живым токеном получает отказ.

**Единая обёртка транзакции** — другого пути к базе в коде нет:
- `BEGIN` → `SET LOCAL` таймаутов (запрос, блокировка, простой в транзакции) → контекст → запросы →
  `COMMIT`; при любой ошибке `ROLLBACK`; не удался `ROLLBACK` — подключение уничтожается;
- контекст — минимальный, собранный сервером (`sub`, `role`, `email`), а не JSON исходного токена;
  только `set_config(…, true)`;
- только параметризованные запросы, без именованных подготовленных; динамические имена — из белого
  списка;
- пока база в Supabase — `SET LOCAL ROLE authenticated` (второй замок). Проверить заранее, что учётка
  подключения вправе на неё переключаться;
- тесты пула с внесением сбоев: ошибка посреди транзакции, обрыв клиента, запрос без токена после
  запроса администратора, проверка роли, `search_path`, блокировок и временных объектов после возврата
  подключения в пул.

**Права.** Решение принимает backend: вход в операцию — в коде маршрута; строки — условием в SQL
операции. На первом этапе условия вызывают прежние функции базы (временный мост, одобрен рецензией);
окончательно — идентификатор пользователя и организации передаются в запрос явными параметрами. Перевод
на параметры — отдельный проход после переноса базы.

**Одно действие пользователя = одна операция = одна транзакция.** Цепочки запросов (около 110, из них 8
теряют данные при сбое) не переносятся по одному запросу, а собираются в операции. Пишущая операция
принимает ключ операции (UUIDv7, как уже сделано для файлов): повтор возвращает прежний результат и
ничего не дублирует.

**Язык.** TypeScript + zod (вход и ответ), SQL через `pg`, без Drizzle — оформить как исключение из §5
стандарта (ADR).

**Фронт.** Модуль `src/api/sections/<раздел>.js` на раздел; два релиза: (1) запросы переезжают в модуль
без изменения поведения; (2) второй путь через osp-api под флагом раздела, флаг читается на лету.

**Телеметрия по операциям.** У каждой операции имя; модуль раздела считает вызовы старого и нового
пути. Раздел закрыт, когда 7 дней нет вызовов старого пути его операций (не «его таблиц» — таблицы
общие) и не было откатов флага. Плюс метрики пула и готовность обеих баз в `/api/ready`.

**Пилоты:**
1. «Реестр расценок» — только списки, фильтры и выгрузка. Кнопка обновления, расписание и внешний
   `rates-api` по ключу — отдельные потоки, не в пилоте.
2. «Задачи» — первый полноценный пилот прав: чтение и запись, свои таблицы, «видят только участники».

**Потоки вне разделов** (каждый — своя приёмка): замена `auth.users` (5 функций) — до раздела
администрирования, а не перед переносом; расписания с защитой от двойного запуска; опрос вместо Realtime
— частота и нагрузка; обложки → cloud.ru с контрольными суммами и проверкой адресов; публичная витрина;
`rates-api` для смежного отдела; `client_errors`; отчёты и выгрузки — лимиты, постраничность, память.

Р2a/b применяется на Supabase как планировалось: дыры есть сейчас, политики — второй замок. Пункты Р2
c–h реализуются сразу в backend.

## 5. Приёмка раздела — сравнение двух путей
Проверки backend должны быть достаточны без политик базы, а политики способны скрыть его ошибку.
Поэтому сравниваются точные ответы.

**Стенд (Docker):** две базы из одной проверенной копии прода и одинаковых добавленных данных:
- А — эталон: роли Supabase, политики, настоящий PostgREST (нужен образ, сейчас его нет);
- Б — целевой вид: загрузка без прав, подключение под владельцем, osp-api.

**Матрица:** операция × пользователь × входные данные. Операции берутся из модуля раздела; тест падает,
если у операции нет случаев (приём — как `tests/osp-api/upload-sites.test.mjs`).
- Пользователи: не меньше двух организаций, свои и чужие объекты, два пользователя одной роли,
  заблокированный, неодобренный, без организации, без строки ролей.
- Чтение: старый путь на А и новый на Б возвращают одни и те же идентификаторы и поля.
- Запись: одинаковая разница в базе (построчные суммы затронутых таблиц до и после); при отказе —
  разница нулевая на обеих и тот же вид ошибки.
- Отрицательные случаи: чужой `object_id` / `counterparty_id` / `created_by`, лишние колонки, массовое
  условие, недопустимый переход статуса, назначение себе роли, повтор с тем же ключом операции.

**Намеренные отличия** (backend строже нынешних политик — правила интерфейса, которых в RLS нет) —
явный список на раздел, утверждает пользователь; всё, чего в списке нет, — ошибка.

`tests/db/baseline/rights.json` остаётся дымовой проверкой.

## 6. Шаг 3 — перенос базы (СТОП 2, отдельное «да»)
**Пауза записи — объявленное окно.** Чтение работает; запись отклоняется. Длительность берётся из
репетиции (локально: загрузка 7 с, сверка 11 с) и согласуется заранее.

**Барьер на сервере** (не баннер), по порядку:
1. osp-api — режим «только чтение»: пишущие операции отвечают 503 с понятным текстом;
2. Supabase — у ролей `authenticated` и `anon` снимается запись: старая вкладка мимо osp-api не запишет;
3. остановлены расписания, Edge Functions, обновление реестра; `rates-api` только читает;
4. ожидание начатых транзакций: в `pg_stat_activity` нет пишущих старше барьера;
5. счётчики строк «до» и «после» копии равны — иначе `verify.sh` для `final` отказывает (уже есть).

**Точка невозврата** — первая запись, принятая базой Яндекса.
- До неё откат: строка подключения osp-api обратно, барьер снят.
- После неё решение принимается **до окна**, как в ред. 8.1: (а) только исправление вперёд + ночные
  проверенные копии базы Яндекса; (б) обратный перенос данных тем же инструментом во втором окне —
  отрепетированный локально до СТОП 2. Рекомендация — (б); выбор за пользователем на СТОП 2.

Условие начала: по телеметрии ни одна операция не идёт старым путём; замена `auth.users` сделана.

## 7. Учётка-владелец у приложения — критическое исключение из §7 стандарта
План соответствует «v3.2 с принятым критическим исключением», а не v3.2. Параметризованный SQL не
защищает от украденного пароля: владелец может менять и удалять структуру, а пароль открывает ещё 11 баз
и уже используется другими системами (5 сеансов).

**До боевого запуска — минимум:**
- доступ к PostgreSQL по сети только с сервера портала и машины миграций;
- секрет — в защищённом хранилище (§18); смена пароля перед запуском — согласуется с владельцами других
  систем на этой учётке;
- бюджет подключений: лимит 30 общий, 6 занято другими — пулу osp-api отводится явная доля с запасом;
- журнал изменений структуры и подключений на стороне кластера;
- **письменное принятие исключения** владельцем кластера или безопасности;
- если администратор может ограничить учётку одной базой или сменить владельцев соседних баз — сделать.

Обращение к администратору кластера неизбежно: сеть, журнал, смена пароля, письменное принятие.
`migration/requests/cluster-owner.md` переписывается под этот список.
