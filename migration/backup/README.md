# Резервная копия, проверка и прогон миграций на копии

Проект Supabase на бесплатном тарифе: **резервных копий Supabase не делает**. Поэтому перед каждой
миграцией снимаем свою копию, проверяем её восстановлением и прогоняем миграцию сначала на копии.
Проверено тестом `npm run test:backup` на синтетическом «проде».

## Правила

1. Пока нет проверенной копии, в прод ничего не пишется.
2. Каждая миграция сначала идёт на копии: два прогона, число строк во всех таблицах не меняется.
3. После миграции на проде строки считаются снова и сравниваются с подсчётом до.
4. Копия содержит данные пользователей. Она лежит только на удалённой машине, в `migration/dumps/`
   (вне git, права `600`). В чат идут только счётчики. Через 30 дней копия удаляется.

## Шаги (на удалённой машине, из корня репозитория)

Всё запускается под вашим пользователем на удалённой машине — тем, под которым вы заходите по
`ssh kg_claude_new`. Пароль базы Supabase (Database → Settings → Database password, см. [schema/README.md](../schema/README.md)) вводится скрыто: он не
попадает ни в чат, ни в историю команд, ни в аргументы процессов.

| # | Кто | Команда | Что делает с продом |
|---|---|---|---|
| 1 | вы | `bash migration/backup/backup.sh` | только читает: подсчёт строк до, `pg_dump` схемы `public`, подсчёт после |
| 2 | я | `bash migration/backup/verify.sh migration/dumps/prod-<время>.dump` | не трогает: восстанавливает копию во временном PostgreSQL и сверяет строки |
| 3 | я | `bash migration/backup/rehearse.sh <копия> <миграция> [проверка]` | не трогает: два прогона миграции на копии, сверка строк |
| 4 | вы | миграция в Supabase SQL Editor (текст файла целиком → Run) | применяет миграцию |
| 5 | вы | `bash migration/backup/counts.sh migration/dumps/prod-<время>.counts-after.tsv` | только читает: строки сейчас против подсчёта на момент копии |

Шаги 2 и 3 печатают «КОПИЯ ГОДНА» / «МИГРАЦИЯ ГОДНА» — только после этого шаг 4.
Шаг 5: рост числа строк в рабочих таблицах — обычная работа людей; тревога — «СТАЛО МЕНЬШЕ» или
«ТАБЛИЦА ИСЧЕЗЛА».

Подключение по умолчанию — session pooler Supabase `aws-1-eu-north-1.pooler.supabase.com:5432`,
пользователь `postgres.<ref проекта>`. Если Supabase в разделе Connect показывает другой хост
session pooler — задайте его перед командой: `PGHOST=<хост> bash migration/backup/backup.sh`.

## Проверочные запросы к миграциям

`checks/<миграция>.sql` — что должно получиться после миграции. Запускаются и на копии (третьим
аргументом `rehearse.sh`), и на проде в SQL Editor. Каждая строка ответа начинается с `OK` или `FAIL`:
- годно — только если нет ни одной строки `FAIL`;
- `rehearse.sh` проверяет это сам и при `FAIL` печатает «МИГРАЦИЯ НЕ ГОДНА».

Перед миграцией `rehearse.sh` включает на копии права по умолчанию, как в Supabase
([`supabase-defaults.sql`](supabase-defaults.sql)): новые таблицы и функции сразу доступны `anon` и
`authenticated`. Поэтому миграция, которая забыла отозвать права, на копии не пройдёт.

| Миграция | Проверка | Ожидается |
|---|---|---|
| `20261006_user_roles_counterparty_restrict.sql` | `checks/20261006.sql` | одна строка `OK … ON DELETE RESTRICT` |
| `20261007_client_telemetry.sql` | `checks/20261007.sql` | 10 строк `OK`: обе таблицы с RLS, у `authenticated` только чтение, у `anon` и `PUBLIC` прав нет, политики только на чтение, обе функции `SECURITY DEFINER` с `search_path`, `EXECUTE` только у `authenticated` |
