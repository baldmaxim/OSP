# Вопросы владельцам контура su10 — портал ОСП

> Ответы нужны до проектирования стенда: от них зависит, где и как работает API портала.

**Портал:** ОСП — отдел сопровождения подрядчиков. Уходит с Supabase в контур su10 (общий кластер
PostgreSQL, вход через `auth.su10.ru`) и одновременно со сменой входа переезжает на новый домен.
**Контакт со стороны портала:** <ФИО, канал>.

## 1. Хостинг

Вместо Supabase у портала появляется свой backend: `osp-api` на Node.js 24 (2 экземпляра) и PostgREST
(2 экземпляра), плюс статика фронта за nginx.

1. Какой стандарт размещения порталов в контуре: Kubernetes, ВМ, что-то ещё? Есть ли шаблон
   (Terraform, Helm, CI/CD), по которому заведены действующие порталы?
2. Где хранить секреты приложения (пароли БД, client secret Keycloak, ключи S3 и Anthropic)?
3. Логи и мониторинг: куда отправлять, есть ли алерты по умолчанию?
4. **Регион.** Портал вызывает Claude API (Anthropic) — помощник юриста по протоколу разногласий.
   Из России API недоступен. Можно ли разместить `osp-api` в регионе, откуда он доступен (например,
   kz1), или есть принятый в контуре способ выхода к внешним API?
5. SLO хостинга: доступность, время восстановления ВМ или пода.

## 2. Домен

1. Какой адрес будет у портала: `<osp>.su10.ru` или другой? Нужны прод и стенд.
2. Кто выпускает TLS-сертификаты и настраивает DNS?
3. Нынешний адрес `osp.root.sx` после переезда должен перенаправлять на новый (закладки, ссылки в
   письмах подрядчикам). Кто держит этот домен после переезда?

## 3. Объектное хранилище

Нужен бакет (прод и стенд) для трёх вещей:
- копии очереди правок пользователей на время окон переключения;
- журнала изменений базы для аварийного восстановления (хранение 30 дней);
- ночных дампов базы портала (хранение 30 дней).

Бакет должен быть **вне общего кластера PostgreSQL**, чтобы пережить его потерю. Подойдёт Yandex
Object Storage контура или нужен другой?

В бакете будут персональные и коммерческие данные (правки пользователей, полные образы строк), поэтому:
1. **Отдельный закрытый бакет** — не общий с документами, без публичного доступа.
2. **Отдельная сервисная учётка** с минимальными правами: запись и чтение только своего префикса,
   **без права удаления**.
3. **Шифрование** — серверное с ключами KMS, если оно есть; иначе шифруем сами (AES-256-GCM), ключ — в
   секрет-хранилище контура. Кто управляет ключами и их ротацией?
4. **Защита от удаления** — versioning и Object Lock (или равноценное).
5. **Журнал доступа** к бакету.
6. **Условная запись** `If-None-Match: *` — поддерживается ли и атомарна ли при одновременных записях.
   Мы проверим это сами на стенде, но просим подтвердить.

Удаление старых объектов — не правилом lifecycle вслепую, а нашим заданием и только после появления
более нового проверенного дампа.

Документы портала сейчас лежат в S3 cloud.ru (бакет `osp`) и в рамках переезда остаются там.
