# Портал ОСП на общем сервере — Docker

Сайт, свой API (`osp-api`) и PostgREST работают на сервере, где рядом живут другие проекты. Это новый
портал с базой Яндекса, адрес — `tender.su10.ru` (сервер corp, 213.171.26.249); прежний портал на Supabase
(`osp.root.sx`) работает на своём сервере как прежде. Порядок переноса данных — `migration/CUTOVER.md`.

```
браузер ──HTTPS──▶ общий nginx сервера (infra-nginx, запись <имя сайта>.conf)
                        │ сеть общего nginx
                        ▼
                  osp-web — nginx с сайтом и правилами /api          ┐
                        │ внутренняя сеть проекта                    │ проект Compose «osp»
                        ▼                                            │ /opt/portals/osp
                  osp-api ──▶ osp-postgrest ──▶ база Яндекса         ┘
```

- Портов на сервере проект не занимает: `osp-web` доступен только общему nginx по сети, `osp-api` и
  `osp-postgrest` — только внутри проекта.
- На сервере ничего не собирается: выпуск (образы и файлы установки) собирается на машине сборки.
- У каждого контейнера потолок памяти и процессора, журнал ограничен по размеру, запуск не от root,
  файловая система только на чтение.
- Проверяется целиком: `npm run test:deploy` (`tests/deploy/docker.test.mjs`).

## Соседние проекты не должны быть задеты — требование владельца портала

На сервере работают другие порталы. Ни один из них не должен почувствовать ни установку, ни работу, ни
остановку ОСП. Проверять это нужно не по тому, «что мы делаем», а по тому, через что соседи могут нас
почувствовать: общая сеть и имена в ней, общий nginx, процессор, память, диск, общие журналы.

| Через что могло бы задеть | Почему не заденет | Чем проверяется (`tests/deploy/docker.test.mjs`) |
|---|---|---|
| Имена в общей сети Docker | Docker делает имя службы именем в каждой сети, куда она подключена. Службы ОСП называются `osp-web`, `osp-api`, `osp-postgrest` — общих имён вроде `web` или `api` у них нет, и обращается ОСП только к своим именам | рядом стоят «соседи» с именами `web` и `api`: их запросы в ОСП не попадают, запросы ОСП — к ним |
| Общий nginx | запись ОСП — отдельный файл на имя, в нём только блоки `server` этого имени; ставит его `infra-nginx/install.sh`: проверка настроек до перечитывания, при отказе прежнее состояние возвращается само; контейнер не перезапускается | негодная запись откатывается, сайт соседа всё это время отвечает, чужая запись не меняется |
| Остановленный ОСП ломает общий nginx | имя контейнера сайта ищется при запросе, а не при запуске: общий nginx запускается и перечитывает настройки и без контейнеров ОСП; 502 получает только сайт ОСП | проверка настроек и перечитывание без контейнеров портала |
| Процессор | потолки в сумме — одно ядро; приоритет вдвое ниже обычного: при нехватке соседи получают процессор первыми | сумма потолков и приоритет у каждого контейнера |
| Память | потолки в сумме — 0,8 ГБ, без подкачки | сумма потолков |
| Диск и журналы | журнал каждого контейнера — не больше 50 МБ; в общий журнал nginx запросы ОСП не пишутся; старые выпуски и их образы убираются | запросов портала в журнале общего nginx нет |
| Выкладка трогает чужое | `deploy.sh` работает только с проектом Compose `osp` и образами `osp-api` / `osp-web` своих меток; первая установка отказывает, если проект, том или сеть с таким именем уже есть | соседний контейнер и общий nginx не перезапускались; установка поверх чужого — отказ |
| Сосед дотягивается до API или PostgREST | они только во внутренней сети проекта | из общей сети запрос не проходит |

**Что ОСП создаёт на сервере:** каталог `/opt/portals/osp`; образы `osp-api:<метка>`, `osp-web:<метка>` и
PostgREST; проект Compose `osp` — три контейнера, сеть `osp_internal`, том `osp_www`; по одному файлу
`<имя сайта>.conf` в каталоге записей общего nginx и сертификат этого имени.

**Чего ОСП не делает:** не использует sudo; не меняет настройки Docker и системы; не выполняет общих команд
(`docker system prune`, остановка всех контейнеров, удаление томов); не открывает портов на сервере; не
перезапускает общий nginx; не правит и не удаляет чужие записи, сертификаты, каталоги и контейнеры.
Сертификат выпускается только для своего имени — общего продления (`certbot renew`) ОСП не запускает.

Проверка по факту — до и после каждого действия на сервере (только чтение):
```bash
bash neighbors.sh --save       # снимок: чужие контейнеры, внешние порты, память, диск
bash neighbors.sh --compare    # все на месте, работают, не перезапускались, образы прежние
```
`FAIL` — остановка и разбор до любых дальнейших действий.

Что остаётся риском: свободной памяти на сервере немного, и ОСП больше своих потолков не возьмёт, но если
память кончится у сервера в целом, система сама выбирает, какой процесс остановить. Потолки ОСП можно
ужать или поднять в `/opt/portals/osp/compose.server.yml` — по наблюдению за настоящей нагрузкой.

## Сборка выпуска — на машине сборки

```bash
bash deploy/docker/build.sh            # → deploy/docker/out/osp-release-<коммит>/
```
Собирается только из закоммиченного. Нужен файл `~/.osp-secrets/web-build.env` с двумя строками —
`VITE_SUPABASE_URL=` и `VITE_SUPABASE_ANON_KEY=` (те же, с которыми сайт собирался раньше; это публичные
значения, но на экран их не выводят). Каталог выпуска переносится на сервер целиком; после переноса —
`sha256sum -c SHA256SUMS` в нём (то же самое делает `deploy.sh install`).

На общем сервере образы портала не собираются, даже если соседние проекты собирают свои там же: сборка
сайта требует 1–2 ГБ памяти и отняла бы её у соседей.

## Первая установка на сервере

Пользователь — владелец `/opt/portals` (на сервере corp — `corpsu`). Значения ключей на экран не выводить.

1. **Каталог портала и снимок соседей:** `mkdir -p /opt/portals/osp/{secrets,certs,shared,state}`, затем из
   каталога выпуска — `bash neighbors.sh --save`.
2. **Настройки** (права 600) — те же файлы, что готовит `migration/target/server-env.sh`:
   - `secrets/postgrest.env` — как есть;
   - `secrets/osp-api.env` — ключи из `server/osp-api/osp-api.env.example` и строки шлюза из `osp-api.add.env`.
     Адреса внутри проекта (`OSP_PGRST_URL`, путь к сертификату, файл барьера) задаёт `compose.yml`.
3. **Сертификат базы** (не секрет): `certs/yandex-root.crt` — `https://storage.yandexcloud.net/cloud-certs/CA.pem`, права 644.
4. **Сеть общего nginx:** `server.env` со строкой `OSP_PROXY_NETWORK=<имя сети, в которой работает infra-nginx>`
   (на сервере corp — `edge`).
5. **Установка** — из каталога выпуска: `bash deploy.sh install .`. Скрипт сверяет
   контрольные суммы и отпечатки образов, поднимает проект и проверяет готовность. Не прошла — проект
   остановлен, причина в журналах.
6. **Сравнение с соседями:** `bash neighbors.sh --compare`.

Запись в общем nginx — отдельным действием, см. ниже; до неё портал снаружи не виден.

## Запись в общем nginx: имена сайта и сертификаты

Общий nginx сервера corp — контейнер `infra-nginx` (проект в `/opt/infra/nginx`): записи сайтов —
`/opt/infra/nginx/conf.d`, сертификаты Let's Encrypt — `/opt/infra/nginx/certbot/conf`
(`/etc/letsencrypt` в контейнере), каталог проверки — `/opt/infra/nginx/certbot/www` (`/var/www/certbot`).
У каждого имени сайта — своя запись и свой сертификат, как у соседних проектов.

Запись на одно имя ставит `infra-nginx/install.sh` — **в два шага**, потому что блок HTTPS ссылается на
сертификат, которого сначала нет:

```bash
# corpsu@corp$ — из каталога выпуска; ИМЯ — имя сайта
bash neighbors.sh --save
bash infra-nginx/install.sh ИМЯ --http-only    # шаг 1: запись «только HTTP» с адресом проверки Let's Encrypt
# Сертификат ИМЕНИ — тем же способом, каким выпущены сертификаты соседних сайтов (проверка через каталог
# /var/www/certbot), и только для этого имени.
bash infra-nginx/install.sh ИМЯ                # шаг 2: полная запись
bash neighbors.sh --compare
```
Что делает скрипт: до изменений убеждается, что настройки общего nginx годны (иначе не трогает ничего);
отказывает, если имя уже есть в чужой записи; кладёт файл и проверяет настройки; не прошли — возвращает
прежнее состояние и проверяет ещё раз; перечитывает настройки только после успешной проверки, без
перезапуска контейнера. Убрать запись: `bash infra-nginx/install.sh ИМЯ --remove`.

Имена подключаются по очереди:

1. **Запасное имя** `osp.213-171-26-249.nip.io` — уже указывает на corp. Под ним проверяются сайт, вход,
   чтение и `?features=ospDb`. Загрузка файлов под ним не работает: CORS бакета cloud.ru его не разрешает.
2. **Имя сайта** `tender.su10.ru` — когда запись DNS указывает на 213.171.26.249 (как у соседних порталов
   `*.su10.ru`): те же два шага и сертификат только на это имя. Для загрузки файлов в CORS бакета cloud.ru
   добавляется `https://tender.su10.ru` (прежние адреса остаются — с них работает прежний портал).

Продление сертификатов — забота общего nginx сервера: у записи портала тот же адрес проверки, что у соседей.

## Обычная выкладка, возврат, состояние

```bash
bash <каталог выпуска>/deploy.sh install <каталог выпуска>   # новый выпуск
bash /opt/portals/osp/deploy.sh status                       # что выложено и отвечает ли
bash /opt/portals/osp/deploy.sh rollback                     # вернуть предыдущий выпуск
```
Каталог портала по умолчанию — `/opt/portals/osp` (`OSP_HOME`). После установки `deploy.sh` и `neighbors.sh`
выпуска лежат в нём.

## Обложки объектов: копирование из Supabase в cloud.ru

```bash
# corpsu@corp$ — список обложек из копии прода (migration/backup/backup.sh), права 600
bash /opt/portals/osp/deploy.sh covers-copy ~/<копия>.covers.csv
```
Внутри — `node src/covers-copy.js` в образе выложенного выпуска с ключами из `secrets/osp-api.env`
(`docker compose run --no-deps`: работающие контейнеры портала не трогаются). Каждая обложка скачивается по
общедоступному адресу Supabase, кладётся в cloud.ru `covers/<имя>` и скачивается обратно для сверки SHA-256.
Supabase только читается; в cloud.ru только добавляются объекты `covers/…`, лежащий там другой файл не
перезаписывается; повторный запуск загружает лишь то, чего ещё нет. Журнал (без секретов) —
`/opt/portals/osp/covers/journal-<время>.json`, его берёт `migration/target/load.sh --covers`. Выход 4 — не
все обложки сверены (причины на экране), журнал всё равно записан.
Выпуск, не прошедший готовность, возвращается на прежний сам. Сайт отдаётся из тома: файлы прежних
сборок сохраняются, открытые вкладки не ломаются (тот же `deploy/publish.sh`, что раньше).

## Флаги и барьер записи

- Флаги портала — `/opt/portals/osp/shared/config.json`; правятся без пересборки, открытые вкладки
  перечитывают их в течение двух минут.
- Барьер записи: `touch /opt/portals/osp/state/db-readonly` — запись через шлюз и загрузка, подтверждение и
  удаление файлов закрыты, чтение работает; снять — `rm`.
- Готовность: `bash /opt/portals/osp/deploy.sh status` — в ответе `data`: `rehearsal` (за шлюзом
  проверочная копия) или `final` (рабочая).
- PostgREST перечитывает описание структуры базы после новой загрузки:
  `docker compose -p osp kill -s SIGUSR1 osp-postgrest`.
