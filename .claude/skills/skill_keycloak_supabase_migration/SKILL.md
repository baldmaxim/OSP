# Портал с Supabase → общий кластер PG + вход через Keycloak su10

Подставляй `<portal>` (client-id портала в Keycloak, латиница, напр. `docflow`) и `<portal-domain>`
(напр. `docflow.su10.ru`). Детали — в `references/`, этот файл — порядок работы и правила.

> Если в репозитории есть и `skill_keycloak_universal`: при расхождениях приоритет у этого skill —
> он актуален для порталов, переезжающих с Supabase.

## Кто что делает

| Сторона | Зона ответственности |
|---|---|
| **Команда портала** (этот репозиторий) | инвентаризация Supabase, перенос схемы и данных, backend OIDC/BFF, выгрузка **списка учёток** для auth, применение **файла сопоставления**, проверки, окно переключения |
| **Команда auth** (репо auth, realm su10) | клиент `<portal>` в Keycloak и роль `<portal>:access`; **сопоставление учёток портала с Keycloak и все решения по ним**; заведение недостающих учёток с прежним паролем; выдача доступа; файл сопоставления |
| **Владелец кластера PG** | база `<portal>_db`, роли, лимиты соединений, расширения |

Портал **не решает**, какой учётке Keycloak принадлежат прежние данные: он отдаёт данные и применяет
решения auth.

## Инварианты (нарушать нельзя)

1. **Секреты и персональные данные не выводить в чат и не коммитить.** Это client secret, пароли БД,
   ключи Supabase (`service_role`, JWT secret), bcrypt-хэши, открытые выгрузки списка учёток и файла
   сопоставления, дампы БД, пароли шифрования. Оперировать именами переменных; проверять наличие и длину,
   не значение. Каталог с выгрузками и дампами — в `.gitignore`.
2. **Внутренний id пользователя = прежний `auth.users.id` из Supabase, навсегда.** Не перегенерировать, не
   заменять на `sub` Keycloak, не переписывать `created_by` / `owner_id` / FK. `sub` живёт только в таблице
   связей. Единственное исключение — одобренный человеком перенос владения по `duplicate_of`.
3. **Портал не сопоставляет учётки по email.** Связь «пользователь портала ↔ `sub`» появляется только из
   файла сопоставления от auth или при создании нового пользователя (JIT). Email в токене используется
   лишь чтобы **не** создать пустой дубль прежнему пользователю (ответ 403 `pending_mapping`).
4. **В Supabase только чтение** (read-only транзакции), кроме согласованных шагов заморозки в окне.
   Скрипты записи проверяют, что цель — не Supabase.
5. **Realm не настраивать.** Клиенты, роли, мапперы и пользователи Keycloak — заявкой команде auth
   (`references/05-auth-handoff.md`). Admin API Keycloak порталу не нужен и не выдаётся.
6. **Любая запись в прод-БД — сначала `--dry-run` с отчётом.** Скрипты миграции идемпотентны.
7. **Стоп-точка = явное «да» человека.** Без него к следующему шагу не переходить.
8. **Не требовать `email_verified=true` при входе:** у сотрудников, импортированных из ФОТ, он `false`
   у всех. Допуск определяют роль `<portal>:access` и связь в БД портала.
9. **TLS к БД — только с проверкой CA** (`verify-full`). `rejectUnauthorized:false` не использовать.

## Факты контура su10 (цель интеграции)

- issuer `https://auth.su10.ru/realms/su10` (Keycloak 26.1), discovery —
  `…/.well-known/openid-configuration`. На `auth.su10.ru` из Keycloak доступны только `/realms/*`,
  `/resources/*`, `/js/*`; Admin API там не отвечает (вернётся HTML витрины с кодом 200).
- **Пользователи.** ~1600 сотрудников импортированы из ФОТ (кадровая система). Их `sub` = id в ФОТ,
  `username` = `email` в нижнем регистре, пароль — **пароль ФОТ**, `email_verified=false`.
- **Учётками управляет auth.** Email меняет только администратор. Самостоятельной регистрации нет.
  SMTP нет: подтверждения почты и самостоятельного сброса пароля нет, пароль сбрасывает админ auth.
- **Пароли.** Минимальная длина 8. После 10 неудачных попыток вход блокируется на время, до 15 минут.
- **Клиенты порталов.** Confidential, PKCE S256, точные redirect URI (`/api/auth/oidc/callback`),
  audience-маппер `aud=<portal>`. Допуск — client-роль `access`: claim `resource_access.<portal>.roles`
  в access token. Бизнес-роли и профиль портал держит у себя.
- **Сроки жизни.** Access token — Keycloak по умолчанию (5 минут), продлевается через refresh token.
  Сессия общая для всех порталов (SSO).
- **БД.** Общий кластер — Yandex Managed PostgreSQL. Подключение через пулер Odyssey (порт 6432,
  transaction mode), TLS с CA Яндекса. Роли и расширения заводит владелец кластера.

## Порядок работы

Переезд идёт в **две фазы со своим откатом**:
- **A** — перенос БД, вход пока через Supabase Auth;
- **B** — переключение входа на Keycloak.

Объединять фазы в одно окно можно только по решению человека: откат тогда сложнее.

### Фаза 0. Инвентаризация и решения → `references/01-inventory.md`
Собрать, что из Supabase реально используется: supabase-js из браузера, RLS и `auth.uid()`, FK на
`auth.users`, триггеры, Storage, Realtime, Edge Functions, cron, расширения. Плюс статистика
пользователей. Результат — `migration/inventory.md` без персональных данных.

**СТОП 1:** показать инвентаризацию человеку и зафиксировать решения:
- RLS — сохранить через прослойку `auth.uid()` (по умолчанию) или перейти на проверки в приложении;
- судьба Storage, Realtime, Edge Functions;
- две фазы или одно окно;
- список колонок-владельцев (по ним считаются «записи пользователя»).

### Фаза 1. Заявки → `references/02-db-move.md` §1, `references/05-auth-handoff.md` §2
- **Владельцу кластера:** база, роли `<portal>_migration` / `<portal>_runtime`, лимиты соединений,
  расширения.
- **Команде auth:** клиент `<portal>` (прод и стенд), роль `access`, плитка в витрине, даты обоих
  раундов сопоставления.

### Фаза 2. Свой backend вместо прямых обращений к Supabase → `references/04-oidc-bff.md`
Managed PG не даёт PostgREST: браузер больше не ходит в БД. Все обращения переводятся на API портала.
Удобно поэтапно, через слой репозиториев. Каждый запрос к БД выполняется в транзакции с
`set_config('app.user_id', <внутренний id>, true)`. В фазе A backend принимает JWT Supabase (`sub` и есть
внутренний id).

### Фаза 3 (A). Перенос БД → `references/02-db-move.md`
Порядок:
- фильтр схемы;
- таблица `users` вместо `auth.users` с теми же id;
- прослойка `auth.uid()`;
- restore без суперпользователя;
- сверка `count(*)` по всем таблицам.

Сначала репетиция на стенде, затем окно.

**СТОП 2:** перед окном фазы A — отчёт репетиции и план отката.

### Фаза 4. Список учёток → auth, файл сопоставления → портал (репетиция)
→ `references/03-identity-mapping.md`, `references/05-auth-handoff.md`
- **Выгрузка.** Из Supabase `auth.users` (+ профили, число записей у каждого) собрать список
  `su10-portal-users` и зашифровать его. Наружу выводятся только счётчики.
- **СТОП 3:** человек проверяет счётчики и передаёт файл команде auth. Пароль шифрования — отдельным
  каналом.
- **Ответ auth.** Auth сопоставляет учётки, заводит недостающие и выдаёт доступ. Порталу возвращается
  файл `su10-portal-mapping`.
- **Проверка на стенде.** `apply-mapping --dry-run` на стенде → отчёт: конфликты, «записи под
  риском». Вопросы по конфликтам — команде auth, она выпускает новую версию файла.

### Фаза 5 (B). Окно переключения входа → `references/06-cutover.md`
1. Заморозка регистраций и смены паролей в Supabase.
2. Финальный список учёток → auth → финальный файл сопоставления.
3. `apply-mapping --dry-run` → **СТОП 4** → `apply-mapping`.
4. Проверка покрытия.
5. `AUTH_MODE=keycloak`.
6. Смоук по каждому классу решений.

**СТОП 5:** решение об откате, если смоук не прошёл.

### Фаза 6. После переключения → `references/06-cutover.md` §«После»
- Мониторинг 403 `pending_mapping`: список уходит в auth, оттуда приходит новая версия файла
  сопоставления.
- Отложенные решения.
- Supabase живёт не меньше 30 дней только на чтение. Режим `supabase` и его код убираются после
  решения человека.

## Чек-лист «запросить у команды auth»
- [ ] Клиент `<portal>`: redirect URI прода и стенда, post-logout, web-origins.
- [ ] Роль `<portal>:access`, audience-маппер, маппер `resource_access.<portal>.roles`.
- [ ] Client secret — защищённым каналом, в env портала.
- [ ] Плитка портала в витрине `auth.su10.ru`.
- [ ] Сроки обработки репетиционного и финального раундов; длительность окна на их стороне.
- [ ] Канал передачи зашифрованных файлов и паролей к ним.
- [ ] Тестовые учётки для смоука на стенде.

## Частые ошибки
- Переписать `created_by` / `owner_id` на `sub` Keycloak: ломает историю, а при пересоздании учётки
  в Keycloak доступ теряется снова.
- Сделать первичным ключом `sub` или связывать по email «для удобства». Решения о совпадении принимает auth.
- Создать нового пустого пользователя тому, кто ждёт сопоставления: потом его данные «не видны».
  Лечится только ручным переносом.
- Сказать сотрудникам «входите со старым паролем». У тех, кто есть в ФОТ, пароль — **от ФОТ**.
- `pg_restore --disable-triggers` и `session_replication_role` на managed PG: нужен суперпользователь,
  restore выйдет частичным.
- Prepared statements и session-`SET` через пулер 6432 в transaction mode.
- Заменить в RLS `auth.uid()` на `sub` из токена. В `app.user_id` всегда кладётся **внутренний** id.
