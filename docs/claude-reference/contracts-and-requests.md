# Contracts And Requests — проектный справочник

> **Справочник, а не инструкция постоянной загрузки.** Ниже сохранено исходное описание проекта, включая историю решений и возможные устаревшие варианты. При противоречии ориентироваться на текущий код, миграции, тесты, новую задачу и корневой `CLAUDE.md`.

## Заявка на заключение ДП (миграции 20261227, 20261231; обе базы)

**С 19.11.2026 (миграция 20270219)** раздела `/dp-requests` нет: заявка на заключение ДП — карточка доски «Заявки на проверку
ДП/ДС» (`doc_check_requests.doc_type = 'dp_conclusion'`), подают кнопкой «+ Заявка на заключение ДП» реестра договоров и формой
доски; описание раздела ниже — история. **Тендер** (миграция 20270221, обе базы; решение пользователя 19.11.2026 — «привязка к
тендеру должна быть», «не обязательна»): `doc_check_requests.tender_id` (ON DELETE SET NULL), поле «Тендер (необязательно)» только
у «Заключения ДП» — у подающего при создании и у отдела в правке; выбор как в форме договора (`tenderChoices`: тендеры объекта
без тендеров на материалы, колонки — те, что шлюз отдаёт с правом «Договоры»), выбранный подставляет пустые объект и победителя.
В окне заявки — строка «Тендер» (ссылкой на карточку при праве «Тендеры»; без права читать тендеры — «тендер указан»), смена — в
истории (триггер `doc_check_requests_tender_history`). Шлюз: `tender_id` — в колонках вставки подающего (`db-sections.json`),
менять — только с правом правки доски. До миграции поля нет: выборка доски с `tender_id` — верхняя ступень `DOC_CHECK_SELECTS`,
кнопка реестра проверяет колонку (`hasTenderColumn`). Большое окно получателей (`dp_request_my_alerts`) тендер не показывает.

**Договор в реестре и окно исполнителю (миграция 20270225, обе базы; решение пользователя 23.11.2026** — «заявка на заключение
ДП со статусом в работе … автоматически создавалась в /contracts/registry, и большое уведомление … у ответственного при его
назначении»; уточнено: ответственный — исполнитель заявки на доске, окно — только «Заключению ДП», заявкам, уже стоящим «В работе», —
договор, «если их ещё нет»). Договор создаёт **база**, а не страница: триггер `doc_check_dp_conclusion_contract` на доске
(перетаскивание, окно, форма — один путь) вызывает `dp_conclusion_contract_create`, когда «Заключение ДП» входит в «В работе»
(или уходит из «Новых» сразу дальше, или создано не в «Новых»). Договор подряда: статус `in_work`, объект, контрагент (+
`contract_counterparties`), тендер — из заявки, «Принят в работу» — сегодня по Москве, примечание «Из заявки «Заключение ДП» ID N» +
примечание заявки, **номер пуст** (кнопка «Подставить» в форме договора), файлы остаются в заявке, ответственный юрист реестра не
ставится. Связь — `contracts.doc_check_request_id` (уникальна, ON DELETE SET NULL): одна заявка — один договор, возврат в «Новые»,
переходы дальше и удаление заявки договор не трогают. История: «Создание» в договоре (автор — переводивший), `contract_created`
(«Договор в реестре») в заявке. Дописка при выкладке — только заявкам «В работе» без похожего договора (тот же объект и контрагент,
внесён не раньше дня подачи); пропущенные потом договора не получают. Окно исполнителю: `doc_check_assign_alerts` заводит триггер
`doc_check_assign_alert` при добавлении в `assignee_ids` (сам себя — нет; снят до прочтения — убирается; назначен снова — окно снова);
`doc_check_assign_my_alerts` / `doc_check_assign_alerts_ack` — в шлюзе любому сотруднику, отдают только своё и пока он исполнитель.
Показывает то же окно `DpRequestAlert` (одно окно на оба повода, две части), опрашивает только роль `lawyer`; функций нет — молчит до
перезагрузки. Тесты: `tests/tender/dp-conclusion-registry-db.test.mjs`, `tests/tender/dp-requests.test.mjs` (стенд `dpAssigned=N`,
`dpAssignMissing=1`).

**Короткая форма подающего** (05.11.2026, позже в тот же день, решение пользователя; заменяет прежнее «документ договора обязателен» и «поля заполняет автор»): кто оставляет заявку, заполняет только понятийное соглашение (обязательно), документы (необязательно) и примечание; «всё остальное мы заполняем» — объект, договор, сумму и ответственного вносит работающий с заявками, частями, по мере готовности, обязательных полей у него нет. Примечание необязательно — моё толкование: в словах пользователя пометки о нём нет. Запрет на статус при незаполненных полях не ставили: об этом не просили.

- **Объект подающего** (06.11.2026, решение пользователя; миграции нет): подающий, привязанный к объектам в «Ролях» (`object_ids`; рукстрой, экономист объекта), сам указывает объект — поле «Объект» первым в окне новой заявки. Один объект — стоит сам, серым, без выбора; несколько — выбор обязателен («выберите объект»), в списке — только свои (отбор `id` в запросе); без привязки — поля нет, как раньше. Правила — `ownObjectChoice` в [dpRequests.js](src/utils/dpRequests.js). Только при создании: объект поданной заявки меняет отдел (`dp_work_fields`), правило вставки `dp_requests_insert` пропускает только свои объекты. Тесты — «подающий с двумя объектами» и «с одним объектом» в `tests/tender/dp-requests.test.mjs` (стенд `scope=obj-1,obj-2`).
- **Автор не перепишет поля отдела — запрет в базе** (`dp_requests_guard`, `42501`, `dp_work_fields`): правка объекта, договора, суммы и ответственного без права работы — отказ (в том числе из старой вкладки с полной формой; те же значения — не правка). При создании поля не запрещены: старая вкладка шлёт их сама. Снять контакт можно: удаление контакта (`ON DELETE SET NULL`) делает сотрудник без права на раздел, и эта правка проходит через тот же триггер.
- **Заявка без объекта и привязка к объектам:** автор с `object_ids` подаёт её и видит свою всегда; работающий с заявками, привязанный к объектам, видит и правит заявку без объекта (иначе она не дойдёт до того, кто заполнит), объект ставит только свой; просмотр с привязкой видит её, когда объект заполнен.
- **Незаполненное не показываем нулём:** в реестре работающему — «не заполнено», остальным — «—»; в большом окне незаполненных строк нет. Столбец с причиной теперь «Примечание» (колонка прежняя, `reason`), документы — категория прежняя (`dp_contract_doc`), в них допустим ещё и Excel, у соглашения — нет.

- **Права — два раздела:** `dp_requests` (просмотр — реестр; правка — работа с заявками: статус, правка и удаление любых; по умолчанию `superuser`, администратор — всегда) и `dp_requests_create` (правка — создавать по своим объектам и править свои, пока статус «Новая»; по умолчанию `economist_object` и `construction_manager`, у обоих ещё просмотр реестра). Кому ещё — галочками в «Правах доступа». Сотрудник с `object_ids` видит и создаёт только по своим объектам — в правиле базы, а не только на странице (`dp_request_scope()`). `economist` («Экономист ОСП») — другой человек, прав по умолчанию нет.
- **Понятийное соглашение обязательно — запрет в базе.** Файл можно загрузить только к существующей строке, поэтому заявка — черновик (`status = 'draft'`, видит только автор), затем файлы, затем `status = 'new'`: на этом переходе триггер `dp_requests_guard` требует файл `doc_category` `dp_concept_agreement` (`P0001`, `dp_concept_agreement_required`), ставит постоянный `request_number` (своя последовательность, у черновика пусто). Сбой посреди создания — черновик и загруженное убираются (`createDpRequest`). Последний файл соглашения у поданной заявки не убрать, в том числе сменой категории (`s3_documents_dp_request_guard`, `dp_required_file_last`); на странице вместо удаления — «заменить» (новый файл, затем прежний); документы убираются свободно. Там же граница прав на файлы: `WRITE_RULES` не отличает свою заявку от чужой, отличает триггер.
- **Файлы** — `s3_documents`, `owner_type = 'dp_request'`, `doc_category` `dp_concept_agreement` или `dp_contract_doc`; новый тип владельца — и в osp-api, и в Edge Function `s3-presign` (прежнему порталу нужен её редеплой).
- **Ответственный** — `responsible_contact_id` + ФИО слепком `responsible_name` + `responsible_role`. В списке — люди объекта из `object_staff`; никого нет — такие люди других объектов с пометкой; сам вошедший, если его роль подходит, а в списке его нет (на копии 02.11 у 3 из 8 руководителей строительства нет карточки в «Контактах»): тогда контакта нет, только ФИО. У контакта ФИО ставит триггер.
- **Большое окно** — [DpRequestAlert](src/components/dpRequests/DpRequestAlert.jsx) в `EmployeeLayout` (на всех страницах, свои стили, `z-index` 3000). Уведомление — строка `dp_request_alerts` на получателя (заводит триггер при подаче, один раз), поэтому кто был не на сайте, увидит при входе. Сведения — из функции `dp_request_my_alerts()`, окну не нужно право на раздел; гасит `dp_request_alerts_ack` (только свои); саму таблицу вошедшим не выдаём. ## Окно заявки ДП/ДС: скриншоты и скорость (13.11.2026, без миграции)

Просьба пользователя: «добавь скриншоты в чат (обсуждение) в /doc-check-requests и оптимизируй окно заявки — медленно открывается и
подлагивает». Скриншоты работают только с миграцией 20270216 (файлы в переписке, `hasChatFields`); до неё переписка — без файлов.
- **Скриншоты** ([DocCheckDiscussion](src/components/doccheck/DocCheckDiscussion.jsx)): Ctrl+V в поле сообщения и в любом месте окна (не в
  другом поле ввода), кнопка с картинкой — `navigator.clipboard.read` (браузер спросит разрешение). «image.png» из буфера →
  `screenshotFileName` («Скриншот 13.11.2026 14-05-33.png», в сообщении без повторов). Есть текст в буфере — вставляется текст (Excel кладёт
  рядом картинку ячеек). Картинки в сообщении — миниатюры постоянного размера (ссылка — когда видна, на 10 минут в памяти), нажатие — во весь
  экран; выбранные — маленькими у поля.
- **Скорость** (замер — боевая сборка стенда, 850 заявок, 40 сообщений, процессор ×4): набор текста перерисовывал всю переписку, а время
  сообщений считалось `toLocaleTimeString` с параметрами (~50 мкс на вызов, 80 вызовов на букву) — сообщения теперь `TalkMessages` (memo),
  даты — общими форматтерами (`formatDateTimeRu`, `fmtDocDate`, `createdShort`, `fmtDocDateTime`, строки те же); поле ввода при росте текста
  высоту не сбрасывает. Подсказка поля — короткая: пустое поле браузер меряет по ней, длинная давала поле в две строки. Файлы окна читались дважды (второй раз — когда приходила переписка) — теперь только если отправленного файла нет в
  списке. Чтение переписки и файлов начинается при нажатии кнопки мыши на заявке (`prefetchCard` / `takePrefetched`, ответ годен 15 с и берётся
  один раз). React при наборе: 88 → 9 мс на 17 букв; открытие: 610–1060 → 400–770 мс (×4).

## Signal: состояния в реестре и карточке (миграция 20270228, только база Яндекса)

Служба и маршруты — `server/osp-api/README.md`, «Интеграция SIGNAL». Браузер ходит только в `/api/signal/*` (`src/api/signal.js`), в SIGNAL — никогда; ссылку `signal_link` меняет только решение человека.

- **Значок** ([DocLinkMarks](src/components/DocLinkMarks.jsx), `DocLinkMarks.css`): красный — ссылки нет; **красный с синей точкой** — предложена папка; **зелёный** — ссылка есть (сверено или не сверялась);
  **жёлтый «!»** — противоречие, папка не видна, файл удалён. Подпись — в `title` и `aria-label`, строит её сервер (путь предложенной папки — только при праве правки). Метка, не сходящаяся со ссылкой, не показывается.
  Нажатие на значок с точкой или «!» при праве правки открывает окно сверки, иначе — как раньше.
- **Фильтр «Сверка Signal»** — один переключатель с числом (право правки): предложение, противоречие, папка не видна, файл удалён. Метки — `signal.allMarks()`; фильтр действует на документы **до построения дерева**
  (`registryRows(…, { only })`): ДС с замечанием остаётся под договором, договор без замечаний — один раз ради него; число — по документам, ждущие пересчёта не входят.
- **Окно сверки** ([SignalReviewDialog](src/components/SignalReviewDialog.jsx), в `<body>`): «Подтвердить», «Заменить на предложенную» / «Оставить текущую», «Другая папка…», «Отклонить», «Позже»,
  «Запомнить … как название объекта». Действие уходит с `expectedStateVersion`, `expectedSignalLink` (CAS) и ключом идемпотентности; устарело — 409 «Данные изменились — откройте сверку заново». Без `SIGNAL_UI_FOLDER_URL` «Подтвердить» нет.
- **После сохранения (Р8)** документа или ссылки `signal.match` по снимку (≤ 3 с, сохранение не ждёт): папка найдена или есть замечание — сообщение под панелью фильтров («Сверить» / «Позже»), от фильтра не зависит; иначе без сообщения.
- **Итог импорта (Ф5)** — строка окна результата «Signal: сверено или найдено N · требуют внимания M · ожидают сверки K»: три непересекающиеся группы по уникальным id созданных документов (порции по 200, ≤ 5 с; сбой — «ожидают»), разбивка — в `title` ([signalReview.js](src/utils/signalReview.js)).
- **Карточка** ([SignalPathRow](src/components/SignalPathRow.jsx), [signalPathRow.js](src/utils/signalPathRow.js)): «Путь к Signal» — путь папки, состояние текстом, «Сверить…» и «Отвязать» (право правки), свёрнутый список файлов (имя, версия, дата, «↗» при `SIGNAL_UI_FILE_URL`).
  **Телефон:** в карточке реестра значков нет — кнопка `.dlm-card` (право правки), окно сверки на весь экран.
- **Вкладка «Signal»** в «Администрировании» ([SignalTab](src/components/admin/SignalTab.jsx)) — только администратору при `status.enabled && isAdmin`: подключение, корни и объекты, обход, журнал, синонимы, папки без объекта; принять `held` — только CLI.
- **Без интеграции** (`status` → `{ enabled: false }`: выключена, нет схемы или права, сервер недоступен): ни меток, ни переключателя, ни окна, ни вкладки; значки прежние, в карточке `SignalLinkCell`, у импорта нет строки итога.
- Тесты — `tests/contracts/signal-review.test.mjs`, стенд (Chromium) `tests/tender/contracts-signal`, `contracts-import-signal`, `contract-card-signal`, `admin-signal`, база и сервер — `tests/db/signal-migration.test.mjs`, `tests/osp-api/signal-*.test.mjs`.

## Нумерация договоров по объектам (миграция 20270110, обе базы)

Решение пользователя 10.11.2026 по файлу «Нумерация_договоров_по_объектам.xlsx»: при создании договора номер генерируется, но его можно заполнить самому.
Формат — `КОД ОБЪЕКТА-ДП-ГГ-НОМЕР` (`АЛИЯ-ДП-26-001`): счётчик на объект и год, общий для всех подрядчиков; в новом году — с 001; номер отменённого договора повторно не выдаётся; ДС нумеруются внутри договора — генератор их не касается.
Правила — [contractNumbering.js](src/utils/contractNumbering.js), запросы — [services/contractNumbering.js](src/services/contractNumbering.js).

- **Форма нового договора** (ContractsPage, поле «№ договора»): номера нет, пока не выбран объект; выбран — следующий номер объекта по счётчику, смена объекта его меняет. Набранный (или стёртый) номер форма больше не трогает (`numberManual`); «Подставить …» возвращает номер по схеме. Договор без номера по-прежнему можно сохранить. У объекта нет кода — поле пустое, подсказка про «Нумерацию договоров». У ДС поле прежнее. При правке договора номер сам не подставляется, кнопка «Подставить» — если номер не по схеме своего объекта.
- **Ручной номер по схеме** — одно окно подтверждения (`manualNumberWarnings`): код не своего объекта; не по порядку (какие номера останутся невыданными и с какого продолжится счётчик); меньше выданного. Номер не по схеме (старый вид, свой номер подрядчика) — без вопросов.
- **Уникальность — в базе:** индекс `contracts_scheme_number_uniq` по ключу `contract_number_key()` среди договоров (`record_type = 'dp'`, удалённые тоже): регистр, латиница-двойник (С/C, А/A…) и ведущие нули не различаются (`АЛИЯ-ДП-26-1` = `алия-дп-26-001`). Прочие номера, как раньше, могут повторяться. Подставленный номер успел взять коллега — страница берёт следующий по свежему счётчику и сохраняет снова, человеку — окно «присвоен …»; занятый ручной номер — отказ с ID договора, форма остаётся открытой. Импорт из Excel — та же причина в строке.
- **Счётчик** — `contract_number_counters` (код, год, последний номер): пишет только триггер `contracts_number_counter` при записи договора с номером по схеме, в том числе ручным; только растёт — удаление, переименование и окончательное удаление номер не освобождают. Ручной номер не по порядку двигает счётчик за собой (поэтому подтверждение). Читает сотрудник; страница берёт его перед каждой новой формой.
- **Коды объектов** — `objects.contract_code` (буквы, цифры, точка, дефис, до 20 знаков, без повторов с точностью до регистра и двойников). Начальные — 17 объектов ОС из файла, по id (в базе «ЖК Дом 56 Реновация» файла — «ЖК Реновация»). Меняет только администратор: «Документы» → «Нумерация договоров» ([ContractNumberingModal](src/components/ContractNumberingModal.jsx): правила, по строке на объект — код, последний номер года, следующий; карандаш в строке), в базе — триггер `objects_contract_code_guard` (42501). Смена кода — новые номера с новым кодом и своим счётчиком, выданные не меняются. Плитка — под `showSetup` (сотруднику объекта не показывается).
- **Год** — по Москве (`moscowYear`). Новый вид номера — правка обеих сторон ключа (функции базы новой миграцией и `contractNumbering.js`): их совпадение сторожит тест базы.
- Нет миграции — форма как раньше (прежний «следующий номер» по всему реестру), окно говорит, что нумерация не включена. Счётчик не прочитался из-за сети — номер не подставляется, следующая форма спросит снова.
- База Яндекса — `migration/yandex/20270110_contract_number_scheme.sql` (+ `.check.sql`), проверка — `migration/backup/checks/20270110.sql`, откат (Supabase; номера договоров остаются, коды и счётчики теряются) — `migration/rollback/20270110_contract_number_scheme_rollback.sql`. Миграция останавливается с перечнем, если номера по схеме уже повторяются. Порядок: `migrate`, затем `both` (список шлюза — в образе API); страница раньше миграции работает как прежде.
- Тесты — `tests/contracts/contract-numbering.test.mjs` (правила), `tests/tender/contract-numbering.test.mjs` (стенд `contracts=24&contractNumbering=1|legacy`; у `obj-1` код СЕВ), `contract-numbering-db.test.mjs` (слепок, ключи базы = страницы, копия под одной учёткой через `migrate.sh`).
