# Правила целевой схемы: все права проверяет API

Целевая архитектура портала: **браузер → API на Node → PostgreSQL**. Требования владельца портала от
2026-10-12; по ним принимается каждый раздел при переводе с Supabase. Порядок перевода и состояние —
`migration/PLAN.md`; каркас API — `server/osp-api/README.md`, раздел «Права на маршрутах».

## База
1. В клиенте нет supabase-js, PostgREST, Hasura, драйверов БД — ни в одном месте.
2. С базой соединяется только сервер. Строк подключения, паролей и ключей в клиентском бандле нет,
   включая `VITE_*`.
3. Подключение к базе разрешено сетевым правилом только с адресов приложения.
4. Роль приложения в базе — не владелец и не суперпользователь. Миграции — отдельной ролью.
   **Принятое исключение — см. ниже.**
5. RLS не используется, политики из Supabase удалены. Авторизации в базе нет.
6. API — операции предметной области. Маршрут, принимающий от клиента имя таблицы, поля, условия
   фильтрации или SQL, — это тот же прямой доступ к базе.

## API
7. Закрыто по умолчанию: маршрут без объявленных прав недоступен никому.
8. Права объявлены на маршруте (guard), а не только в теле обработчика.
9. Маршруты без авторизации — короткий именной список с обоснованием.
10. Личность и роль — из подписанного сервером токена. Роль, организация, авторство, цены из тела запроса,
    заголовков и `localStorage` не принимаются.
11. Токен выпускает и проверяет своё API, в httpOnly cookie. Supabase Auth не участвует.
12. Проверки роли мало: каждый обработчик с id записи проверяет право на ЭТУ запись (организация, проект,
    авторство). Раньше это делала RLS — теперь код.
13. Отбор — в SQL, не фильтрацией результата в коде и не на клиенте.
14. Интерфейс не защита: каждый адрес закрыт на сервере сам по себе.
15. Тело запроса валидируется по схеме с явным перечнем полей, лишние отбрасываются.
16. Файлы отдаёт API или короткая временная ссылка. Публичных бакетов нет.

## Тесты
17. Доступ каждой роли к каждому маршруту, включая запрос без авторизации.
18. Список открытых маршрутов сверяется с утверждённым: новый открытый адрес валит сборку.
19. Доступ к чужой записи: отказ на id записи другой организации.
20. Проверки в CI и перед пушем. Маршрут без теста прав считается незаконченным.
21. Снимок прав, измеренный тестами и хранимый в репозитории: любое расширение доступа видно строкой в diff.

## Принятое исключение из правила 4: одна учётка базы

Решение владельца портала от 2026-10-12: в базе Яндекса портал работает под одной выданной учёткой —
владельцем базы; вторая учётка не заводится. Правила по строкам (RLS) PostgreSQL к владельцу не применяет,
поэтому разграничение целиком на API (правила 5–15), а учётка окружается мерами:

| Мера | Механизм | Состояние |
|---|---|---|
| Остальным учёткам кластера данные и функции портала закрыты | у своих функций и типов снято право «всем», для будущих — не выдаётся; выданных прав нет (`migration/target/sql/load-lockdown.sql`); сверка `verify-closed.sql` | сделано, тест с соседней учёткой |
| Загрузка и очистка не попадут в другую базу той же учётки | отпечаток базы (`migration/target/pin.sh`) | сделано, тест |
| Читающая операция не может изменить данные | транзакция `READ ONLY` в единой обёртке транзакции API | с первым разделом |
| «Кто вошёл» не переходит между запросами | контекст только на транзакцию; при сбое отката подключение уничтожается | с первым разделом |
| API не меняет структуру базы | в коде сервера нет команд изменения структуры — тест по исходникам; миграции выполняются отдельной командой с машины миграций, не из API | с первым разделом |
| Запросы не подставляются | только параметризованные запросы; имена таблиц и колонок — из закрытого списка | с первым разделом |
| Подключения не исчерпываются | пул с явной долей общего лимита учётки, таймауты запроса и простоя | с первым разделом |
| Ошибочное или злонамеренное удаление обратимо | ночная проверенная копия (`migration/backup`), репетиция восстановления | при переносе базы |
| Изменение структуры вне миграций заметно | ежедневная сверка структуры с эталоном (`migration/target/sql/verify-facts.sql`) | при переносе базы |
| Действия прослеживаются | журнал пишущих операций API: кто, какая операция, ключ операции | с первым пишущим разделом |
| Секрет не утекает | файл окружения службы с правами `600`, вне репозитория, сборки и журналов | сделано для osp-api |

Чего эти меры не дают и что решается только на стороне кластера: пароль учётки открывает и другие её
базы; сетевое правило «только с адресов приложения» (правило 3); журнал подключений на стороне кластера.

- правило 21 на уровне таблиц — `tests/db/baseline/rights.json`.

Не переписано: правила 1, 2, 5, 6, 10–14 — данные, вход и права идут через Supabase. Правило 3 — на
стороне кластера.
