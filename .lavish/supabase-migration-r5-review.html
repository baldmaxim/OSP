Блокеры

Каждый пункт меняет формулировку гарантии или последовательность окна.

A6 выполняется после барьера, который запрещает A6

Блокер

В A4 node_role='retired' включает statement-trigger, отклоняющий запись во все таблицы public. Затем A6 пытается сделать upsert в public.users. Исключение в механизме заявлено только для ops.node_role.

План: строки 140–148 и 377–380.
Исправление: синхронизировать public.users до A4; перед A4 запретить signup; после A4 только сверить снимок auth.users ↔ public.users. Альтернатива — отдельный строго ограниченный cutover-bypass с аудитом, но он ослабляет гарантию барьера.

Outbox не покрывает DELETE, смену видимости и границу ночного дампа

Блокер

В механизме записан только «полный образ новой строки», но у DELETE нет NEW. Для UPDATE, меняющего владельца, SSE нужен и старый, и новый образ — сам план ниже уже требует оба. Кроме того, «зафиксировать последний id при старте дампа» даёт дыру при долгой незавершённой транзакции с меньшим id.

План: строки 195–218 и 354–357. PostgreSQL даёт OLD TABLE для UPDATE/DELETE и NEW TABLE для INSERT/UPDATE — это разные образы.
Исправление: хранить event_id, transaction id, PK, old_row, new_row, operation, schema version; проигрывать транзакциями с журналом применённых событий. Манифест дампа и безопасная граница outbox должны формироваться из одного экспортированного snapshot либо под кратким барьером. Добавить тест с long-running transaction вокруг границы.

JIT противоречит гарантии pending_mapping

Блокер

План обещает, что несопоставленный прежний пользователь не получит пустую учётку. Но resolver проверяет совпадение email и при несовпадении сразу делает JIT. Изменённый, отсутствующий или дублирующийся email превращает прежнего пользователя в «нового».

План: гарантия на строках 98–102; фактическая ветка resolver на строках 411–418.
Исправление: на период миграции отключить общий JIT: любой неизвестный sub → pending_mapping. Новых пользователей создавать только по явному provisioning-решению auth/администратора. После закрытия всех pending можно отдельно включить JIT с проверяемым признаком «новый пользователь».

Нет исполнимого шага для переключения всех чтений

Блокер

Этап 2 переводит через фасад только записи. Между тем 488 вызовов .from() живут в 52 файлах, а текущий Supabase client одновременно обслуживает Auth и REST. Нельзя просто заменить один base URL: в фазе A Auth должен остаться в Supabase, а данные уже идти через osp-api.

План: строка 297 против заявленных «старых клиентов ноль» на строке 358. Репозиторий: src/supabase/client.js создаёт единый client.
Исправление: добавить отдельный milestone «split transport»: supabaseAuth только для Auth и отдельный PostgREST-compatible data client через /api/rest/v1. Gate перед A: ноль .from/.rpc/.storage/.channel/.functions вне утверждённых адаптеров.

«Ровно один раз» не определено на границе PostgREST

Блокер

Pre-request может обнаружить дубликат и прервать SQL, но сам по себе не возвращает сохранённый бизнес-результат вместо выполнения основного PostgREST handler. Не описаны состояние «первый запрос ещё выполняется», таймаут ожидания и различие между stale version, RLS deny и отсутствующей строкой при результате 0 rows.

План: строки 152–173 и тесты 5, 19, 21. Формулировка «ровно один раз» на строке 92 сильнее описанного протокола.
Исправление: зафиксировать протокол: duplicate exception → osp-api читает private request_log → возвращает сохранённый результат; in-flight имеет отдельный статус и bounded wait. Для внешних саг формулировать «at-least-once delivery + idempotent/effectively-once effect». Классификацию 0 rows делать внутри конкретного RPC, а не общим триггером.

Backup под osp_migration нельзя запускать из osp-api

Высокий

Архитектура помещает экспортёр и ночной dump в osp-api, а dump выполняется ролью-владельцем. Компрометация долгоживущего приложения тогда даёт DDL/ownership-доступ ко всей базе. Плюс собственный outbox экспортируется асинхронно и не даёт нулевого RPO при потере всего кластера.

План: строки 122–124 и 195–218.
Исправление: отдельный backup/export workload и отдельный секрет; по возможности роль osp_backup с минимальными правами. Явно разделить сценарии: logical corruption, отказ БД, потеря кластера; для каждого записать RPO/RTO и основной механизм (PITR владельца кластера либо собственный dump+outbox).

Что в редакции 5 уже хорошо

Эти решения стоит сохранить.

Стабильный внутренний id

Прежний auth.users.id остаётся владельцем данных, а Keycloak sub вынесен в таблицу связей.

Раздельные фазы A и B

Перенос данных и смена identity имеют независимые откаты и отдельные smoke-наборы.

Fail-closed RLS-контекст

app.user_id задаётся transaction-local, runtime не владеет таблицами, session state не используется.

Стоп-точки и rehearsal

Dry-run, репетиции, явное подтверждение и условия допуска превращают миграцию в управляемый процесс.

Осознанный Odyssey-контур

Нет LISTEN, session locks и session SET; prepared statements отключены для transaction pooling.

Публичная витрина через API

Отказ от прямого anon-доступа к базе уменьшает поверхность атаки и позволяет фиксировать projection.

Минимальная редакция 6

Не переписывать весь документ — достаточно закрыть следующие контракты.

Сейчас

  • можно начинать стенд, инвентаризацию и заявки;
  • нельзя обещать zero-loss и exactly-once для всех сценариев;
  • нельзя выполнять runbook A/B буквально;
  • не определён полный frontend cutover и lifecycle пользователей.

После правок

  • A6 перенесён до барьера, Auth drift закрыт;
  • outbox имеет OLD/NEW, snapshot boundary и replay ledger;
  • JIT выключен для неизвестных identity до закрытия mapping;
  • есть split auth/data client и gate «0 прямых Supabase data calls»;
  • привилегии, backup role, RPO/RTO и onboarding зафиксированы.
Рекомендация по утверждению

Утвердить только этапы −1 и 0 и подготовку заявок этапа 1. Этап 2 начинать с transport split и privilege model. Окна A/B считать неутверждёнными до редакции 6 и прохождения архитектурного стенда по исправленным критериям.
